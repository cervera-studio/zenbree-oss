# Automations

An automation is a stored, ordered definition (find people, qualify with AI, find emails, add to a campaign, write to HubSpot) that a manual run or a schedule starts (#939). The API is `/v1/automations`, with two Celery tasks (`dispatch_automations` on the beat, `run_automation`). The web shows the automations, their runs and each step at `/automations`, and its editor creates, previews, publishes and deletes one (#940). No step sends a message or activates a campaign.

## Sub-features

- `auto-create` makes an automation and refuses a definition that names a list or campaign of another project, a step out of order or a cap above 100.
- `auto-review` puts the people of the first run of a version in the campaign as `draft`.
- `auto-approve` approves that run: later runs use the campaign's normal status.
- `auto-edit` bumps `version` on an edit of the definition or the cap, and sends the next run back to review.
- `auto-schedule` queues a due schedule once and moves it to its next slot.
- `auto-pause` pauses (cancels a queued run), cancels a run and deletes.
- `auto-cap` stops a run at its credit cap (SQL test only, see below).
- `auto-editor` creates an automation paused, previews it, publishes a new version of it and deletes it in the app.
- `auto-webhook` starts one run for each signed call that names one person of the list (#1031): the secret shown once, rotation, the calls that wait, the run page's call, and the refusals.
- `auto-signal` starts one run for each account of a watchlist whose new signals reach the minimum score (#1030): the editor's watchlist picker, the preview of recent signals, the signals seen before the trigger that start nothing, the run at that account only, once per signal, the run page's signal block, and the refusals.
- `auto-instantly` holds the people of a review run for an Instantly campaign and sends them as one batch at the approval (#1032): the editor's picker, the preview, the run page's hold and batch counts, and the approve warning for a running campaign.

## How to get to it (user POV)

Any HTTP client with an `sbk_` key ([api-keys](api-keys.md)) or a session token: `curl -H "Authorization: Bearer <key>" "$VERIFY_API/v1/automations"`.

In the app: sign in, pick the client in the sidebar, and open **Automations** under Campaigns. A run opens from the automation's **Runs** table (`/automations/<id>/runs/<run>`).

- **Run detail.** Each step is a card with its status in words, its counts (for `add_to_campaign`: `Added as drafts <n>` and the reasons under `Left out of the campaign`, such as `No usable email or LinkedIn 3`), credits, attempts, started and finished. No raw JSON key shows. A skipped step says why (`Skipped because no people were left after the earlier steps.`).

Its dialog warns that a running campaign can send to the run's people on its next step when the campaign is `active`, and has no warning for a `draft` campaign. An approved run whose held HubSpot write failed (`summary.hubspot_after_approval.error_code`), or has no `hubspot_after_approval` yet while its step held people, offers **Write to HubSpot again**; it does not when the automation's creator is gone (`user_id` null). ## Native review banner (#1113)

With a review version that has `add_to_campaign` and no `add_to_instantly`, open each run at 1280 px and 390 px:

- A run that failed, was cancelled or has an unknown outcome before enrolling anyone shows neither the approval-wait banner nor **Approve run**. Read back `status`, `review: true` and the step's absent or zero `output.enrolled` from the run API.
- A run that succeeded with zero enrolled people still shows the banner and **Approve run**: approving the version allows future runs without review.
- A run that failed, was cancelled or has an unknown outcome after its succeeded `add_to_campaign` step enrolled people keeps the banner and **Approve run**. Approve one and read back `approved_at` and the campaign's draft targets or their promotion, as in **Driving it**.
- A queued or running native review run keeps the approval-wait note (no **Approve run** yet). Read back `status` from the run API. A queued run has `review` NULL until the worker claims it, so the `review: true` read-back applies only to started runs.
- **Approve run** needs `automation_enrollments` rows when a worker outcome is staged: insert them with the staged step, or approval has nothing to promote. Record the campaign `status` first: a draft campaign means `promoted: 0` and the targets stay draft.
- Staging: stop beat (`bin/stack compose stop beat`) before staging a `running` run, or its reaper closes it as `unknown`. An automation allows one live (queued or running) run: stage the terminal runs first, then the queued and running cases one after the other, each in its own run. A staged `add_to_campaign` step output is `{"enrolled": n}` (a succeeded draft-campaign case may also carry `"status":"draft"`). A failed run needs a real code from `ERROR_CODES` in `web/lib/automations/run-view.ts` (for example `vendor_failed`); an unknown code renders "ha avuto un errore che non ha ancora una descrizione".
- Save run JSON, screenshots and DOM text under `$VERIFY_ARTIFACTS/automations/native-review/`. Use only the disposable verification database if a worker outcome must be staged; no vendor calls are needed.

## Webhook

A webhook automation starts one run for each signed Standard Webhooks call that names one person of its list. Start the stack with `API_PUBLIC_BASE_URL` set, or the panel says `L'URL non è disponibile. Chiedi a un amministratore o all'assistenza Zenbree.`: `export VERIFY_API_PORT=<api port>`, then `API_PUBLIC_BASE_URL=http://localhost:$VERIFY_API_PORT bin/stack up` (a prefix that reads `$VERIFY_API` expands before `bin/stack env` exists). `bin/stack` makes `OAUTH_TOKEN_ENCRYPTION_KEY`, which seals the secret. No email or vendor is needed. Check that no `RESEND_API_KEY`, `EMAIL_FROM`, `UNIPILE_DSN` or `UNIPILE_API_KEY` is set in the api and worker (`bin/stack compose exec -T api env | grep -cE '^(RESEND_API_KEY|EMAIL_FROM|UNIPILE_DSN|UNIPILE_API_KEY)=.'` prints `0`).

Preconditions:

- A person list made by CSV upload, so each row gets the dedupe key that the lookup reads: `curl -sS -X POST -H "Authorization: Bearer $K" --data-binary @inbound.csv "$VERIFY_API/v1/lists/upload?entity=person&name=Inbound"`, with the header `full_name,email,linkedin_url` and the rows `Ada Rossi,ada@acme.verify.test,https://www.linkedin.com/in/ada-rossi`, `Bob Neri,bob@acme.verify.test,` and `Cleo Gallo,cleo@acme.verify.test,`. Wait until `GET /v1/lists/imports/<id>` says `done`, then until `bin/stack psql -tAc "SELECT count(*) FROM audience_link_queue"` is `0`, as in [audience](audience.md). Ada's call names only her email, and her row is keyed by LinkedIn, so the lookup needs the link: a no-match answer is stored and replayed for that `webhook-id`.
- A `draft` campaign from an empty person list (`POST /v1/campaigns {"name":"Bozza","list_id":"<empty>"}` with the JWT of [Driving it](#driving-it)). Its drafts make the queue wait for the approval of the review run, which is what this drive shows. The queue waits only while the review run left drafts or HubSpot-held people (`discard.WAITING_FOR_APPROVAL`). A second automation on the same campaign and people enrolls nobody, so its calls start at once: give each automation fresh people and a fresh campaign.
- A company list, only for the Find people check: `curl … "$VERIFY_API/v1/lists/upload?entity=company&name=Aziende"`.

## Signal trigger

A signal automation starts one run for each account of its watchlist whose unused signals, first seen since `signal.since`, add up to its `min_score` (#1030). The run works on that account only. Make it in the editor, and use curl for the API cases. - `bin/fake-apollo` and the API key of [watchlists](watchlists.md) (`APOLLO_API_KEY=verify-key APOLLO_BASE_URL=http://host.docker.internal:<port>` before `bin/stack up`). The user needs at least 5 credits.

## Driving it

Preconditions:

- An API key for the seeded user, as in [watchlists](watchlists.md). The campaign routes take no `sbk_` key (401 `AUTH.TOKEN_INVALID`): sign in (`POST $VERIFY_WEB/api/auth/sign-in/email` with an `Origin` header and a cookie jar) and use the JWT from `GET $VERIFY_WEB/api/auth/token` for `/v1/campaigns`. No paid vendor is called: the steps driven need none, so no model, email vendor or HubSpot key is needed and nothing is sent.
- `find_people` runs against `bin/fake-apollo` (wiring in [saved searches](saved-searches.md); pick a free port when another session runs it). A company list `Aziende` with one row `{"name":"Hiring Srl","domain":"hiring.verify.test"}` is enough: the fake answers the same three people (`Anna`, `Bruno`, `Carla`, no email) for any domain.
- A person list `Persone` in the user's project (`INSERT INTO lists … entity 'person'`), empty at first. Create the campaign before the people exist: `POST /v1/campaigns` enrolls the people already on its list as draft targets, and those would then be `already_handled` for the automation. For the same reason the campaign needs one live target of its own: an `active` campaign with no `active` or `paused` target is `completed` by the campaign beat within a minute, and the run then fails with `campaign_ended`. So make a list `Seed` with one person (`Zed Verdi`, with an email), `POST /v1/campaigns {"list_id":"<Seed>"}`, `PATCH` two email `steps`, then `UPDATE outreach_campaigns SET status = 'active', activated_at = now()` and `UPDATE outreach_campaign_targets SET status = 'paused', paused_until = now() + interval '30 days'` for that campaign. Then insert into `Persone` rows whose `cells` are `{"full_name":"Ada Rossi","first_name":"Ada","last_name":"Rossi","email":"ada@acme.verify.test","email_status":"verified"}`, the same for `Bob Neri` and `Cleo Gallo`, each with a different `dedupe_key`. A second campaign from the empty `Persone` that stays `draft` serves the draft-campaign approval. The user needs no credits for these step lists.

- **Create.** `POST /v1/automations {"name":"Add leads","credit_cap":10,"definition":{"list_id":"<Persone>","steps":[{"type":"find_people","accounts_list_id":"<Aziende>","titles":["Head of Sales"]},{"type":"add_to_campaign","campaign_id":"<campaign>"}]}}` answers 201 with `version: 1`, `approved_version: null`, `enabled: true`. The same body with `credit_cap: 101` answers 422; with the steps listed `[{"type":"find_emails"},{"type":"qualify","brief":"x"}]` 422 (the order is fixed); with a campaign id of another project 422 `AUTOMATION.CAMPAIGN_NOT_FOUND`, with a list of another project 422 `AUTOMATION.LIST_NOT_FOUND`. A schema error is `{detail: {code: "REQUEST.INVALID_INPUT", message, fields}}`. Without a key: 401.
- **Preview.** Before the create, `POST /v1/automations/preview` with the create body's `credit_cap` and `definition` answers 200 with `problems: []`, `people: 3`, `with_email: 3`, `with_contact: 3` (Ada, Bob and Cleo), `accounts: 1`, `campaign: {"id":"<campaign>","name":…,"status":"active"}`, `people_per_run: 25` and `max_credits: 0` (no paid step). The same body with the campaign of another project and `{"type":"write_hubspot"}` appended answers `problems` with codes `["AUTOMATION.CAMPAIGN_NOT_FOUND","AUTOMATION.HUBSPOT_OFF"]` and `campaign: null`. `SELECT count(*) FROM automations` is the same before and after, and `apollo.log` gets no line.
- **First run, in review.** `POST /v1/automations/<id>/run` answers 202 with `status: queued`. Within a minute `GET …/runs/<run>` shows `status: succeeded`, `review: true`, `find_people` `succeeded` (`accounts: 1`, `people_found: 3`; `apollo.log` has one `POST /mixed_people/api_search`) and `add_to_campaign` `succeeded` with `output.status: "draft"`, `enrolled: 3` and `left_out: {no_contact: 3}` (the found people have no email). `GET /v1/campaigns/<campaign>/targets` has the three people as `draft`. The step output holds counts, no email.
- **Approve.** `POST …/runs/<run>/approve` answers the run with `approved_at` set and `summary.promoted: 3`, and the three targets are `active` (the campaign runs). A second `approve` answers the same `approved_at`. Approving a run that is not in review answers 409 `AUTOMATION.NOT_IN_REVIEW`.
- **Second run, normal status.** Insert two more people into `Persone`, `POST …/run`: the run shows `review: false` and the two enter as `active` at once. The campaign's `status` is still `active`; no message was sent by the automation (`SELECT count(*) FROM outreach_campaign_sends` changes only by the campaign's own beat).
- **Edit.** `PATCH … {"credit_cap":20}` answers `version: 2`; a rename answers the same version. Insert one more person; the next run shows `version: 2`, `review: true` and the person enters as `draft`. Do not approve it: edit the `definition`, which answers `version: 3`, then approve that run: 409 `AUTOMATION.RUN_OUTDATED` (the earlier runs are approved or not in review, so they answer the same `approved_at` or `NOT_IN_REVIEW`). Right after that edit, the person of the version 2 run is gone from `outreach_campaign_targets` and from `automation_rows` (a target that was sent anything would stay). Run version 3: it takes the same person again as `draft`; approve it: `summary.promoted: 1`, the person is `active`, and the campaign holds no `draft` target.
- **Drafts keep a running campaign open.** A campaign whose only people are an automation's drafts waiting for approval stays `active`. Make a person list with two people (emails), a campaign from that list while it is empty (`draft`, two steps), an automation with only `add_to_campaign` to it, run it (the two enter as `draft`), then `UPDATE outreach_campaigns SET status = 'active'`. After three beats (`campaign.dispatch.done` in `bin/stack logs worker`, `completed: 0`) it is still `active`; approving the run promotes both to `active`. A control campaign from a list with one person (a plain `draft` target, no automation) set `active` the same way is `completed` by the next beat, as on main.
- **Approve into a draft campaign.** An automation that adds to the `draft` campaign: its review run's people enter as `draft`, and approving answers `summary.promoted: 0`; they stay `draft` and the campaign stays `draft`. People already active in the other campaign are refused before any credit as `in_other_campaign`, so give this run fresh people. Activating the campaign needs a mailbox: not driven.
- **Schedule.** `PATCH … {"trigger":{"kind":"schedule","cadence":"daily"}}` shows `next_run_at` now; within a minute the beat queues one run and `next_run_at` moves a day on.
- **Pause, cancel, delete.** `POST …/run` then `PATCH … {"enabled":false}`: the queued run is `cancelled` with `error_code: automation_paused`, and `POST …/run` answers 409 `AUTOMATION.PAUSED`. `POST …/runs/<run>/cancel` ends a queued run. `DELETE` answers 204.
- **HubSpot held in review.** Insert the kill switch `settings ('vendor_disabled:hubspot', 'true')` first, so no beat or task reaches HubSpot. With no HubSpot connection, `POST` with steps `[{"type":"write_hubspot"}]` answers 422 `AUTOMATION.HUBSPOT_OFF`. Insert a fake `user_oauth_connections` row (`provider 'hubspot'`, `status 'connected'`, `crm_write_back true`, `granted_scopes` with `crm.objects.contacts.write`, any `refresh_token_encrypted`): the `POST` answers 201, and the run is `review: true` with the step `succeeded`, `output.held_for_approval: <n>`, `automation_runs.hubspot_row_ids` holding them and no `crm_contact_writes` row. Approving it ends with `summary.hubspot_after_approval.error_code: vendor_disabled` and the people still held. Delete the connection: the next run is `failed` with `invalid_configuration`, and a `PATCH` answers 422 `AUTOMATION.HUBSPOT_OFF`.
- **Another organization.** A second `seed-user` with its own key gets an empty list, and 404 `AUTOMATION.NOT_FOUND` on the automation's runs, run, `run`, `approve`, `cancel`, `PATCH` and `DELETE`, also with the owner's `X-Project-Id`.
- **Proof.** Save the JSON answers under `$VERIFY_ARTIFACTS/automations/`.
