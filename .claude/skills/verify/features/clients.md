# Clients (projects)

Projects are an organization's clients (#307). The sidebar's client switcher picks the active one, and every page then shows that client's data: its business profile, exclusions, senders (mailboxes, LinkedIn), campaigns and inbox. A sender is one row of the organization that several clients can use (`project_senders`). Creating a client opens the onboarding profile step for it. A campaign sends only through its own client's senders. Any member can use a client's senders, but only whoever connected one, or an admin, can disconnect or replace it.

## Sub-features

- `clients-switcher`: `button "Cliente: <name>"` lists the organization's clients, plus `Nuovo cliente`, `Rinomina cliente` and `Elimina cliente`. Choosing one re-renders the page for it.
- `clients-crumb`: Panoramica, Liste, Campagne and Risposte start their topbar path with the active client: `navigation "Percorso"` reads `<client> / <page>`. The name is plain text, not a link. It follows a switch with no reload, and it truncates on phone while the page name stays whole. It appears once the switcher has its list, so a page adds no `GET /v1/projects`.
- `clients-new-onboarding`: `Nuovo cliente` names the client, makes it active and opens `/onboarding` (`Parlaci della tua azienda`) for it.
- `clients-profile`: each client has its own profile. The sidebar profile link reads `<user> <client's company>`, and the profile step's `Dove lo uso` rail ends with `In ogni chat.`
- `clients-exclusions`: `/settings/exclusions` lists the active client's rules only. A CSV import into a client drops only that client's matches.
- `clients-senders`: `/settings/senders` and `/settings/integrations` show the active client's mailboxes and LinkedIn. A campaign's builder shows its own client's mailboxes, whichever client is active.
- `clients-campaigns`: `/campaigns` lists the active client's campaigns. Activating a campaign whose client has no mailbox is 422 `CAMPAIGN.NO_SENDER`, even when another client of the same user has one.
- `clients-inbox`: `/inbox` lists the active client's replies. A reply opened by id (a notification, a campaign's people) opens whichever client is active.
- `clients-disconnect`: another member sees the mailbox and LinkedIn rows without `Scollega`. `DELETE` is 403 `INTEGRATIONS.DISCONNECT_FORBIDDEN` for them; their admin may. Connecting their own account where a colleague's serves the client is 403 `INTEGRATIONS.REPLACE_FORBIDDEN` (SQL-tested; the connect flow needs OAuth keys).
- `clients-delete`: `Elimina cliente` asks in `alertdialog "Eliminare «<name>»?"` (`button "Elimina cliente"`). Deleting a client deletes its chats, lists, campaigns, inbox, profile and exclusions, and unlinks its senders; they stay with the organization and the clients they serve. The API refuses the last client (409 `PROJECT.LAST`) and, for anyone but an admin or the sender's connector, a client that uses a colleague's live sender (409 `PROJECT.HAS_SENDERS`).
- `clients-accounts`: senders are keyed by account: one member can hold two Gmail accounts for two clients in one organization, each client's Mittenti showing its own. Without OAuth keys, fake the connect in SQL: a second `user_oauth_connections` row with its own `provider_account_id` (the provider's `sub`), linked in `project_senders` to the other client.
- `clients-cap`: an admin sets a monthly credit cap per client (`PATCH /v1/projects/{id} {"credit_cap":N,"credit_cap_mode":"hard"|"soft"}`; a member gets 403 `AUTH.ORG_ADMIN_ONLY`). The switcher shows `<spent>/<cap> crediti questo mese` (`1/1 credito questo mese` at a cap of 1; red past it). `hard` refuses a hold past it: a saved search run fails `project_cap_reached` with no hold; `soft` lets it hold and only reports `over_cap`.
- `clients-backfill`: on a stack upgraded from main, every existing project gets its creator's profile and exclusions (copied), and every sender is linked to every project of whoever connected it in their own organization: campaigns in all of them keep sending. A project a user created in a team organization they joined gets none of their personal profile, exclusions or senders (it goes through onboarding).

## How to get to it (user POV)

- Sidebar, top of `navigation "Navigazione principale"`: the client switcher `button "Cliente: <name>"`, outside any region.
- `/campaigns`, `/inbox`, `/settings/senders`, `/settings/integrations`, `/settings/exclusions` and `/settings/profile` follow the active client.
- API: every call takes `X-Project-Id: <project id>`. Without it, or with a project outside the active organization, the API answers for the organization's default project. The web sends the `zb-project` cookie's value.

## Driving it with bin/browser

Preconditions: a stack (`VERIFY_ID=307` used its own ports `VERIFY_WEB_PORT=13307 VERIFY_API_PORT=18307`, since others ran in parallel), and a user who opened the app once (the sidebar creates the default project). SQL is setup only. In SQL, "the user's default project" is `(SELECT id FROM projects WHERE organization_id = default_organization('<uid>') ORDER BY created_at LIMIT 1)`. A second client is `POST /v1/projects {"name":"Cliente Beta"}` with the session token, or `Nuovo cliente`.

- **Backfill (upgrade from main).** Build the stack from a detached worktree of `main` (`git worktree add --detach ../zenbree-307-base <main sha>`, then `bin/stack up` from its `.claude/skills/verify`). Seed with the API and the session token: two projects, `PUT /v1/onboarding/profile` (with an exclusion line), `POST /v1/exclusions`, a CSV list per project (`POST /v1/lists/upload?project_id=`) and campaigns (one in the first project, two in the second). Seed in SQL a google and a unipile `user_oauth_connections` row (main schema: no `project_id`) and one `outreach_inbound_messages` row tied to the first project's campaign. Then run `bin/stack up` from this checkout with the same `VERIFY_ID`/ports: `bin/stack logs migrate` prints `migrations applied: 20261006134459_project_clients.sql`. Read back: `business_profiles` has one row per project with the same company and `exclusion_lines`; `exclusions` repeats both rules (`source` kept) per project; each sender is still one row, and `project_senders` links it to both projects; campaigns follow their list's project; the reply sits in the first project. Then both clients' Mittenti pages show the same mailbox. A project of a user with chats but no profile gets a `completed_at` row (no onboarding forced).
- **Switcher.** `bin/browser click button "Cliente: Il mio cliente"`: `menuitem` per client, then `Nuovo cliente`, `Rinomina cliente`, `Elimina cliente`. `bin/browser click menuitem "Cliente Beta"`, then `bin/browser wait button "Cliente: Cliente Beta"` (a client with no profile and no chat opens `/onboarding`: choose `button "Salta per ora"`). The page re-renders (on `/inbox` the list changes in place), and `bin/browser eval "document.cookie"` shows `zb-project=<Beta id>`.
- **Crumb.** On `/lists`, `bin/browser eval 'document.querySelector("header.sticky nav").innerText'` reads `Il mio cliente\n/\nListe`; after the switch above, `Cliente Beta\n/\nListe` with no reload. Repeat on `/`, `/campaigns` and `/inbox`. For a long name, rename a client to 80 characters (`PATCH /v1/projects/<id> {"name":…}`) and run the same `eval` and `document.documentElement.scrollWidth` with `--width 390`: the width stays 390. To count `/v1/projects`, grep `"GET /v1/projects HTTP` in `bin/stack logs api` before and after each step. The client address of each line tells the caller: the network gateway is the browser, and the web container's address is the server (`docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}} {{.Gateway}}{{end}}' <project>-web-1`).
- **Inbox, campaigns, senders per client.** On each client open `link "Risposte"`, `link "Campagne"`, and `Impostazioni` › `Mittenti`. Only that client's reply, campaigns and mailbox show; the other client reads `Ancora nessuna risposta qui` and `Nessuna casella di invio. Collegane una in Integrazioni.`
- **Builder.** With `Il mio cliente` active, open a campaign of `Cliente Beta` (`/campaigns/<id>`): `checkbox "<Beta's mailbox>"` under `Invia da`. A campaign of `Il mio cliente` reads `Nessuna casella collegata: la campagna non può partire.` `POST /v1/campaigns/<id>/activate` (with a step saved) answers 422 `CAMPAIGN.NO_SENDER`.
- **New client.** `menuitem "Nuovo cliente"`, `bin/browser fill textbox "Nome del cliente" "Cliente Gamma"`, `button "Salva"`, then `bin/browser wait-url /onboarding`. The wizard opens on `Parlaci della tua azienda`. Without an LLM key `Analizza` fails, so set the profile with `PUT /v1/onboarding/profile` and `X-Project-Id: <Gamma id>`, then reload: `Il tuo profilo`. Add a rule with `button "Aggiungi" --nth 4`, fill `textbox "Da non contattare mai, voce 1"`, and click `Conferma e proponi segmenti` (segments then fail, keyless). The rule lands in Gamma only. Finish with `Salta per ora`: the sidebar profile link reads `Ada Verify Gamma Logistica`.
- **Exclusions per client.** `Impostazioni` › `Esclusioni` on each client lists only its rules. `POST /v1/lists/upload/preview?entity=person` with the same CSV and each client's `X-Project-Id` counts `excluded` by that client's rules. An import into Gamma keeps a person whose domain only `Il mio cliente` excludes.
- **Member and disconnect.** Seed a second user and a `member` row in the first user's organization (`role 'member'`), and sign in as them. `button "Menu account"` › `menuitem "<org>"` switches organization and forgets the old client (`zb-project` then points at the new org's default). Switch to the client with senders and open `Integrazioni`: the mailbox and LinkedIn rows have no `Scollega`. With their token: `GET /v1/integrations/mailboxes` shows `"can_disconnect":false`, and `DELETE /v1/integrations/mailboxes/<its id>` and `DELETE /v1/integrations/linkedin` are both 403 `INTEGRATIONS.DISCONNECT_FORBIDDEN`. `PATCH /v1/campaigns/<a colleague's campaign>` is 200 (no owner gate). Deleting a client only unlinks its senders, and a member may delete only a client whose senders are their own (else 409 `PROJECT.HAS_SENDERS`): `SELECT count(*) FROM user_oauth_connections` is unchanged.

- **Cap.** As the admin, `PATCH /v1/projects/<client> {"credit_cap":1,"credit_cap_mode":"hard"}`. Setup in SQL a committed `deduction` of 1 with that `project_id` (this month's spend: no vendor key means nothing real spends). Create a saved search on one of the client's lists (`POST /v1/saved-searches`, then `PATCH {"enabled":true}`) and `POST /v1/saved-searches/<id>/run`; after the next beat (about a minute) `GET …/runs` shows `failed`, `error_code` `project_cap_reached`, `reservation_id` null. Switch the mode to `soft` and run again: the run holds (a `reservation` row with the `project_id`, then `released`, `search_failed` without an Apollo key), and `GET /v1/projects` shows `over_cap: true`. The switcher reads `Cliente Beta 1/1 crediti questo mese`. As a member, the same `PATCH` is 403.
- **Cap settings page (#327).** `Impostazioni` › `link "Cliente"` (`/settings/client`) shows `heading "Cliente: <active client>"` and `region "Tetto mensile di crediti"` with `Questo mese: <spent> di <cap> crediti (<pct>%)` and `progressbar "Crediti spesi questo mese"` (no cap: `Questo mese: <spent> crediti spesi.`, at 1 `Questo mese: 1 credito speso.`). An admin gets `radiogroup "Tetto"` (`Nessuno`, `Avviso`, `Blocco`), `spinbutton "Crediti al mese"` and `button "Salva"` (toast `Tetto salvato.`); psql `SELECT credit_cap, credit_cap_mode FROM projects` reads back, and `Nessuno` stores both null. A member sees only `Tetto: <cap> crediti al mese · …` (at 1 `Tetto: 1 credito al mese · …`; 1500 reads `1.500`) (or `Nessun tetto: …`), no form. Under the cap, `region "Profilo di vendita: <company>"` has `link "Rifai il profilo"` (`/onboarding?redo=1`). A client that never finished or skipped onboarding goes to `/onboarding` instead: choose `Salta per ora` first.

## Gotchas

- The `zb-project` cookie outlives sign-out. The next user's calls name a project outside their organization, and the API falls back to their default; the switcher then resets the cookie.
- The first client is named in the language saved on the user who first needs it (#699): `Il mio cliente` for a user who signed up in the Italian browser, `My client` for one made by `bin/stack seed-user`, whose request names no language. The names below assume the Italian one.
- The first saved profile renames that first client to the profile's company name (#794: `PUT /v1/onboarding/profile` with `"company_name": "Gamma Logistica"` turns `My client` into `Gamma Logistica`). A name the user chose, such as `Cliente Beta`, stays (`projects.name_is_placeholder`). After the analyse or a profile save, the switcher no longer reads `Il mio cliente`.
- A page fires several API calls at once. Each resolves the active project, so the first visit creates the default project under an organization row lock. A stack used before that lock (f5f0c12) can hold two `Il mio cliente` rows for one organization.
- A chat turn needs an LLM key. The agent reading the chat's client profile (`api/tests/test_onboarding.py::test_the_agent_reads_the_profile_of_its_chats_project`) and the hard cap on a chat turn (`api/tests/test_agent.py::test_a_hard_project_cap_refuses_a_paid_step_at_the_cap`) are covered by tests, not driven.
- Saved search runs and AI fills under a cap are dispatched by the beat or the worker: wait about a minute before reading a run.
- `Nuovo cliente` and the switcher work only once the sidebar has listed projects. Right after sign-in, wait for `button "Cliente: …"`.
