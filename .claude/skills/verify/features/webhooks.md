# Webhooks

An admin of the organization registers https endpoints that receive signed events (#93); endpoints belong to the organization (#323): every admin manages all of them, and they receive every member's events, never another organization's: `list.completed`, `contact.replied`, `campaign.finished`, `sequence.stopped`. Contract: `docs/contracts-m1.md`, section Webhooks. Admins manage them on Settings › Webhooks (#943); the API stays usable with an `sbk_` key.

## Sub-features

- `hook-crud` lists, creates (the `secret` is in the create response only) and deletes endpoints through `/v1/integrations/webhooks`. JWT or `sbk_` key. `GET` returns `{"webhooks": […], "events": ["list.completed", "contact.replied", "campaign.finished", "sequence.stopped"]}`. An organization has at most 10 endpoints: the eleventh `POST` is 409 `WEBHOOKS.CAP_REACHED`.
- `hook-refuse` rejects `http://`, private, loopback and metadata hosts (422 `WEBHOOKS.INVALID_URL`) and unknown events (422).
- `hook-test` `POST /v1/integrations/webhooks/<id>/test` answers with the endpoint's HTTP status, delivered by `worker-webhooks`.
- `hook-team` a member's event reaches the endpoint an admin set up; an endpoint in the member's own organization does not fire; a member gets 403 on every webhook route (#323).
- `hook-ui` (#943) `/settings/webhooks`, admins only: the add form (name, receiver URL, event checkboxes built from the API's `events`), the one-time secret panel, a table of endpoints (name, receiver host only, event badges, added date) with `Invia test`, `Consegne` and `Elimina`, and below it the delivery history of the endpoint chosen.
- `hook-history` (#943) `GET …/{id}/deliveries`: the newest 50 attempts, `{event_id, event_type, is_test, attempt, attempted_at, status_code, category, will_retry}`, no payload, URL or secret. A test is `is_test: true`.
- `hook-deliver` an event reaches subscribed endpoints from the worker. No answer, a 5xx or a 429 is retried after 30 s, 300 s and 1800 s (`RETRY_DELAYS_S` in `api/app/integrations/webhooks.py`) with the same `webhook-id`; a 410 marks the endpoint revoked (`gone_at`): it stays listed with its history until an admin deletes it.

## How to get to it (user POV)

- Choose `link "Impostazioni"` in the sidebar, then the tab `link "Webhook"` in `navigation "Impostazioni"` (admins only: a member does not see it, and `/settings/webhooks` tells a member that only admins manage webhooks). It opens `/settings/webhooks`.
- Or call `/v1/integrations/webhooks` with the session JWT or an `sbk_` key ([API keys](api-keys.md)).

## Driving it with bin/browser

Preconditions: a seeded user, signed in; an `sbk_` key from `POST /v1/me/api-keys` with the session JWT (`bin/browser eval "fetch('/api/auth/token').then(r => r.json())"`).

The SSRF guard refuses every local host, at create and at delivery, and it is never relaxed for a drive: no receiver on `localhost` or in the stack can be reached. Never point an endpoint at an external service. Use an https literal from the documentation range `203.0.113.0/24` (RFC 5737, `https://203.0.113.10/hook`): it passes the create check without DNS, and no server answers there, so a delivery ends `no answer` (`timeout` or `unreachable`). A delivery that a receiver answers (a 2xx, 503 or 410) cannot be driven under this rule: the SQL seeds below and `api/tests/test_webhook_deliveries.py` cover those rows.

- **`hook-crud` / `hook-refuse`.** `curl` `GET`, then `POST` with `{url, label, event_names}` for `http://example.com/hook`, `https://127.0.0.1/hook`, `https://169.254.169.254/latest/meta-data`, an unknown event, then `https://203.0.113.10/hook` (`campaign.finished`) and `https://203.0.113.11/hook` (`sequence.stopped`). `GET` again: no `secret` field.
- **`hook-ui`.** Sign in as the seeded admin and get past onboarding (see [api-keys](api-keys.md) Preconditions).
  1. `bin/browser click link "Impostazioni"`, `bin/browser click link "Webhook"`, `bin/browser wait-url /settings/webhooks`. A new team sees `Non hai ancora aggiunto webhook.`
  2. Refusal first: fill `textbox "Nome"` with `local`, `textbox "URL del destinatario"` with `https://localhost:8080/hook` (a local receiver) and click `button "Aggiungi webhook"`: `alert` `Inserisci un URL https pubblico valido.` and no row. Repeat with `http://203.0.113.10/hook` (the browser's URL field may refuse it before the API does) and `https://169.254.169.254/latest`.
  3. Add: name `verify`, URL `https://203.0.113.10/hook`, leave the four event checkboxes on (`Lista completata`, `Contatto ha risposto`, `Campagna terminata`, `Sequenza interrotta`; uncheck one and the POST body has three). `status` region `Webhook aggiunto: copia il suo segreto di firma` with `textbox "Segreto di firma"` holding `whsec_…` focused and selected, and `button "Copia"`. `bin/browser eval "document.querySelector('input[aria-label=\"Segreto di firma\"]').value"` starts with `whsec_`. Click `button "Ho salvato il segreto"`: the panel is gone and no `whsec_` is in `bin/browser text`. Reload: the endpoint is in the table, the secret is not anywhere on the page.
  4. The table shows the host `203.0.113.10` only, never a path. Seed a path token: `UPDATE user_webhooks SET url = 'https://203.0.113.10/hooks/tok-9f8e'` (`bin/stack psql`), reload: the page still prints only the host.
  5. `button "Invia un test a verify"`: the button spins while the route waits (up to 45 s), then an error toast `Il destinatario non ha risposto.` (nothing answers on `203.0.113.10`). Choose `button "Mostra le consegne di verify"`: one row, `Test` badge, `Nessuna risposta`, a `Tempo scaduto` or `Irraggiungibile` badge, attempt 1, no `Nuovo tentativo in coda`.
  6. Seed history by SQL (`INSERT INTO webhook_deliveries (organization_id, webhook_id, event_id, event_type, attempt, status_code, category, will_retry) …`, the organization and endpoint ids from `user_webhooks`): `('…', 'ev1', 'campaign.finished', 1, 503, 'server_error', true)`, `('…', 'ev1', 'campaign.finished', 2, 200, NULL, false)`, `('…', 'ev2', 'sequence.stopped', 1, 404, 'rejected', false)`. Choose `button "Aggiorna"`: rows show the status, `Errore del server` with `Nuovo tentativo in coda`, `Consegnato` and `Rifiutato`; the two `ev1` rows share the Event ID. The help line says a retry repeats the event ID.
  6b. Receiver revoke (#943): `UPDATE user_webhooks SET gone_at = now() WHERE label = 'verify'` and insert one `('…', 'ev3', 'campaign.finished', 1, 410, 'gone', false)` history row, then reload. The row's status badge reads `Revocato dal destinatario`, `button "Invia un test a verify"` is disabled, `Consegne` still lists the `Non più attivo: webhook revocato` row under a warning line, and `Elimina` works. The endpoint still counts toward the cap of 10. `POST …/<id>/test` through the API answers 409 `WEBHOOKS.REVOKED`.
  7. Phone (`bin/browser resize 390 844`): the table becomes cards, each with `Invia test`, `Consegne`, `Elimina` at full touch height; the history cards keep the result badge first. Tab through the form: every checkbox and button takes the keyboard focus, and `Space` toggles a checkbox.
  8. `button "Elimina il webhook verify"` opens `alertdialog "Eliminare il webhook «verify»?"` with two consequences; `button "Elimina webhook"` removes the row and the history, and `SELECT count(*) FROM webhook_deliveries` is 0 for it.
  9. As a member of the team (see `hook-team`) the tab is missing and `/settings/webhooks` shows `Solo gli admin del team gestiscono i webhook.`
  10. At the cap: add endpoints (SQL) up to 10: `Hai raggiunto il limite…` and `button "Aggiungi webhook"` is disabled.
- **`hook-deliver`** (needs a receiver that answers, so it is out of reach under #943; kept for a drive that has one). Setup by SQL (`bin/stack psql`): for the user, one active campaign whose only target is `replied`, and one active campaign (`activated_at` an hour ago, one email step with `send_after_days: 0`) whose only target is `active` with an email that is also in `exclusions`. Within a minute the beat completes both campaigns and excludes the target. `TAIL=600 bin/stack logs worker-webhooks | grep webhooks.` shows (deliveries run only there, on the `webhooks` queue: `bin/stack logs worker` has none) `webhooks.delivered` with `status: 503` for `campaign.finished` (and again ~30 s later, same `webhook_id`), `status: 410` for `sequence.stopped`, then `webhooks.deregistered_gone`. Read side: `SELECT label, revoked_at IS NOT NULL, left(secret_encrypted, 6) FROM user_webhooks` (the secret is Fernet ciphertext, `gAAAAA…`, never `whsec_…`).
- **`hook-team`.** Team from [team](team.md): Ada (admin) creates `https://203.0.113.10/hook` (`campaign.finished`, `sequence.stopped`); Bo, switched to his own organization (`POST /api/auth/organization/set-active`), creates `https://203.0.113.11/hook` there and switches back; Bo's `GET` in the team lists only Ada's; Cy's (member) `GET` and `POST` are 403 `AUTH.ORG_ADMIN_ONLY`. Cy uploads a list and creates a campaign in the team; setup by SQL: the campaign `active`, its only target `replied`. Within a minute Ada's deliveries list (`GET …/<id>/deliveries`) has one `campaign.finished` row (no answer, `timeout` or `unreachable`) and Bo's endpoint has none; nothing answers on the documentation range, so there is no `status_code`. Driven 2026-10-06 with `VERIFY_ID=323`.
- **`hook-test`.** `POST …/<id>/test` → `{"status":null}` when the receiver does not answer; on a revoked or deleted one → 404 `WEBHOOKS.NOT_FOUND`. A receiver that answers is out of reach (see above).
- **`hook-history`.** `GET …/<id>/deliveries` with the session JWT or an `sbk_` key: the rows above in the order newest first; another organization's or a deleted endpoint → 404 `WEBHOOKS.NOT_FOUND`; a member → 403 `AUTH.ORG_ADMIN_ONLY`. The body has no `url`, `secret` or `data`.
- **Cap.** Create endpoints up to 10, then one more: 409 `WEBHOOKS.CAP_REACHED`. Delete them afterwards (`DELETE …/<id>` → 204).
- Check that no log carries the secret: `bin/stack logs api`, `worker` and `worker-webhooks`, piped to `grep -c whsec_`, all print 0.

## Gotchas

- #943 changed the drive: httpbin.org was removed because the brief and the guard allow no external receiver. The `hook-deliver` steps below that need an answering receiver (the 503 retry and the 410 revoke by the beat) are not drivable now; `api/tests/test_webhooks.py` and `test_webhook_deliveries.py` cover them. The #943 UI was not driven when this recipe was written: the verifier records the first drive here.

- Not reachable here: `list.completed` needs a chat turn that adds rows (an LLM key and search vendor keys), `contact.replied` needs a signed inbound email (Resend) or a Unipile webhook. Both are covered by the SQL tests.
- Driven 2026-10-10 at dae0d57 (API only): list with `events`, the three refusals and the unknown event, create, the test call, the cap, delete, and no `whsec_` in the logs. Delivery and retries by the beat were not driven again.
