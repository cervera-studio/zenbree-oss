# API, SSE and tool contracts

`/openapi.json` (served with `/docs`) is the source for request and response shapes: field names, types, required fields and status codes of the routes it lists. This document holds what that schema cannot say: what a field means, which events a stream sends and in what order, which error codes exist and when they fire, who may call a route, and the contract of each agent tool. Where a field name is enough, this document does not repeat it.

The API speaks snake_case JSON. Errors are `{detail: {code, message}}` (see Errors below).

A change to a stream, an error code, a field's meaning or a tool contract updates this file in the same PR. A change to a shape updates the Pydantic model, which updates `/openapi.json`.

Routes that `/openapi.json` hides (`include_in_schema=False`): `POST /v1/inbound/email`, `GET /v1/unsubscribe/{token}`, `GET /v1/integrations/mailboxes/{provider}/callback`, `GET /v1/integrations/hubspot/callback`, `POST /v1/webhooks/hubspot`, `POST /v1/integrations/instantly/webhooks/{subscription_id}` and `POST /v1/automation-hooks/{hook_id}`. This document names them where they matter.

## Errors

Every HTTP error body is `{detail: {code, message, ...}}`. `code` is `DOMAIN.REASON` (UPPER_SNAKE with a domain prefix) and stable: the web translates by it. `message` is English for developers and is never shown to users. Routes build the error with `api_error(status, code, message)` (`app/core/errors_http.py`), and `tests/test_error_shape.py` fails on an `HTTPException` built anywhere else. A `Result` error goes through `unwrap_or_raise`, which takes the status from the code's suffix, else its domain, and may add recovery keys (`suggestion`, `valid_values`, …). The errors that no route raises have their own codes (`app/core/error_handlers.py`):

- 422 `REQUEST.INVALID_INPUT` for a request that fails validation, with `fields: [{loc, msg, type}]`: pydantic's location, message and error type. `/openapi.json` types every 422 as `InvalidInputError` (`detail: {code, message, fields?}`): `fields` exists only for `REQUEST.INVALID_INPUT`, and a route may send its own 422 code without it. The rejected value is never echoed back. A non-numeric `Content-Length` is also `REQUEST.INVALID_INPUT` (400, without `fields`).
- 404 `REQUEST.NOT_FOUND` (no such route), 405 `REQUEST.METHOD_NOT_ALLOWED` (with `Allow`), and `REQUEST.HTTP_<status>` for any other status Starlette answers itself. 413 `REQUEST.TOO_LARGE` is under Request size.
- 500 `INTERNAL.UNEXPECTED` (`message: 'internal error'`) for an unhandled exception. It carries the CORS headers, so the browser can read it. The server logs the traceback and reports the error. A streaming response that already started cannot change its status: it just ends.

A step error of a campaign (`CAMPAIGN.INVALID_STEPS`, `LINKEDIN_NO_INVITE`, `LINKEDIN_DM_DELAY`, `COPY_TOO_LONG`, `SUBJECT_LINE_BREAK`, `PLACEHOLDER`) adds `step`, the step's number, when the API knows it (absent otherwise), so the web names the step.

SSE `error` frames (every stream, see Server-sent events) carry the same `{code, message}`. The chat's codes are under Server-sent events.

## Authentication and organizations

- **Auth abuse protection.** Better Auth registers `sentinel()` on the server and `sentinelClient()` in the browser. The public `BETTER_AUTH_IDENTIFY_URL` is embedded at build time; changing it requires rebuilding the web image. Sentinel uses the server-only `BETTER_AUTH_API_KEY` already shared with the dashboard plugin; without it, infrastructure checks may fall back to allow mode. The client handles identification and automatic proof-of-work challenges.
- **Credentials.** The web mints a short-lived EdDSA JWT (Better Auth `jwt` plugin). The API verifies it against the web's JWKS (`AUTH_JWKS_URL`). The claims are `sub` (user), `org` (active organization), `role` (Better Auth's global role, which means the back office) and `email`. A token without `org` gets the user's own organization. Routes that use `current_user_or_api_key` also accept a `sbk_` personal API key.
- **Role in the organization** is never a claim. On every call the API reads the caller's `member` row for (`sub`, `org`). No row (removed since the token was minted) gives 401 `AUTH.NOT_A_MEMBER`. The read repeats at each database access of the call, so a member removed or banned while a call runs gets the same 401 from the next access. A stream that has already started ends with an `error` frame `AUTH.NOT_A_MEMBER` within 30 s (see Server-sent events), and a reconnect gets the 401. The row's `role` is `admin` or `member`. A `sbk_` key acts as its creator with the creator's current role. A key whose creator left the organization gives 401 `AUTH.API_KEY_INVALID`.
- **Admin-only** for the organization (403 `AUTH.ORG_ADMIN_ONLY` for a member, with a JWT or a key): API keys, webhooks, billing, and invites, role changes and removals (Better Auth endpoints that its plugin refuses for members). Back-office routes (`/v1/admin/*`) use `require_admin`, which reads the global `role` claim: 403 for a non-admin, 401 without a token.
- **Bans** (`user.banned`, until `banExpires` if set) refuse every call the same way: 401 `AUTH.NOT_A_MEMBER` with a JWT, 401 `AUTH.API_KEY_INVALID` with a key. Keys are not revoked, so an unban restores them. After Better Auth's `admin/ban-user`, the web calls `POST /v1/admin/users/{id}/after-ban`, which cancels the user's queued and running jobs like `POST /v1/jobs/{id}/cancel` does (503 `JOB.CANCEL_UNAVAILABLE` when Redis is down). A turn that reaches its next database access before the cancel ends `failed` with `AUTH.NOT_A_MEMBER` instead (see Server-sent events). The campaign dispatcher, the saved-search scheduler and the webhook sender skip what a banned user created. Their `status` and `enabled` fields never change, so an unban resumes everything at the next beat. A scheduled search missed meanwhile runs once.
- **Roles** are `admin` and `member`. Better Auth's `owner` is refused on invite and role change. The last admin cannot be removed or demoted, and neither can the organization's founder: the user whose own organization it is (slug equals their id) or who created the team (slug `<their id>/<uuid>`). `/organization/leave` is disabled. Any user can create a team (`/organization/create`, #676): the server sets the slug, the creator becomes its admin and it becomes the active organization, and its wallet opens with 0 credits (the signup grant is once per user). A user creates at most 4 teams besides their own (counted by founder, so leaving one frees nothing); past that Better Auth answers `YOU_HAVE_REACHED_THE_MAXIMUM_NUMBER_OF_ORGANIZATIONS`. An invitation links `/invite/{id}`, where the invitee accepts or declines; accepting makes that organization the active one. An invitation carries its inviter's authority (#982): accepting is 403 `INVITER_GONE` when the inviter is no longer a member, or no longer an admin for an `admin` invitation; removing a member cancels their pending invitations, and demoting an admin cancels their `admin` ones. The invite page shows its generic failure text.
- **Scoping.** Projects, chats, lists, campaigns (with their targets and sends) and API keys belong to the organization (`organization_id`, with `user_id` or `owner_id` as the creator). Another organization's id is 404. The database enforces this with row-level security, whatever the query names: a call reads and writes the rows of its token's organization only, and the back office (`require_admin`) reads every organization. Runs and jobs, saved searches, notifications and memory are per user, with the exceptions below. Credits and billing belong to the organization.
- **Removing a member** moves their open sessions to an organization they still belong to and disconnects the senders they connected there (`status_detail: 'owner_removed'`, token dropped, unlinked from every client, a LinkedIn account id cleared so it can be connected again). Before the removal the web calls `POST /v1/integrations/senders/members/{user_id}/release` with `{organization_id}` (`require_org_admin`; 403 `AUTH.ORG_ADMIN_ONLY` when the body names another organization than the token's, 404 `REQUEST.NOT_FOUND` for a user who is not a member; response `{released}`), from Better Auth's `beforeRemoveMember`: a failed release stops the removal. It revokes their senders of that organization at the provider (Google unless another live row of the same account in any organization still uses the grant, which Google's revoke would end; HubSpot; the Unipile account; Microsoft has no per-app revoke, so only its token goes), then disconnects them as `owner_removed`. Provider calls are best effort and the row is released anyway. Campaigns keep their owner. `DELETE /v1/integrations/mailboxes/{sender_id}` makes the same shared-grant check before revoking; deleting an account also revokes HubSpot (#471).
- **Request size.** Every route answers 413 `REQUEST.TOO_LARGE` to a body over 1 MB (`app/core/body_limit.py`) before auth or parsing. The CSV upload and its preview allow 5 MB.

### Deleting an account

An admin uses Better Auth's `admin/remove-user`. A user deletes themselves with `delete-user` from the profile's danger zone. Both first call the API, and an error aborts the delete:

- `POST /v1/admin/users/{id}/before-delete` (admin) and `POST /v1/me/before-delete` (the caller's own account; 403 `ACCOUNT.NOT_YOURS` for another `user_id`). Called alone, the second still acts: it cancels the sole member's plan and disconnects their senders.
- 409 `ACCOUNT.LAST_ADMIN` when the user is the last admin of an organization that has other members.
- Every organization the user alone belongs to stops billing: live Stripe subscriptions are cancelled at once and auto top-up is switched off. A Stripe failure is 502 `ACCOUNT.BILLING_CANCEL_FAILED` and nothing is deleted. A subscription already over at Stripe counts as cancelled.
- A trigger on `"user"` (`guard_account_delete`) holds both rules in the database (`ACCOUNT.LAST_ADMIN`, `ACCOUNT.STILL_BILLING`), because the `dash()` plugin's delete routes skip Better Auth's hooks. The web refuses any other Better Auth delete path (`ACCOUNT.DELETE_PATH`). The same plugin's `/dash/*` routes answer 404 whatever the token unless they are one of the dashboard's reads listed in `web/lib/dash-guard.ts` (#978): an Infra-signed JWT ranks above our admin role, and its write routes skip our rules (founder, sender release). A route a later Infra version adds is closed until listed; the reads still need that JWT.

What the organization owns outlives the member: their `user_id` or `owner_id` becomes `NULL` on projects, chats, jobs, lists, campaigns with targets and sends, the inbox, saved searches, webhooks, senders, cost records and the money tables. Their own rows cascade (sessions, accounts, memberships, API keys, memory, notifications). Their senders are revoked at the provider best effort, then disconnected (`status_detail: 'owner_deleted'`). A campaign whose creator is gone keeps sending from its client's other senders. Its reply address names the campaign, as every campaign's does (see Inbox and replies), and its unsubscribe links name the project instead. Addresses and links minted while the creator existed still work: an unsubscribe always leaves an exclusion (where the person is a target, else in the creator's former campaigns' clients, else in the clients of the organizations the creator belonged to), and a reply to such an address reaches only the campaigns the trigger recorded (`outreach_campaigns.former_owner_id`). A saved search with no creator is no longer scheduled. The back office shows the creator as `ex membro` or `former member`.

### Profile

Profile routes belong to Better Auth in the web, not to the Python API. `change-email` is two steps for a verified address: the current address gets a confirmation, and opening it mails a verification to the new address, which changes only when that link is opened. An unverified current address changes at once. `user.timeZone` holds an IANA name (at most 64 characters), validated and stored canonical on write and canonicalized again on read: offsets such as `+05:30`, abbreviations such as `EST` and unknown names are 400. The web formats dates in it (saved zone, else the `NEXT_TIME_ZONE` cookie, else UTC). The API does not read it.

### Profile photo

The photo belongs to the user, not an organization: the objects are `avatars/<user id>/<token>.webp` in the R2 photos bucket (`R2_*` settings; any empty, or no `API_PUBLIC_BASE_URL`, makes the feature inert), so no route reaches another user's photo and no table holds it.

- `PUT /v1/me/photo`: the body is the image itself (any content type; at most 5 MB, else 413 `REQUEST.TOO_LARGE`). The bytes are decoded and sniffed, not trusted: JPEG, PNG or WebP only (422 `PHOTO.BAD_TYPE`, also for an undecodable file), at most 25 million pixels, 40 million for a JPEG and 8 million for a WebP (it cannot be decoded at a reduced size) (422 `PHOTO.TOO_LARGE`). It is stored as a 256 px square WebP, under a new random token; the user's older objects are deleted, so their URLs answer 404 (an upload that started earlier never deletes a newer one). It answers `{url}`: `<API_PUBLIC_BASE_URL>/v1/avatars/{user_id}/{token}`. The web then saves that URL as Better Auth's `user.image`. 503 `PHOTO.UNAVAILABLE` when unconfigured or the bucket fails.
- `DELETE /v1/me/photo`: 204, removes all the caller's objects; the web clears `user.image`.
- `GET /v1/avatars/{user_id}/{token}`: public (an `<img>` sends no token); the random token, not the user id (visible to org members), is what makes the URL unguessable. `image/webp`, `Cache-Control: private, max-age=86400` (browser only, no shared cache) and `X-Content-Type-Options: nosniff`. 404 `PHOTO.NOT_FOUND` for a replaced or removed photo.
- An account delete (`before-delete`, either path) removes the objects, best effort. The daily beat task `sweep_profile_photos` (03:30 UTC, `SystemReason.PHOTO_SWEEP`, declared in `app/auth/photo_sweep.py`) is the retry: it deletes objects older than an hour whose user no longer exists, or that the user's `image` does not name (a failed save). A run that would delete over 20% of the objects, and more than 5, deletes nothing and logs an error.

## Projects (clients)

A project is a client: an agency's customer, or a direct customer's product line. `X-Project-Id` names the active one on every call (the web sends it from the `zb-project` cookie, also from server components). No header, a malformed id, or a project outside the active organization gives the organization's default project, the oldest, which is created on first use.

A project owns its business profile, exclusions, senders, campaigns (through their list) and inbox messages (through the campaign they answer). A chat turn reads its chat's project: the profile enters the system prompt as a data block, its exclusions filter rows, and its LinkedIn account runs `linkedin_search`.

- **Monthly credit cap** (`credit_cap` with `credit_cap_mode`, admin-only to change; both set, or both `null`). `credits_this_month` counts the project's holds this UTC calendar month: an open hold whole, a released one nothing, a settled one what it kept. `soft` only reports (`over_cap`). `hard` also limits every hold the project spends through (`reserve_project_credits` locks the project row): a chat turn holds at most what is left, a paid step past the cap fails `no_credits`, a scheduled run fails `project_cap_reached`, an AI column fill holds whole cells within it and fails `project_cap_reached` when none fits. Every hold goes through `app/billing/credits.py` (#660), with one rule for which refusal the user sees: the cap's when the project's room this month is less than the least the caller can use (one cell, the step's price, the run's hold), whatever the wallet holds; else the wallet's. Onboarding free runs are counted per organization, not per project.
- **Deleting** cascades to its chats, lists, campaigns, inbox, profile and exclusions, and unlinks its senders. 409 `PROJECT.LAST` for the last project. 409 `PROJECT.HAS_SENDERS` when it uses a live sender someone else connected and the caller is not an admin. 404 `PROJECT.NOT_FOUND` outside the organization.
- **Senders** are physical `user_oauth_connections` rows, one per provider account in the organization (unique on `(organization_id, provider, provider_account_id)`). The id is the provider-verified identity: Google `sub`, Microsoft `id`, the Unipile account id, never an address. A connect whose profile names no account is refused (`INTEGRATIONS.PROFILE_UNAVAILABLE`, 503). A project uses several Google and Microsoft mailboxes and at most one LinkedIn account (`project_senders`, #935). A sender may serve several projects, and a member may connect several accounts of one provider. Every send and inbox answer records its `sender_id`, and the daily and LinkedIn limits count by it.
- **Who may change a sender.** Any member sends from the project's senders. Only whoever connected a sender, or an admin, disconnects it (403 `INTEGRATIONS.DISCONNECT_FORBIDDEN`; it stops for every project it serves), replaces it, or links it (403 `INTEGRATIONS.LINK_FORBIDDEN`). Connecting or linking a mailbox adds it to the project's other mailboxes and never replaces one. Connecting or linking a LinkedIn account over a colleague's live LinkedIn account of the project is 403 `INTEGRATIONS.REPLACE_FORBIDDEN` and changes nothing. The same provider account is re-authorised in place and keeps its connector. For LinkedIn, `POST /v1/integrations/linkedin/connect` (both branches, so a hosted reconnect of a colleague's broken account too) and `/checkpoint` answer that 403 before any Unipile call, so a refusal leaves no orphaned Unipile account. `/checkpoint` answers only for an `account_id` that this user's own `/connect` returned as a checkpoint in the last 15 minutes (422 `INTEGRATIONS.INVALID_INPUT` otherwise, with no Unipile call). A Unipile account of a colleague is never re-authorised or linked by a member: 403 `INTEGRATIONS.REPLACE_FORBIDDEN`, whatever the route. A LinkedIn account is one row across organizations: one another row holds is 409 `INTEGRATIONS.ALREADY_CONNECTED_ELSEWHERE`. `PUT` and `DELETE /v1/integrations/senders/accounts/{sender_id}/projects/{project_id}` link and unlink an existing account (idempotent; 404 `INTEGRATIONS.LINK_NOT_FOUND` when not linked). Unlinking the last project leaves the account connected and linkable. The accounts list covers every provider, LinkedIn (`unipile`) included. A send claims its mailbox only while the mailbox is still linked to the campaign's project: an unlink that commits between the queue pick and the claim leaves the send `approved`, and an inbox answer whose sender was unlinked during its OAuth round trip is 409 `INBOX.NO_MAILBOX` (`INBOX.NO_LINKEDIN` on LinkedIn), nothing sent (#985).

## Chat and runs

`POST /v1/chat` stores the user message, creates a `jobs` row (one per chat turn, `kind='chat_turn'`), enqueues the Celery task `run_job` and streams the job's frames. `POST /v1/runs` takes the same body, returns 202 with the job id and does not stream; `GET /v1/runs/{id}` and `POST /v1/runs/{id}/cancel` alias the job routes. Both accept a JWT or a `sbk_` key.

- A new session without `project_id` goes to the active project. `goal` and `project_id` are read only when the request creates the session and never rewritten.
- `locale` (optional; one of the interface languages in `api/app/core/locale.py`, other values 422) is the language the user sees. The web sends its `<html lang>`, which follows the `NEXT_LOCALE` cookie. The turn writes its answer, plan, list and question text in it (`jobs.locale`) and never saves it on the user (#795). Without it the turn uses `"user".locale`. Notifications and emails always use `"user".locale`.
- A new session's `title` is the first non-empty line of its first message, with whitespace collapsed, cut at a word to at most 80 characters, with `…` when cut. A session that `segment` opens takes the segment's name instead (see below). A list that a search creates without a plan is named the same way after the turn's latest user message.
- A request sends either `message` (1 to 20,000 characters) or `segment`, never both (422). `segment` is the `key` of a `GET /v1/home/welcome` card: it names an onboarding segment stored on the project (`business_profiles.segments`). The chat opens like the onboarding first list, from texts the server writes: the first message is `first_list_message`, the title is the segment's name (the message's first line when the name is empty), and `chat_sessions.brief` is `first_list_brief`. The agent reads the brief in place of the first message on every turn. Both texts are in the segment's language or, for a segment without one, in `locale` (else `"user".locale`). 422 `CHAT.SEGMENT_GONE` when no stored segment has that key (the segments were proposed again since the page loaded) or it no longer parses. `segment` opens a new session: with a `session_id` the request is 422.
- `goal: 'campaign'` stores `chat_sessions.goal` and adds a fixed paragraph to every turn's system prompt: a person list with email, a last optional `draft_campaign` plan stage, then one `draft_campaign` call. Nothing is sent. If the chat's last approved plan dropped the `draft_campaign` stage, later turns replace the paragraph with a line that the user refused the draft, withhold the tool from the model and refuse a call to it, until a newer approved plan keeps it.
- **409 `CHAT.JOB_RUNNING`** when the user already has a `queued` or `running` job (one per user), or the chat has one from any member (one per chat, #473). The 409 comes before a `plan_approval` is applied, so the plan and its required columns do not change. A job idle for more than `STALE_JOB_MINUTES` (20), in any of the user's organizations, blocks neither: the new turn ends it `failed` with error `stale`. Nothing else ends it, so a turn that waits longer in the queue still runs when a worker takes it. Other failures: 404 for a session that is not the caller's, 503 `CHAT.QUEUE_UNAVAILABLE` when the queue is down. On a 503 the job ends `failed`. A session that the request opened (no `session_id`, also `POST /v1/runs` and `POST /v1/onboarding/complete`) is deleted with its message, so a retry opens one chat. The message of a turn on an existing session stays.
- `pick` is an index into the options of the last assistant message's `question` (the no-results funnel). 422 `CHAT.PICK_INVALID` when that message has none. `retry_stage` and `plan_approval` are described under Plans. `retry_stage` needs a `session_id` and cannot come with `plan_approval` (422).
- `ask_user` ends a turn `needs_input`. The user's answer is the next message to the same session, which starts a new turn and marks the session's `needs_input` jobs `succeeded`.
- `GET /v1/chat/sessions` takes an optional `project_id`. Each row carries the sidebar dot and meta line from the session's latest job. `status` is `null` with no job; `running` for `queued` or `running` updated within `STALE_JOB_MINUTES`; `error` for `failed` or a stale `queued` or `running`; `plan` for `needs_input` whose message has `question.plan`; `asking` for any other `needs_input`; for `succeeded` or `cancelled`, `error` when a `jobs.stages` entry has an `error` or the job's message has a tool call with `verdict: 'failed'` other than `ask_user` and `set_brief` (the chat header's step error), else `done`. `list_count`, `people` and `companies` count the session's lists that are not deleted and their non-excluded rows. At most 200 sessions, pinned first.
- `GET /v1/chat/sessions/{id}` returns `active_job`, the session's latest job whatever its status, so a reload shows a finished run's plan card or a failed step. `fill_credits` (#239) is the net credits charged by the settled AI column fills of the session's lists (the `ai_column` deductions with `reference_id` `<list_id>:<key>`, minus refunded slack). The header shows the turns' `credits_used` plus `fill_credits`. Messages saved before #211 have `question.options` as strings, the question appended to `content`, and no `summary`, `brief` or `memory_saved`: the web reads both forms. `messages[].tool_calls[]` is `ToolCallRecord` (`app/agent/tool_calls.py`), which reads every shape the loop ever stored and never fails the load: a field that does not parse becomes its default (logged once), and an entry with no `name` is left out. The saved `vendors` of a tool call (back office) never leave this route.
- `DELETE /v1/chat/sessions/{id}` is 409 `CHAT.JOB_RUNNING` while the session has a `queued` or `running` job (#434), so a turn never writes into a gone chat.

### Jobs

`phase` is the running tool's name, `scoring` during the fit-score pass, `null` when done. Without a plan, `progress.done` counts executed tools and `progress.total` is 0 (unknown). With an approved plan, `stages` carries `{tool, label, units, done, per_row, started_at?, finished_at?}` (`per_row`: `units` count rows, else calls, i.e. searches) and `progress.total` is the sum of `units`. `started_at` runs from the stage's first call to its last result, and a retry restarts from it. Statuses: `needs_input` is terminal for streams and pollers; `cancelled` means stopped by the user.

Jobs are shared like their chats (#323). `GET /v1/jobs/{id}` answers for any job of a chat in the caller's active organization. Another organization's job is 404 `JOB.NOT_FOUND`. A job whose chat was deleted stays visible to whoever started it only, in the job's organization. Stopping one is for whoever started it or an admin (403 `JOB.NOT_OWNER`).

`POST /v1/jobs/{id}/cancel` answers `{status: cancelling}` for a `queued` or `running` job. For a finished job it changes nothing and returns that job's status. The request is one entry in the Redis stream `job:{id}:cancel` (TTL 1 h) that the worker reads with a blocking XREAD. 503 `JOB.CANCEL_UNAVAILABLE` when Redis does not accept it. The worker stops at the first safe point: the model is interrupted mid-answer (written text stays), a running tool finishes and is charged if it found anything, no later tool or step starts, and the request is checked again before anything that still spends (funnel, plan and research fill, fit score). It then closes like any turn: credits settled and the rest of the hold released, `error {code: 'cancelled'}`, the assistant message saved `partial` with `terminal_code: 'cancelled'`, final `stages`, `done`. A job still `queued` stops as soon as a worker takes it. If the worker cannot reach Redis, the job runs to its end.

## Server-sent events

Transport is `text/event-stream`. A frame is `event: <name>\nid: <n>\ndata: <json>\n\n` with snake_case JSON (the web's store applies `toCamelCase`). `: ping` follows every 15 s of silence. The job runs in the worker and writes each frame to the Redis stream `job:{id}:events` (TTL 1 h) with entry id `<n>-0`, so the SSE `id:` is the integer `n`. The HTTP endpoint tails that stream, so closing the connection does not stop the job.

Streams: `POST /v1/chat`, `GET /v1/chat/sessions/{id}/stream`, `GET /v1/lists/{id}/stream`, `GET /v1/lists/imports/{id}/stream`, `GET /v1/home/stream`, `GET /v1/home/nav/stream`, `GET /v1/notifications/stream` and `POST /v1/onboarding/profile`. `test_streams_are_event_streams` pins five of them as `text/event-stream` in the schema.

`GET /v1/chat/sessions/{id}/stream` re-attaches. With `Last-Event-ID: <n>` it resumes at the frame after `n`. It is 404 when the session has no active job.

Every stream re-checks its caller every 30 s (`MEMBER_RECHECK_SECONDS` in `app/core/event_stream.py`), counted from when it opened, whether or not frames flow. A caller removed from the organization or banned gets one `error {code: 'AUTH.NOT_A_MEMBER', message}` without an `id:`, and the stream ends. A database read the stream makes for its own frames ends it the same way at once. The chat streams (the POST and the re-attach) send a `done` without an `id:` after that `error`. A database failure in that re-check is not a removal: the stream is cut with no frame, as by a network cut. The chat, the list fill, the CSV import, the bell, the sidebar and Home then reconnect; the onboarding study, a POST, does not. The web stops following a stream after any `error` frame and does not reconnect, except for `AUTH.NOT_A_MEMBER` on the three streams that hold none of the user's work: the bell, the sidebar (`/v1/home/nav/stream`) and Home (`/v1/home/stream`). A removed member's session has already moved to an organization they still belong to (`afterRemoveMember` in `web/lib/team.ts`), so these three refresh the page's server data and reconnect once, with a fresh token, into that organization (`rejoin` in `web/lib/api/event-stream.ts`). The bell first loads `GET /v1/notifications` again, which lists only the organizations the user still belongs to, and reconnects from its `cursor` (`reload`). When that reconnect, or the bell's reload, answers 401 (no organization left, or a ban), the stream stops and the refreshed page handles the signed-out user. The chat, the list fill, the CSV import and the onboarding study keep their visible error. `EventStream` holds this check for every stream, and `test_every_stream_is_an_event_stream` keeps every SSE route on it.

The turn stops too (#701). The worker runs it as the member who started it, so a member removed or banned while it runs ends it at its next database access, before another model or tool call, and the other searches of the same step stop too. The turn sends `error {code: 'AUTH.NOT_A_MEMBER'}` with an `id:`, then `message_saved` with `status: 'failed'` and `done`. The job ends `failed`. The credit hold settles for what the turn spent, and the cost of a vendor or model call already made is still recorded. No notification follows. A turn whose member left while it was still queued ends `failed` and sends nothing.

### Chat events, in the order they can arrive

| event | `id:` | meaning of the payload |
|---|---|---|
| `session` | no | `{session_id, job_id}`. Always first, also on re-attach. |
| `text` | yes | `{content}`, a text delta. |
| `text_dropped` | yes | `{}` (#567). The step whose text just streamed also calls a tool, so that text is not the answer. Sent before the step's first `tool_start`. The web removes the step's text and the saved message leaves it out. |
| `agent_thinking` | yes | `{turn_seq}` between one model step and the next. Not sent before the first step. |
| `tool_start` | yes | `{tool_id, tool_name, tool_input}` |
| `tool_result` | yes | `{tool_id, tool_name, result_preview, status: success\|failed, summary?, brief?, memory_saved?, campaign?, error_code?}` (`error_code` is the failed tool's own code when it has one: `disabled`, `no_credits`, `over_budget`, `crashed`, `skipped`, `not_connected`. The web treats a call with none, or `crashed`, as retryable, so a turn of only such failed searches reads «search failed, retry shortly»). See below. |
| `credits` | yes | `{tool_id, tool_name, cost, remaining}`, only when `cost > 0`. `remaining` is the balance as it will be after the settle. At the end of a turn, when per-row credits are refunded (#45), one frame for each call that charged them: `{tool_id, tool_name, cost: -n, remaining, refund: true, summary?}`. `summary` is the call's whole summary after the refund, with `refunded` set to the rows the call gives back (#659); the web replaces its copy and merges nothing. A call with no summary sends none. |
| `list_updated` | yes | `{list_id, entity, rows_added, rows_updated, row_count}` after a tool writes rows. `{list_id, entity, rows_scored}` after the fit score. `{list_id, entity, rows_updated}` after the settle, for each list where the turn left a pending per-row charge on a row. `{list_id, entity: null, rows_updated}` when `enrich_email` or `enrich_phone` claims rows before its vendor calls (`rows_updated` counts the claimed rows; the web finds the list by `list_id`). The web reloads the list's rows. |
| `stages` | yes | A snapshot of the whole plan run, only in turns that run a plan. See Plans. |
| `error` | yes | `{message, code}`. `code: 'max_turns_reached'` and `'cancelled'` are terminal (`TERMINAL_CODES`) and the turn ends `partial` (lowercase for history: the web compares them as they are). `CHAT.TURN_FAILED`: the turn failed (job `failed`). `CHAT.SAVE_FAILED`: the answer was not saved (the job stays `running` until the next send marks it `failed`). `AUTH.NOT_A_MEMBER` is described above: without an `id:` from the stream's check, with one from the turn (job `failed`). |
| `message_saved` | yes | `{message_id, status: success\|partial\|failed, question?}`. `question` appears only when the turn stopped on `ask_user` or the no-results funnel. `{question: '', options: [], plan}` when it stopped on a plan to approve. |
| `done` | yes | `{sources: [{url, title, domain, kind: web\|scrape, snippet, tool_id}], list_id, job_id}`. Always last. |

`tool_result.result_preview` is JSON cut at 2000 characters. `summary` says what the tool found, one object by `kind` (`ToolSummary`, `app/agent/summary.py`; `/openapi.json` carries the union). `{kind: count, noun: company|person, count}` is for searches and `save_to_list`: rows added plus rows updated in the list (not the rows returned before dedupe and exclusions), 0 when nothing is found. A contact call (`enrich_email`, `enrich_phone`) sends its `ToolResult.outcome` (`app/lists/lookup_outcome.py`), counted once per searched row by the row rule, from the cells the call wrote: `{kind: all_found|partial|none_found|all_failed, contact: email|phone, searched, tally: {found, invalid, not_found, failed, no_source, no_input}, unmatched, refunded}`. `found` is what the call bills, `invalid` a found email with verdict `invalid` (shown, not billed), `failed` a row whose source failed (a retry can help), `no_source` a row that no source that is on could be asked about (a retry finds the same sources), and `no_input` a phone row without the data to search. `kind` is the one classification: `all_found`, else `partial` when `found > 0`, else `all_failed` when `failed + no_source` is every row, else `none_found`. `unmatched` counts requested ids that loaded no row; `refunded` counts the rows the turn took back and is set after the result. The other kinds carry no tally: `{kind: nothing_to_search, contact, unmatched}` (#562: nobody left to search, `ok: true`), `{kind: no_row_match, contact}` (#550: the ids match no row; the result is `ok: false` and still has this summary) and `{kind: legacy, contact, found, failed, refunded}` (a stored call whose tally the stored counts do not determine: `found` is certain, `failed`, the rows to retry, is 0 when it was not stored, and `refunded` is the count that #666 stored, 0 when none; the refund settle leaves a `legacy` as it is). The chip and the back office read the state from `kind` (done, none, retry, error) and never from the counts. A call that fails otherwise, or whose tool has no noun, has no summary. `summary`, `brief` (`set_brief`), `memory_saved` (`remember`: the text saved) and `campaign` (`draft_campaign`) are whole typed copies of what the card shows, also stored in `tool_calls[]` (which adds `id, name, input, result, credits_used, verdict: success|failed`). A `summary` stored before the union is read at the boundary and never rewritten: `{count, noun: company|person}` is a `count`, `{count, noun: email|phone, searched, failed[, refunded]}` is a counted `kind` only when those counts determine the tally (`count == searched` with `failed == 0` is `all_found`, or `none_found` when `searched` is 0, and `failed == searched > 0` is `all_failed`; before #713 the people with no source were left out of `failed` and a phone `searched` counted rows that could not be searched, so the remainder is never read as «not found»), else `legacy` with `found`, `failed` and `refunded` (a stored `refunded` is kept on every old row, `legacy` or counted); `{count, noun: email|phone}` is `legacy`. The chip shows a `legacy` call as «N email» beside «M da riprovare» when `failed > 0`, and «credito reso per N righe» last when `refunded > 0`, as for a counted call. `result_preview` is cut, so the typed copies are what the web reads.

Text of 200 characters or fewer is held before it streams. The loop drops it with no frame when its step calls any tool except `ask_user` and `propose_plan`, and sends it when its step ends. A longer text streams at once and `text_dropped` takes it back. When no later text comes (an empty last step, a stop, the step limit, the deadline or a failure), or before a step that calls `ask_user` or `propose_plan`, the text taken back is the answer: the loop sends it again as `text` before any `error` or `tool_start`, and saves it. A short text dropped in the hold never comes back. The funnel question after an empty search does not bring it back.

The payload of each chat event is a model in `api/app/agent/event_payloads.py`, which `/openapi.json` carries as `ChatEventPayloads` under `POST /v1/chat`. A new event is a field there and a name in `SSE_EVENT_TYPES` in `web/lib/chat/types.ts`, or the store drops it with a warning. The list there matches the table. The store tolerates these the earlier implementation events, which Zenbree never sends: `variant*`, `assistant_writing`, `agent_recovering`, `agent_regrounding`, `tool_heartbeat`, `outcome`, `data_contract`, `plan_step`, `progress`, `credits_refunded`, `shutdown`.

## Agent tools

Each tool is a module in `app/agent/tools/handlers/<name>.py` that calls `register(ToolDef(...))` at import time. `handlers/__init__.py` imports them all. A handler is `async (args: dict, ctx: ToolContext) -> ToolResult` and never raises on a vendor error.

- **Rows.** `rows` are flat dicts with these canonical keys (extra fields are allowed). Company: `name, domain, website, linkedin_url, industry, employees, city, country, description, source`. Person: `first_name, last_name, full_name, title, company_name, company_domain, linkedin_url, email, email_status, city, country, source`.
- **Row updates.** `row_updates` are `{row_id, cells, if_empty?}`. With `if_empty: <key>` the update applies only to a row whose cell `<key>` is still empty, checked in the same SQL statement (`apply_row_updates`).
- **Credits.** The loop reserves first. The store then bills each found row it lands (pay-if-found). See Credits for holds and charging.
- **Vendor costs.** Every paid vendor call goes through `app.billing.paid_call`, which writes `vendor_calls` and needs a tariff per operation on the vendor's registration in `app.billing.vendors`.
- **Kill switches.** Before a paid call the loop reads the `settings` row `vendor_disabled:<provider>` on every call, uncached, through `app.admin.settings.vendor_disabled_now`: any value but `null`, `false`, `0`, `''`, `'false'` and `'0'` blocks, and a missing table lets the call through. `channel_disabled:<channel>` and the switches of sends and the CRM go through `is_disabled`: exactly `true` blocks, results are cached 30 s per process, and a database error fails open. `vendor_disabled:exa` sends web search to Firecrawl and `vendor_disabled:millionverifier` makes email verification MX-only.
- **Registered tools:** `web_search`, `fetch_page`, `search_companies`, `search_people`, `search_jobs_signals`, `linkedin_search`, `save_to_list`, `more_rows`, `list_row_feedback`, the scheduler tools (`schedule_check`, `list_schedules`, `cancel_schedule`), `enrich_email`, `enrich_phone`, `find_rows`, `set_brief`, `draft_campaign`, `ask_user`, `propose_plan`, `remember`, `forget`.

**`fetch_page`** reads only a host, or a subdomain of a host, that a message of the turn's own user (a teammate's message in a shared chat names none, nor does a `web_search` result of a turn a teammate started, nor a list cell a teammate hand-edited or one with no recorded editor, #963), a `web_search` result or a list row's `domain`, `website` or `company_domain` of the session named (#407). A cell that `save_to_list` wrote with `cell_meta` provider `web` does not name one, even after the row merged into a vendor row. Otherwise it returns `ok: false`. A host that only a `web_search` result named yields only its exact pages (#437): the result URLs and the same-host links on pages `fetch_page` read from it in the turn, matched without scheme, `www.`, fragment or one trailing slash, but with the port, and fetched as the result or link spelled it. A URL with userinfo never names a host. A public suffix such as `co.uk` or `pages.dev` names none of the hosts under it. A redirect is followed only to a page `fetch_page` could read or on the same host, else `ok: false` with the target in `error`.

**`web_search`** has no price but calls a paid vendor, so it follows the free searches' balance rule (`no_credits` at zero balance) and an organization gets at most 300 calls a UTC day, counted in Redis when the call is admitted (`over_budget` after that; fail-open on a Redis outage, #964).

**Lasting tools** (`remember`, `forget`, `schedule_check`, `cancel_schedule`) are refused (the model is told to ask the user to confirm) in a turn that read a non-first-party tool result (#409), and in every turn of a chat that holds a message of another member or of a turn another member started (#963); in that case the refusal tells the model to send the user to a chat of their own or to the Memory and saved-searches pages, since confirming in the same chat cannot work. The business profile is framed as data and does not count. A hand-edited cell (`PATCH /v1/lists/{id}/rows/{row}`) has `cell_meta` `{status: 'manual', by: <user id>}`, as is a CSV import's (the importer). A manual cell stored before `by` existed has none and fails closed: it names no host until the owner edits it again (acceptable before go-live).

**`remember {content}`** returns `{entries, chars, saved}` and **`forget {text}`** returns `{entries, chars, removed}`, both free (no `Price`). Both are refused when the memory document is locked or full, or when `text` matches none or several entries.

**`enrich_email`** and **`enrich_phone`** (max 25 `row_ids`, 8 credits per phone found, pay-if-found) run a waterfall of contact sources. Email uses Apollo, AI Ark and Treg (PDL and Hunter). Phone uses Apollo (an asynchronous phone job), then Treg. A row that already has the value is skipped. `data.found` is the number found. The handler returns no charge: the store bills each found row that lands (see Charging). The kill switch is per source (`vendor_disabled:apollo|aiark|treg|pdl|hunter`; `treg` stands for PDL and Hunter). The tools have no provider argument. A source with no key counts as off. With every source off they return `ok: false`, "temporarily disabled". Every lookup writes `contact_lookups(provider, channel, found)`.

- **Verdicts.** `enrich_email` writes the verifier's `email_status` (`verified|catch_all|mx_ok|unknown|invalid`) with the address, and `not_found` when the sources answered with none (final). When a source failed (`unreachable_sources`) it writes `email: null, email_status: 'failed'`, so `next_unenriched` takes the row again after every row never tried (#506, #659). The same for a person no source that is on and keyed can search (#520: a source with no key counts as switched off, and AI Ark reveals only its own ids): `email_status: 'failed'`, and the person is not in `failed`. `enrich_phone` writes `phone_status: revealed|not_found` the same way, and `phone_status: 'failed'` when a source failed (an Apollo phone job that did not finish: `CONTACTS.PHONE_JOB_UNANSWERED`) or when Apollo, the main phone source, is off or unkeyed (#504, #659). A `not_found` written before #504 could be a failure, and migration `20261009093638_phone_status_retry.sql` removed it from rows with no phone. A `not_found` email written before #506 could be a failure too, and migration `20261013091036_email_not_found_retry.sql` turned it into `failed` on the rows a lookup wrote (email null); a `not_found` from a CSV stays final (#519). A row with no Apollo id, LinkedIn URL, email, or name with a company is not searchable: no call and no `phone_status`. `app/lists/lookups.py` holds the values each status takes and how a reader turns them into a state; migration `20261012152552_lookup_status.sql` converted the values stored before it. An AI Ark id is not sent to Apollo. When `enrich_email` finds the email of a `not_found` row, it resets `phone_status` to null. A phone result carries `if_empty: 'phone'` (#507), so it never erases a number a click paid for meanwhile. Names come from `full_name` when `first_name` and `last_name` are missing (`app/people/person_name.py`, #509).
- **`data`** of both: `{searched, found, failed: [{row_id, name}]}`. `failed` names the people left without a verdict, so the chat says "retry" and not "no contact". It leaves out a person no source could be asked about: that is the model's text, so the tool description tells it apart; the summary's `tally.no_source` counts that person. `enrich_email` adds `statuses` (without the rows in `failed`) and `revealed: [{row_id, name}]` (#560), the first and last name a source returned for each person found, absent when none. The model names a person whose surname was masked by this name, never by the surname the user guessed.
- **Outcome.** Both tools set `ToolResult.outcome`, a `ContactOutcome` (`searched` with a `tally {found, invalid, not_found, failed, no_source, no_input}` counted once per row from the cells the call wrote, `nothing_to_search`, `no_row_match`). `ToolResult` refuses, at construction, a result that writes `email_status` or `phone_status` or bills `email` or `phone` without one. `invalid` (an address the verifier rejected) is counted and not billed; `no_input` is a phone row with nothing to search by.
- **No row matches** (#550). When the ids match no row of the list (wrong id such as the list id, another list's row, an excluded row, `people` with no `row_id`), the tools search nobody and return `ok: false` with nothing billed, `error_code: 'skipped'`, with an error that says not to retry excluded ids. The chat shows the tool failed, never "0 email". The plan step stays open for the correct call. An id is any uuid spelling Postgres accepts. An empty list (`row_ids: []`, `people: []`) names nobody: `enrich_email` takes the next batch as it does without ids, and `enrich_phone`, which has no next batch, answers as above. When only some ids match, the tools search those and `data.unmatched_row_ids` lists the rest (the key is absent when all match).
- **Nothing left** (#562). When nobody is left to search, the tools search nobody and return `ok: true` with nothing billed, `data: {searched: 0, failed: [], nothing_left, unmatched_row_ids?}`. Nobody is left when the given rows already have the email or phone, or, without ids, when the next `enrich_email` batch is empty (every row has an email or a verdict, is excluded, or was refunded). `nothing_left` is text for the model: no row remains, do not call again, tell the user. With a `nothing_to_search` outcome, `tool_result` carries `summary: {kind: nothing_to_search, contact, unmatched}`, and the chip shows the neutral state with «Nessuno da cercare» (plus the unmatched ids), and the plan step stays "Finita". `searched: 0` leaves the plan step as it was. Without a list, `enrich_email` answers "there is no list yet", also without ids.
- **Without ids**, `enrich_email` takes the next 50 person rows with no `email`, not refunded and not matched by the user's exclusions: first the rows never tried (no `email_status`), then those whose search failed (`OPEN_EMAIL_SQL`). The credit preflight assumes the full batch (`Price.batch`).

**`find_rows {names: string[] (1..50)}`** (#560, free) returns the rows of the current list (`ctx.list_id`, the one `enrich_email` and `enrich_phone` read) that carry a person's name, so "find the email of <name>" reaches those rows. A `names` value that is not a list names nobody. The result is `{matches: [{name, matches, rows, not_counted}], no_list?: true}`, one element per name in the order given.

- `matches` counts the rows whose name (first and last name from `app/people/person_name.py`, titles removed) contains every word of the given name, ignoring case, accents and order. Rows with exactly those words win over longer names that contain them ("Maria Rossi" is not also "Maria Pia Rossi").
- `rows` shows up to 5 as `{row_id, name, title?, company_name?, has_email, has_phone}` in list order. It never shows the email or phone, because the result goes to the LLM provider.
- `not_counted` (up to 5) lists rows the user sees that may be this person but never count in `matches`. `reason: 'masked'` (with `row_id`) means Apollo masks the surname until the email reveals it (`masked_parts`, "Ma···i") and the given name is the row's first name plus what the surname could be ("Paolo Marchi", "Paolo M.", "Paolo Ma"). Other words are read joined in order, so "De Luca" matches "De····a". The model asks the user whether it is her and uses that `row_id` only after a yes. `reason: 'excluded'` (no `row_id`) means a row excluded by hand or by an Exclusions rule, which is never enriched and never makes a name ambiguous.
- The model uses a `row_id` from `rows` only when `matches` is 1, asks which when it is above 1, and says the person is not in the list only when `matches` is 0 and `not_counted` is empty (#140). Without a list the result is `ok: true`, `no_list: true`, every name with `matches: 0`.

**`set_brief`** (#211, free, does not end the step) takes `{who?, companies?, where?, signal?: string[] (6 at most, 60 characters each), email?: required|if_found|not_needed}` and returns the same fields normalised (`email: null` means undecided). It records what the agent understood, for the "Cosa ho capito" rail. The chat's last call replaces earlier ones. There is no table and no SSE event: the normalised brief travels in the typed `brief` field of `tool_result` and `tool_calls[]`. Duplicates and non-string entries are dropped. An empty brief does nothing: `ok: true`, no `brief`, the previous one stays.

**`draft_campaign`** (#209, free) takes `{name?: string 1..200, campaign_id?: string, steps?: [{channel, subject?, body, send_after_days, threaded?}] (12 at most)}` and returns `{campaign_id, name, enrolled, target_count, fields, steps_written?}`. `fields` lists the draft's own field tokens (`{{recentNews}}`), empty for a new draft.

- `name` is required unless `campaign_id` is given. `campaign_id` picks the exact draft (default: the most recent for the list) and must be a draft (`status = 'draft'`) of the person list of this chat, else `ok: false` and nothing changes.
- It has no list argument: it uses the most recent person list of this chat (same `chat_session_id`, same organization). `ok: false` with a readable error when the chat has no person list, the list has no rows or nobody is reachable.
- `steps` (#346) is the whole sequence the agent wrote in the conversation's language. It replaces the draft's steps (without `steps` the text stays), is numbered 1..n, and goes through `app.outreach.step_copy.checked_steps`, the checks of `PATCH /v1/campaigns/{id}` plus: unknown `{{…}}` tokens, leftover `[Name]` placeholders and a LinkedIn invitation note over 300 characters are refused. Allowed tokens are those of `sending.CONTACT_TOKENS`: `{{firstName}}`, `{{lastName}}`, `{{companyName}}`, `{{role}}`, `{{email}}`, and also `{{first_name}}`, `{{last_name}}`, `{{company_name}}`, `{{company}}`, `{{title}}`, plus the tokens of the draft's own `fields` (#933). A refusal names those tokens. Never a signature or an unsubscribe footer: the system adds them when it sends. A validation error gives `ok: false` with the reason and writes nothing. A step may carry `b: {subject, body}`, its copy B (#934), with the checks of copy B on `PATCH`. A refusal in copy B names `variant b`. A `steps` rewrite with no `b` on any step, of a draft that has copy B, gives `ok: false` and writes nothing, because the rewrite would delete the test. This also applies to the draft that a call without `campaign_id` continues. A rewrite that passes `b` on some steps replaces copy B as it replaces copy A.
- It is idempotent: it reuses the most recent draft with that `outreach_campaigns.list_id` and enrolls only people not yet targets (the rules of `POST /v1/campaigns`), so two calls give one draft and no double target. The shared code is `app/outreach/drafts.py`.
- The typed `campaign = {id, name, target_count}` travels on `tool_result` and `tool_calls[]`. A `draft_campaign` stage the user dropped from the plan blocks the tool even though it is free.

**`ask_user {question, options?: {label, description?}[] (6 at most)}`** (#40, free). Each option has a one-line `description` of what it commits to (300 characters at most). The server normalises to `{label, description: string|null}` and drops non-string or repeated labels. The loop runs the step's tools and then stops. The question is not in `content` or a `text` frame. It is only in `message_saved.question` and `chat_messages.question`, and the loop appends it to the assistant message when it rebuilds the model's history. The job ends `needs_input`.

**`more_rows {list_id}`** (`list_id` is required and never defaulted, because a chat can hold a company list and a person list; only lists of this chat). Every `search_companies` and `search_people` call that stores rows records `lists.last_search` (not the `name` and Google Maps modes, which have no pages), keeping the furthest page of the same filters. `more_rows` re-runs that search at the next page, so a fetched page is never bought twice. It drops rows whose `dedupe_key` is already in the list. The search tools and `more_rows` have no `Price`: rows are free (2026-10-07), and the credit pays for contacts found. The result adds `page` and `already_in_list`, or `exhausted: true` for an empty page, which is free and does not move the cursor. It sets `last_search.exhausted`, and later calls are refused before the vendor until a search with other filters or a further page replaces it. The kill switch is the re-run search's.

**`list_row_feedback`** (free) returns this chat's rated rows as `{good: [...], bad: [...], how_to_read}` (200 rows at most). The note reaches the model only here, as data: the turn's `<chat_state>` only counts rated rows per list.

### No-results funnel

When a search found nothing, the server builds the question itself (#214, #260, free). The model supplies nothing.

- **When.** A company search in the B2B database (`search_companies`, Apollo discovery, page 1) returns 0 rows after at least one filter applied, and reports `data.applied_filters`. An Apollo people search (`search_people`, page 1, not `source: 'aiark'`) does the same when every filter it got is one the funnel knows. Any other filter (company domains, names or ids, technologies, email status, job dates) means no funnel, because an alternative would drop it silently. AI Ark searches have none. The loop builds the funnel from the turn's first such search, once per turn (#259: a failed build is not retried that turn), when no tool of the turn found rows. A company search with a `local_fallback` waits for the Google Maps search to come back empty too. A turn that never runs it gets no funnel. A Maps search that finds nothing only explains the company search it stood in for. The funnel ends the turn `needs_input`.
- **Groups**, broad to narrow. Companies: `where` (locations), `what` (industries, keywords), `size` (employee ranges), `money` (funding, revenue), `signal` (job titles, minimum active jobs). People: `where` (locations, company locations), `what` (industries, keywords, keyword tags), `size`, `money` (revenue), `signal`, then `who` (titles, seniorities, functions).
- **Counting.** Each step adds one group to the previous ones and counts it with one Apollo page (`total_entries`), stopping at the first 0. The last group is the empty search itself and costs no page. Alternatives drop one group each (the excluding group first, then the narrowest), at most 3, each counted with one page. One that finds 0 or leaves no filter is dropped. A company funnel costs at most 4 + 3 pages through `paid_call('apollo.discover_organizations')` and the Apollo kill switch, one Apollo credit per page including an empty one (#259), never user credits (`search_companies` has no `Price`). A people funnel counts with free `apollo.search_people` pages (`per_page` 1).
- **Result.** `chat_messages.question` has options with `estimate: {count, noun}`, `filters`, `drop` (the dropped group) and `tool`, plus `funnel: {steps, excluded_index, entity}`. Funnels saved before #260 lack `entity` and `tool` and mean company. `question`, `label` and `description` are English fallbacks: the web words the card itself from `group` and `drop`. `filters` stays on the server side; the web ignores it. The web shows "non ti ho addebitato nulla" when `credits_used` is 0.
- **Picking** an alternative is `POST /v1/chat {message, session_id, pick: <option index>}`. The server reads `filters` from the last assistant message's question and stores `{tool, args: filters}` in `jobs.pick` (a bare filters object saved before #260 means `search_companies`). That turn runs that search with exactly those filters before it calls the model.

### Local fallback

Apollo comes first for companies (#52). When an Apollo discovery search with `locations` returns fewer than 10 rows on page 1 and Serper is not disabled, `search_companies` adds `data.local_fallback`, a hint for the model that names the first location. The agent then runs or offers the Google Maps search (`local_query` and `local_location`), whose rows carry `source: google_maps`.

## Plans

- **Mode** (#42). `lists.mode` is `build` (find new rows) or `enrich` (work on rows the user has, such as an upload). The model classifies the brief in `propose_plan`. A list made by an upload is `enrich`.
- **`propose_plan`** (free, called alone in its step like `ask_user`) takes `{mode, entity, target_rows (1-2000), list_name?, list_id?, columns, stages}`. A column is `{key, label?, description?, required?}` or `{label, research, required?}` (`description`, 120 characters at most, is the line under a plain column). A stage is `{tool, label?, units, per_row?, optional?}`. `optional: true` marks a stage the list is still useful without, such as phone lookups next to emails, and the user can drop it on the card. The result's stages add `unit_cost` (the tool's `Price.credits`, 0 for a tool with no `Price`), so a stage costs `unit_cost * units`. The plan goes on the session's list for `entity` (created if missing), or on `list_id` (owned by the user, same entity, required for `enrich`), as a new version in `list_plans(list_id, version, plan, approved_*)`, and the list's `mode` follows the plan.
- **Pricing.** `credits_fixed` is the sum of `unit_cost * units` of the fixed stages. `credits_per_row` is the sum of `unit_cost * units / target_rows` of the `per_row` stages. A stage's `unit_cost` is its tool's `Price.credits`, 0 for a tool with no `Price`. `estimated_credits(N) = credits_fixed + ceil(credits_per_row * N)`. `large_run_credits` is the threshold above which the web warns (100).
- **Approval** (#43 #44 #47 #408). A plan is approved at once for its own turn only when it is the turn's first plan (no `list_plans` row has `approved_job_id` equal to this job) and what the turn recorded (its `row_charges` records that are not `refunded`, its research fills included) plus `estimated_credits` is at most 100 (owner decision). A research fill bills after its plan, so each further plan in the same turn needs the card, including a plan in a turn that runs a card-approved plan or retries a stage. Otherwise the result has `needs_approval` and the turn pauses `needs_input` like `ask_user`, with `chat_messages.question = {question: '', options: [], plan}`.
- **Approving** is the next message: `POST /v1/chat` (or `/v1/runs`) with `plan_approval: {list_id, version, rows (1-2000), dropped_stages?: [stage index]}`. Only the latest version of a list the user owns, in the same chat session, can be approved: 404 `PLAN.NOT_FOUND`, 409 `PLAN.STALE`, and nothing is created. `dropped_stages` are indexes into `stages`. Only `optional` ones can be dropped: 422 `PLAN.STAGE_REQUIRED`, or 422 `PLAN.STAGE_UNKNOWN` for an index the plan lacks. The server reprices without them and the client never sends a price. The approved version stores each stage with `dropped`, and `credits_fixed`, `credits_per_row` and `estimated_credits` without the dropped ones. Repricing uses each stage's stored `unit_cost`, never the tool registry (the API process does not load it), and does not round `credits_per_row`, so the web prices the same credits. A plan stored before `unit_cost` existed has no droppable stage. A repeated approval of one version starts from the plan again, not from the first approval's flags. The approval writes the approved copy back into the plan message (`question.plan`, with `approved_rows`), so a reloaded card shows what was approved, and records `approved_rows`, `approved_credits = estimated_credits(rows)` and `approved_job_id`.
- **The card** compares the plan's own `estimated_credits(rows)` with the balance for the shortfall and for locking Approve, never `large_run_credits`. It shows the spend cap `estimated_credits(rows)` as "fino a N" (#259: the loop never lets a plan spend more) and the balance left after it. The run skips dropped stages (no `jobs.stages` entry). A tool whose every stage was dropped is not sent to the model, a call to it still fails with an error (also through `more_rows`, which counts as the search behind its list), and the turn's `<chat_state>` names them.
- **Spend gate.** A paid tool runs only if `spent + Price.credits * estimated units <= budget`, else it fails with nothing charged. `budget` is 100 credits without a plan; `approved_credits` in the turn that runs an approved plan, plus what that turn spent before a plan it proposed itself, never above the cap the turn already had (#259: no 100-credit floor, so a 30-credit plan spends at most 30). A second plan in one turn needs the card (#408). The check uses estimates (see Credits). A paid handler works on at most its estimated units (`ToolContext.max_units`, #418). The store bills at most the estimated rows of a call. A found row past them is not stored and stays to retry. An AI Ark `search_companies` stage is sized at 25 units per call (its page), also when `more_rows` continues it. The 25 only sizes the estimate: `search_companies` has no `Price`, so the stage charges nothing.
- **Required columns** (#45). An approved plan creates its columns and sets `list_columns.config.required`, replacing the previous plan's flags. A row is **delivered** when it is not `excluded` and every required column has a non-empty value. A required `phone_status` counts as filled when the row has a `phone`: no search runs on a row that has one, so none would write the status, and a non-empty `email` fills a required `email_status` the same way, since a hand edit of an email clears its status (#720; `_MISSING_SQL`, and the web's `missingRequired` follows). Undelivered rows stay in the list (they may still be completed) with `delivered: false`, and they are not exported or counted in `delivered_count`. A tool call that updates rows reports the ones still short of a required column in its result's `list.undelivered` (`{row_id: [column keys]}`, absent when none; #539), because the model cannot read a row's cells. It describes the rows right after that call: a later call of the turn may fill them. The `enrich_email` and `enrich_phone` descriptions tell the model not to call such a row complete.
- **"Not charged" for an undelivered row** (#45). A tool call bills only rows: no tool charges per call. Every search tool, `linkedin_search` and `search_jobs_signals` have no `Price`, so they are free. A tool is paid only through its `Price`, and the tests in `api/tests/test_delivery_sql.py` fail until a fake vendor proves that each paid tool bills each row it delivers (`test_every_paid_tool_records_one_charge_per_row_it_finds`, `test_every_paid_tool_has_a_vendor_that_finds_rows`).
  - A charge pays for work on one row: `enrich_email` (1 credit per email found on that row) and `enrich_phone` (8 per phone found), each a row whose update the tool's `Price.found` accepts. AI column cells (1 per filled cell, `AI_CELL` in `app/lists/ai_columns.py`) are billed by their own fill task, with its own hold, which researches delivered rows only (#150). A plan's research fill names the turn that asked for it in its records.
  - Each per-row charge is one `row_charges` record (#660): the hold that pays for it (`hold_id`), its job (none for a per-row phone search or a manual AI column fill, whose tool call id is the click's or the cell's own id; for a plan's research fill, the turn that queued it), its tool call, its row, the billed keys the row holds (the `keys` of the tool's `Price`: `email, email_status, email_source` or `phone, phone_status, phone_source`; an AI column's own key), the `Price.credits` of one row (#668) and one state: `held`, `charged` or `refunded`. `app/billing/row_charges.py` is the only code that writes it. A charge on a row that misses a required column right after its cells are stored is *pending* (#416): its record is `held`, written in the same transaction, and the row endpoints hide the cells it bought while its hold is `reserved`. The other cells an email reveal writes (`first_name`, `last_name`, `full_name`, `title`, `linkedin_url`) are free on purpose (#476): a name or a profile link is not a priced unit, so they are never pending and a refund keeps them.
  - A charge on a complete row is final at once (`charged`). A later plan that adds a required column, an exclusion or a hand edit never refunds it. A pending charge on a row a campaign draft enrolls becomes final the same way (#462, `finalize` in `app/billing/row_charges.py`). The end-of-turn refund locks the turn's hold, then its `held` records, before it reads them, so a draft that commits first wins and its rows are never refunded. A hand edit (`PATCH /v1/lists/{id}/rows/{id}`) of `email_status` / `phone_status` is normalised as a CSV import's (#687): known values lower-cased, an unknown one dropped (the stored one stays; `not_found` when the row has no address / number), `null` clears it. A required cell cleared by hand (`cell_meta.<key>.status = 'manual'`) does not count as missing (`UNFINISHED_SQL` in `app/lists/rows.py`). A billed cell typed by hand while its charge is held is the user's value: the row endpoints show it at once, and the end-of-turn refund keeps it even when it refunds the charge.
  - At the end of the turn, in the transaction that closes the hold, every pending charge on a row that still misses a required column is refunded (a `credits` frame with `refund: true` for each call that charged them; `credits_spent`, the message's `credits_used` and the call's `credits_used` are net of it, and the call's `summary.refunded` counts its refunded rows, which the frame carries), its record becomes `refunded`, and its cells and their `cell_meta` entries are removed. Its other `held` records become `charged`. A refund returns only the charges whose cells it takes back. The refund, the close and the job's `credits_spent` commit together. A turn whose worker dies or whose end fails before that commit refunds nothing: its records stay `held`, and its hold `reserved`. The reaper closes that hold (see Credits), which makes them `charged`, so their cells show 20 minutes after the hold was taken. A turn whose hold the reaper closed first refunds nothing either, and its `credits_spent` and `credits_used` are what its records cost.
  - Completing the row later never delivers the cells for free: a later enrichment buys them again when asked by row id. The batch `enrich_email` picks without row ids skips a row whose latest email charge is `refunded`, so the vendor is not paid again every turn.
  - So an undelivered row costs 0 credits.
- **Visible cells.** One rule (`VISIBLE_CELLS_SQL` in `app/lists/row_view.py`) hides a pending cell from every reader that sends cells to a user or a model: the rows route, the `PATCH` and rating responses, `export.csv` and `export.xlsx` (the file cell is empty, and `rows=with_email` does not count a pending email; the user's exclusions still match every cell), and the rows an AI column fill researches. Campaign readers do not apply it (#462): the draft enrolls delivered rows with every cell and makes their pending charges final, and the saved-search refill holds a row with a pending charge until its turn settles.
- **Research columns** (#59). A plan column `{label, research: <question>}` becomes an AI column (`kind: 'ai'`, key `ai_<slug>`, `config.prompt` the question; a key a non-AI column uses gets `ai_<slug>_2`), filled by `fill_ai_column` (1 credit per filled cell, its own hold). It cannot be `required`, because its cells fill after the turn and the end-of-turn refund would treat every row as undelivered. Priced at 1 credit per row per research column (`credits_research_per_row`, part of `credits_per_row`). With research, the turn's tool budget is `approved_credits` minus the research share, and each plan fill is capped at `approved_rows` filled cells per column (`config.fill.cap`, counting every filled cell of the column), so tools plus fills never exceed the estimate. The turn that runs the plan enqueues `fill_plan_columns(list_id, keys, cap, job_id)` when it starts (for rows the list already has), on the first rows it adds (best fit first, delivered rows only), and at its end (the rest). A retry turn enqueues none. A column whose fill is still live is retried every minute, 30 times at most, then logged `ai_column.plan_fill_gave_up`. A manual "Fill" has no cap. An existing AI column with the same key keeps its prompt and cells.
- **Stage errors** (#213). A failed call (`ok` false) puts `error: {code}` on the stage it pays for (the first unfinished stage of its tool; in a retry turn, the retried stage) in `jobs.stages`, and the next working call of that stage removes it. `code` is `provider` (a vendor tool failed), `failed` (any other tool), `disabled` (kill switch), `not_connected` (`linkedin_search` with no LinkedIn account: connecting it fixes it, a retry does not), `no_credits` (also a free search on a balance of 0), `over_budget` (also an organization past its 1000 free rows of the day) or `crashed`. The vendor's own message is never in it. A complete stage never takes an error, and a call refused only because a retry turn does not pay for other stages (`skipped`) marks nothing. A turn that ends on an exception (the model provider failing) puts `failed` on the stage that was running (in a retry turn, the retried stage; else the first unfinished one). The job ends `succeeded` when the model answers despite a failed stage, and `failed` after an exception.
- **`stages` event** (#213). `{stages: [{tool, label, units, done, per_row, error?}], phase, credits_spent, retry_stage, list_id}`, a snapshot of the whole run so a replay never needs the frames between. `retry_stage` is the index of the stage this turn retries, else `null`. `phase` is the tool in flight, `scoring` or `null`. Sent when the plan run starts, at each tool start, when a retried stage's error clears, after each call that advances a stage, and once more at the end, after the per-row refund (`credits_spent` is then net). Only turns that run a plan send it. The web handler is `sse-handlers/stages.ts`.
- **Retry a failed stage** (#213). `POST /v1/chat` (or `/v1/runs`) with `retry_stage: {job_id, stage}`, a `session_id` and a `message`, and no `plan_approval`. It is an ordinary turn (SSE, one active job, credit hold). It is allowed only when `job_id` is the session's latest job, is not queued or running, ran an approved plan and that stage has an `error`: else 409 `RETRY.STALE`. A job that is not the user's chat's is 404 `RETRY.NOT_FOUND`. Another job running is 409 `CHAT.JOB_RUNNING`, so a double click starts one retry at most. The new job has `jobs.retry_of` and `jobs.retry_stage`, starts from the failed job's `stages` (progress is kept, and the error stays until the tool starts again in the retry), and takes over the plan's `approved_job_id`. Its system prompt says to run only that stage's tool for the rows still lacking its result and states the remaining budget. One gate before every paid call (serial, parallel and `more_rows`) refuses a call that does not pay for the retried stage (`skipped`). Its spend budget is the plan's budget minus what the failed job and earlier retries kept. Billing is unchanged, pay-if-found, and per-row charges on rows that end undelivered are still refunded at the end of that turn. Limits: other stages are not re-checked (a row whose cells were refunded stays missing until the stage that bought them runs again). A worker that died leaves no stage error, so its job has nothing to retry. The card's `credits_spent` of a retry counts that turn only.
- **Progress** (#49). The turn that runs a plan writes `jobs.stages`, with units scaled to the approved rows. A successful call adds its units to the first unfinished stage of its tool: the `searched` count it reports, else its estimated units. A per-row stage whose tool works on a list's rows (its schema takes `row_ids` or `people`, as `enrich_email` and `enrich_phone`, #568) waits for no more rows than the list its call worked on holds, not counting `excluded` rows. Once the stage is called in the turn, after every call and before a stage error is set, its `units` become the stage's units for `min(approved rows, list rows)` when that list is the plan's list, or the list's rows when it is another list (a company plan's email step counts the people list), never below `done` or above the approved units, and `jobs.progress_total` follows. So a search that delivered fewer rows than approved still lets the stage finish, and rows added later grow it back.

## Credits

- **Holds.** A job keeps one hold. It starts at `min(100, balance)` through `reserve_project_credits(project, org, user, amount, 'job', job_id, …)`, which charges the organization's wallet and respects the project's hard cap. Before a paid tool the loop estimates units (#418): the distinct rows of `row_ids` and `people[].row_id` together, else `len(items)`, else `Price.batch`, counting only keys the tool's schema declares. The handler gets the estimate in `ToolContext.max_units` and works on no more rows. If `Price.credits * estimate` exceeds what the hold has left, the loop grows the hold by `max(shortfall, 100)`, capped at the balance and the cap room. `grow_reservation` grows it under the same project lock and cap check, so the ledger shows one line with the final `amount` and, as `balance_after`, the wallet after the last growth. A hold taken in an earlier month moves into the current one when it grows, so the current month's cap must have room for all of it. If the balance or the project cap cannot cover the shortfall the tool is refused and nothing is charged: the cap message when the cap room is short of it (whatever the balance), else "Not enough credits…".
- **Charging.** The store derives the charge (`app/lists/delivery.py`). The transaction that stores a call's `row_updates` also writes one `row_charges` record at `Price.credits` for each update that the tool's `Price.found` accepts and that lands on the job's list, and the job's `credits_spent`. A miss lands and bills nothing. Found updates past the call's estimated rows are not stored, so their rows stay to retry (#418). If the store raises, nothing is stored and nothing is charged. The transaction of a paid call first locks the job's hold. If the hold is no longer `reserved` (the reaper closed it), the call stores nothing, bills nothing and fails like a handler that raised (`error_code: 'crashed'`), and the turn goes on. `credits_spent` is a cache: the `row_charges` records of the hold are the spend. At the end of the job one transaction refunds the pending charges on unfinished rows (see the per-row charges above), closes the hold through `settle_hold(hold_id)` and writes `credits_spent` as the hold's spend. The close makes the other `held` records `charged`, and the hold keeps what its records that are not `refunded` cost and refunds the rest (`settle_reservation_with_slack`), or is released when they cost nothing (`release_reservation`). A second close changes nothing. A job whose hold the reaper closed first refunds nothing, and its `credits_spent` becomes what its records cost. `jobs.reservation_id` is the hold and `credits_reserved` its amount.
- **Stale holds.** Every minute the `reap_stale_reservations` janitor closes each `reserved` hold older than `RESERVATION_STALE_AFTER_MINUTES` (20) with `settle_hold`, whatever its kind, so a holder killed before its close keeps what it recorded (#415). A chat turn's deadline (`TURN_DEADLINE_SECONDS`, 840) ends it before its hold turns stale. The per-row phone search records its charge and closes its hold in the store's transaction, so a click killed after the store keeps its charge, and one killed before it is released whole. An AI column fill writes the record of each filled cell in the transaction that writes the cell, so a fill killed midway keeps what it wrote. The scheduled search and the watchlist record their charges and close their hold in the transaction that stores the result, so a run killed before that transaction has no record and its hold is released whole.
- **Wallet.** One wallet per organization. `user_id` on credit rows is who opened, spent or bought, and `NULL` once that account is deleted (#323). A chat turn charges the chat's organization, an AI column, a scheduled search or a watchlist run the list's. A user in several organizations spends in the active one.

## Lists

- **One list per `(session, entity)`.** Later turns of a chat append to it. `ToolContext.list_id` is the last list touched in the session. Rows with the same `dedupe_key` merge field by field (#37): the first value wins and later sources fill blanks, except fields in `FIELD_OWNER` (`phone`: `google_maps` wins), and only when the existing value was written by another vendor (never an AI cell, a `manual` cell or one with no source). `source` becomes the list of sources (`"apollo, google_maps"`), and `list_rows.cell_meta[<key>] = {status: 'filled', provider}` records each value's source (the column AI cells use; only changed keys update). `static` columns are created for each key seen, plus `relevance_score` (`kind: score`, label "Fit") at position 0. A column of `config.required: true` is mandatory (#45). The columns route never returns `*_id` or `source`, `email_source`, `phone_source` columns: that plumbing stays stored in the row, and the row routes do not send it in `cells` (`public_cells`).
- **List fields.** `delivered_count` counts rows delivered under the required-columns rule. `status` is `running` while the chat's latest job is queued or running, `plan_pending` when it waits on input and this list's latest plan is not approved, `needs_input` when it waits on anything else, `empty` when it has no delivered rows (a failed or fruitless run is not `ready`), else `ready`. `target_rows` is the latest plan's `approved_rows`, else its proposed `target_rows`, `null` without a plan. `credits_used` is what the chat spent (the header's figure): the sum of `jobs.credits_spent` of the chat's turns, net of refunds, plus the AI column fills of the chat's lists (a list without a chat counts only its own fills). `brief` is the chat's first user message (300 characters at most). A list whose chat was deleted reads `ready` (`empty` without delivered rows), with its own fill credits and a `null` brief and title. `can_expand` is true once a paged search filled the list and false once it is exhausted. `findable` (#344) is the vendor's total for the last paged search (capped at the 500 pages paging reaches) minus the rows fetched so far (`last_search.total`, `last_search.fetched`), an estimate for "~N persone ancora trovabili"; `null` when the vendor sent no total, the list is exhausted, or nothing is left to fetch.
- **Prices** (#660). `GET /v1/lists/{id}` and the CSV preview carry `prices {search, email, phone, ai_cell, ai_cells_per_run}`: the credits `more_rows` charges per row, `enrich_email` per email found, `enrich_phone` per number found, an AI column per filled cell, and the most cells one fill run researches. They are read from the tools' `ToolDef.price` (0 for a tool with none) and the AI column constants (`app/lists/prices.py`); the web prices its estimates from them and keeps no copy.
- **Row fields.** `lookups` is `{email, phone}`, the state of the row's contact lookups, read from the stored cells and the row's `row_charges` records when the row is served (#659, #660): `{state: 'found', verdict}` for an email (`verdict` is the `email_status`, `unknown` when there is none), `{state: 'found'}` for a phone, else `{state: not_searched|searching|not_found|failed|refunded}`. `searching` means a running turn has the lookup open: it claimed the row before its vendor calls (`lookup_claims`, released with the call's answers, or when the call fails or stores nothing, #659), or it bought the value and hides it while the charge's hold is `reserved` (`PENDING_KEYS_SQL`). A claim of a turn whose worker died stops counting at once; a held charge of that turn reads `searching` until the reaper closes its hold (see Credits). The `list_updated` frame sent when `enrich_email` or `enrich_phone` claims its rows makes the chat panel refetch them; the list page shows `searching` when it loads and does not follow it live. `refunded` means the latest charge of the cell was refunded: a turn took the value and its status back. A `not_found` from a later search by row id, a later charge that bought the cell again, or a hand edit of the cell then wins: a PATCH that sets a new non-empty `email` or `phone` without its `*_status` clears the stored status, and an explicit status in the same PATCH wins. The row `cells` carry neither `email_status` nor `phone_status` (nor `source`, `email_source` or `phone_source`): `app.lists.rows.public_cells` strips them after `lookups` is built from the raw cells, in the rows route, the `PATCH`, rating and phone responses and the `row` frame of the fill stream. The web reads the state only from `lookups`. The status columns stay in `columns`, as markers for the web's email and phone columns, and the CSV and xlsx export keep the stored values. `crm_hold` is `null` or `{reason, until}`: why the HubSpot read gate holds this person (`HUBSPOT_COOLDOWN` until `until`). `people_count` (#229) appears only on a company list whose chat also has a person list: the not-excluded people at the company, matched domain to domain (`company_domain` against `domain` or `website`, normalised like the dedupe) when both have one, else by name (`company_name` against `name`, trimmed and case-folded). `people` (#344) is the first 3 of them in list order, `[{row_id, list_id, full_name, title}]`, with no other cell. `[]` when `people_count` is 0. `score_reasons` (#159) is `null` or up to 3 `{match, category, freshness, key}` from the scoring pass: `category` is `firmographics|website|hiring|news|technology|contact|other`, `freshness` appears only when a date is in the row's data, and `key` is the cell the evidence comes from (never a vendor or `*_id` key; the web links `cell_meta[key].source.url` when it exists, no other URL). Reasons citing a figure absent from the row are dropped. `PATCH /v1/lists/{id}/rows/{row_id}` replaces the `cell_meta` of every cell it sets with `{status: 'manual'}`: no source, AI refills skip it, and vendor merges never overwrite it.
- **Export** (`export.csv` and `export.xlsx`, free, same content; xlsx is one sheet of plain cells whose strings are never evaluated). Only delivered rows not matched by the user's current exclusions, sorted by fit, with no `*_id`, `source`, `email_source` or `phone_source` columns. `rows=all|high_fit|with_email` (`high_fit` is `relevance_score >= 70`; `with_email` on a company list is 422 `LIST.EXPORT_INVALID`). Repeated `columns=<key>` keeps those keys in list order. `verified_only` keeps rows with a non-empty email whose `email_status` is `verified` (`verified_email_sql`) (person lists only, else 422 `LIST.EXPORT_INVALID`). `hide_off_target` drops rows the user rated `bad`. The three filters combine.
- **Rate limits.** Row reads: 60 per minute per user. Exports: 10 per hour per user. Past the limit: 429 `LIST.RATE_LIMITED` with `Retry-After`. A Redis outage fails open with a log warning. Every AI column fill goes through `queue_fill`, so the limits below hold for a new column, a refill and a chat plan's research alike (#960, #971): 10 fills per hour per organization, past it 429 `LIST.AI_FILL_RATE_LIMITED` with `Retry-After: 3600`; at most 3 fills live at once per organization, past it 429 `LIST.AI_FILL_BUSY` with `Retry-After: 60`. A refused request creates nothing (a new column is rolled back), and only a claimed fill counts, so a 404, 409 or 422 uses no quota. A column with no pending delivered row is not counted. A chat plan whose fill the hourly quota refuses marks that column `fill: {status: 'failed', error: 'fill_rate_limited'}` (the list shows why, no retry); one the live cap holds is retried each minute for 30 minutes, then given up with a log line. A list holds at most 20 AI columns (deleted ones do not count): 422 `LIST.TOO_MANY_AI_COLUMNS` on add and restore; a plan proposing more than 20 research columns is refused to the model, and the plan's new columns past the list's room are not created. A fill run also stops, status `done`, after 10 cells in a row came back empty or failed (an unanswerable prompt costs a search and a model call per cell and bills nothing); the cells in flight finish. Billing stays pay-if-filled.
- **Ratings.** `PUT …/rows/{row_id}/rating` with `null` clears the rating and the note, and the note is kept only with a rating (500 characters at most). The web shows thumbs per row (bad opens an optional note) and, on an expandable list, a "More rows" button that sends a chat message naming the list id.
- **Bulk row actions and the fit filter** (#834). The bulk routes answer for the active project (`X-Project-Id`, else the default one): a list or campaign of another project is 404 `LIST.NOT_FOUND` / `CAMPAIGN.NOT_FOUND`. `POST /v1/lists/{id}/rows/mark-off-target {row_ids}` is the rating `bad` of the rating route (what exports hide with `hide_off_target`, there called "off target") for up to 1000 rows; it answers `{marked, not_found}` (ids that are no row of the list). `POST /v1/lists/{id}/rows/rate {row_ids, rating}` sets one rating (`good`, `bad` or `null`, which clears it) on up to 1000 rows; a `null` clears `rating_note`, as the rating route does, and `good` or `bad` keep it. A row with no rating has no note, so it restores the exact state before a mark-off-target (its undo); it answers `{rated, not_found}`. `POST /v1/lists/{id}/rows/add-to-campaign {campaign_id, row_ids}` enrolls the people of the rows as draft targets of a draft campaign (409 `CAMPAIGN.NOT_DRAFT` otherwise; 422 `CAMPAIGN.LIST_NOT_PEOPLE` on a company list) by the one rule of `create` (`enroll_rows` in `app/outreach/drafts.py`: exclusions, people already targets, replied or contacted before, people in another active or paused campaign) and answers `{added, skipped}`; `skipped` counts by reason, with only the reasons that occurred: `not_found`, `not_delivered`, `excluded`, `duplicate`, `no_contact` (no usable email or LinkedIn URL), `in_other_campaign`, `held_by_instantly` (Instantly holds the email and the campaign has an email step), `stopped` (the person replied, opted out or bounced in Instantly, and that stop holds every channel: never retried), `over_limit` (1000 targets a campaign). `GET /v1/lists/{id}/rows?min_fit=N` (0 to 100) returns only the rows whose `relevance_score` is at least `N`; unscored rows are out. There is no "with an SDR job ad" signal yet: `score_reasons` has a `hiring` category per row, but no field to count or filter on.
- **Delete with undo** (#341). `DELETE /v1/lists/{id}` hides the list with its rows and columns (`lists.deleted_at`). `POST …/restore` is the undo toast's call (no time limit, nothing purged). Only the creator or an organization admin may (403 `LIST.NOT_OWNER`). Another organization's or an unknown list is 404 `LIST.NOT_FOUND` (for restore, a list that is not deleted too). 409 `LIST.BUSY` while the list's chat runs a turn or one of its columns fills. A deleted list is absent everywhere a user reaches lists: `GET /v1/lists` and the campaign picker, every `/v1/lists/{id}…` route (404), the chat's `lists`, the home data (recent lists, finished searches, campaign hint, welcome `has_list`), `POST /v1/campaigns` (404), saved searches (not scheduled while deleted, resumed by a restore; a queued run fails `invalid_configuration`; saving one on it is 404) and the agent (the next turn neither loads nor plans on it, so new rows go to a new list; restoring it later leaves both lists in the chat).
- **Columns.** `DELETE …/columns/{key}` hides an AI column (`kind: 'ai'`). Any other or an already deleted column is 404 `LIST.COLUMN_NOT_FOUND`, and a live fill is 409 `LIST.COLUMN_FILLING`. Its cells stay in the rows, it leaves `columns`, exports and fills, and its key stays taken. `POST …/restore` returns the column at its old position (404 `LIST.COLUMN_NOT_FOUND` if not deleted).

### CSV upload and imports

`POST /v1/lists/upload?entity=&name=&project_id=` takes a raw CSV body (not multipart; 5,000,000 bytes and 5000 rows at most: 413 `REQUEST.TOO_LARGE`, 422 with the cause as the code: `LIST.CSV_EMPTY`, `LIST.CSV_UNREADABLE`, `LIST.CSV_NO_COLUMN` or `LIST.CSV_TOO_MANY_ROWS`) and answers 202 with the import state (#344). The worker does the import and the call does not wait. 503 `LIST.IMPORT_UNAVAILABLE` when it cannot queue.

- **Mapping.** Headers map to the canonical keys through the aliases in `app/lists/csv_import.py`. Unknown headers become extra columns, `*_id` headers are renamed `*_ref`, and a `Source` header becomes `csv_source`. UTF-8 or cp1252, with `,`, `;` or tab sniffed. The optional `mapping=` (also on the preview) is a JSON array with the key per CSV column by position: a canonical key except `source`, `''` to drop the column, anything else keeps the detected key. 422 `LIST.CSV_BAD_MAPPING` if it is not an array of strings or is longer than 8000 characters.
- **What happens to rows.** Uploaded rows carry no `source`, and every cell gets `cell_meta {status: 'manual'}`, so a vendor merge never overwrites it. Rows merge on `dedupe_key`. Dropped rows are discarded: matching the project's exclusions (`excluded`), whose `dedupe_key` is already in a live list of the target project with the same entity (`in_lists`; another project's lists do not count, since a project is a client), repeats inside the file (`duplicates`, merged into the first), and rows with no identity (`skipped`). `discarded` is the sum of the four. The list gets `mode = 'enrich'` and a new chat session in the project, where the agent can enrich it.
- **Preview.** `POST /v1/lists/upload/preview` takes the same body and limits, writes nothing and is free. `samples` holds the first non-empty value under each header (80 characters at most), `rows` the non-blank data rows, and `mapping` the detected key per header. The counts are what the upload would do with that mapping. `incomplete` counts rows to import with no `email` (person) or no `domain` and `website` (company).
- **Import state** lives in `csv_imports`, owner-scoped (another caller is 404 `LIST.IMPORT_NOT_FOUND`). `processed` counts rows written so far, in chunks of 100. `cursor` is the stream position read before the state. `GET /v1/lists/imports/active` returns the caller's newest import in the active project that is queued or running, or finished and not marked seen within 24 h, else `null`. `POST …/seen` marks it. `GET …/discarded.csv` returns the rows not imported as they came, plus a last column `Motivo` (`In Esclusioni`, `Già nelle tue liste`, `Duplicata nel file`, `Senza nome, dominio o LinkedIn`).
- **Stream.** `GET /v1/lists/imports/{id}/stream` (SSE, `Last-Event-ID`, `: ping` every 15 s) sends `progress {processed, total}`, `done {list_id, chat_session_id, rows_added}` or `failed {code}` and ends after `done` or `failed`. A caller who left the organization gets `error {code: 'AUTH.NOT_A_MEMBER'}` (see Server-sent events), and the dialog shows the import failed with that code. The import task runs as that member, so it stops at its next database access.
- **Failure.** A failed import stores an error code in `csv_imports.error` (the state's `error`) and sends it in the `failed` frame: the file's cause (`LIST.CSV_EMPTY`, `LIST.CSV_UNREADABLE`, `LIST.CSV_NO_COLUMN`, `LIST.CSV_TOO_MANY_ROWS`), `LIST.IMPORT_FAILED` for anything else, or `LIST.IMPORT_INTERRUPTED`. Imports that failed before #674 hold English text there.
- **Lifetime.** A failed import keeps the rows already written. The uploaded file is deleted when the run ends. The beat janitor `reap_csv_imports` (every 5 minutes) fails an import running with no progress for 15 minutes, or still queued after 2 hours (`error` `LIST.IMPORT_INTERRUPTED`, a `failed` frame, the file deleted), and clears `discarded` 7 days after the run ends, after which `discarded.csv` is empty. Closing the dialog does not stop the job.

### AI columns

- `config.fill` is `{status: queued|running|done|failed, error, queued_at, started_at, filled, empty, failed, credits, cap?, by?, job?}`. `by` (#323) is the member who queued it, from the API or through the turn whose plan asked for it, and who spends it; without it the list's creator spends it. `job` (#408) is that turn: the fill's `row_charges` records name it. `error` is `insufficient_credits`, `project_cap_reached`, `vendor_disabled`, `not_a_member` (whoever spends it is no longer a member of the list's organization when the worker claims it; nothing held or charged), `fill_crashed` (the task or a cell crashed, or the reaper closed the hold. The hold is settled, and a crash of the task itself is re-raised) or `fill_stale` (an API-only view: queued more than 20 minutes since `queued_at`, or running more than 20 minutes since `started_at`, so the worker was killed; a refill is then allowed).
- `POST /v1/lists/{id}/columns` queues the fill (`key` is `ai_<slug>`, unique in the list, appended last). `POST …/columns/{key}/fill` returns 202 and fills cells still missing or `failed` on delivered rows. 404 `LIST.COLUMN_NOT_FOUND` (not an AI column), 409 `LIST.COLUMN_FILLING` while a fill is live (not `fill_stale`), 503 `LIST.QUEUE_UNAVAILABLE` (the fill is then marked `failed`).
- The Celery task `fill_ai_column` researches each pending delivered row (not excluded, every required column set, #150, checked again when the cell is written so a row excluded mid-fill is not billed; best fit first, at most 200 per run, 5 at a time): one `web_search` (vendor cost in `vendor_calls`, kill switch `vendor_disabled:firecrawl`), then one LLM call (`llm_usage`, endpoint `ai_column`) that must answer from the results only. A value is kept only with an http(s) `source_url` from those results and with every figure present in the evidence, else the cell is `empty`.
- **Per-cell source.** `list_rows.cell_meta[<key>] = {status: filled|empty|failed, source: {url, title}|null, error, at}`. The value is in `cells[<key>]` only when `filled`. `cell_meta` never reaches the CSV.
- **Credits.** One hold per run (a `Tab`, `app/billing/tab.py`, with `reference_type='ai_column'`, `reference_id='<list_id>:<key>'`) for `min(pending, balance, what the project cap leaves)` cells. 1 credit per **filled** cell (empty and failed are free): the transaction that writes a filled cell also writes its `row_charges` record. The end of the run closes the hold through `settle_hold`, which keeps what the records cost and refunds the slack, and `fill.credits` is what it kept. The reaper settles a run killed before its end by the same rule (see Credits, Stale holds). The cell's transaction locks the hold before the row. If the reaper closed the hold first, the cell's write rolls back and nothing is billed. The run then stops, so the other cells make no new vendor call, and the fill ends `failed` with `fill_crashed`. A balance of 0 gives `fill.status=failed` with `insufficient_credits` and nothing researched.
- **Snippets** (#933). An AI column with `config.mode = 'snippet'` writes one short line per row from the research cells the list already holds. It makes one LLM call a cell (`llm_usage`, endpoint `ai_snippet`) and no web search. A research column has no `mode`. A snippet column's `config` is `{mode, prompt, inputs, row_ids, approved_credits, fill}`: `inputs` are keys of live research columns of the same list (not a snippet, a vendor or a plain column), and `row_ids` and `approved_credits` are what the user approved.
  - `POST /v1/lists/{id}/columns/estimate` `{inputs, row_ids}` (1 to 10 inputs, 1 to 200 rows) returns `{research_rows, credits}`. `research_rows` counts the rows of `row_ids` that are delivered and hold, in one of `inputs`, a `filled` cell with a source that the user can read. `credits` is `research_rows` × 1 (the AI cell price), the most the fill charges. It is a POST because 200 row ids do not fit in a URL.
  - `POST /v1/lists/{id}/columns` with `mode: 'snippet'` also takes `inputs`, `row_ids` (at most 200) and `approved_credits` (≥ 1). Without `row_ids` or `approved_credits` it returns 422 `LIST.SNIPPET_APPROVAL_REQUIRED`. With an input that is not a research column of this list, it returns 422 `LIST.SNIPPET_INPUTS_INVALID` (the estimate too). The fill and every `…/fill` retry take only `row_ids` that have research and a missing or `failed` cell, until `approved_credits` of the `row_ids` cells are `filled` or `manual`. A hand edit can replace a charged cell, so a `manual` cell still counts against the approval. A fill reads only inputs that are not deleted: a research column deleted after the create stops feeding the snippet. A row with no research gets no cell and costs nothing.
  - `POST /v1/lists/{id}/columns/{key}/regenerate` `{row_ids (1 to 200), approved_credits}` returns 202 and queues a fill with `fill.refill` (the row ids) and `fill.cap` (`approved_credits`). It takes those rows whatever their cell holds, except a hand edit (`manual`), at most `cap` of them. A hand edit made while the fill runs also wins: the fill does not write that cell and charges nothing for it. It overwrites a cell only with a new `filled` snippet: an empty or failed answer keeps the old cell and counts in `fill.empty` or `fill.failed`. It skips a row whose `cell_meta.at` is after `fill.queued_at`, so a run claimed again charges a row once. Each new snippet costs 1 credit. 404 `LIST.COLUMN_NOT_FOUND` (not a snippet column), 409 `LIST.COLUMN_FILLING`, 429 as a fill, 503 `LIST.QUEUE_UNAVAILABLE`.
  - A snippet is `filled` only when the answer names, in `used`, an input cell that is filled for the row, and when each figure in it appears in those cells, the row's name fields or the prompt. Else the cell is `empty` with `error` `ungrounded` (or `no_research` when no input is filled). A model error is `failed` with `snippet_failed`. `source` is the source of the first used cell. The check cannot prove each phrase: the prompt forbids any fact outside the cells.
  - Kill switch: the settings row `vendor_disabled:ai_snippets` (an admin adds it in Settings). A fill then ends `failed` with `vendor_disabled` before it holds credits. `vendor_disabled:firecrawl` does not stop a snippet.
- **Live fill** (#252). Nothing polls. `GET /v1/lists/{id}` carries `fill_cursor`: while a column is `queued` or `running`, the list's newest fill-stream entry id (`'0-0'` when none), read before the columns it returns; `null` when no column fills (no Redis read) or Redis is down. `GET /v1/lists/{id}/stream` (JWT or `sbk_` key) replays frames after `Last-Event-ID: <redis entry id>` (none or invalid means from now). 404 `LIST.NOT_FOUND`, 503 `LIST.STREAM_UNAVAILABLE` when Redis is down. Frames are pushed by the fill task after its commit: `fill {key, fill}` (the column's whole `config.fill`, raw: `running` when the task claims it, then `done` or `failed` with the counts) and `row {row_id, cells, cell_meta}` (the patch one researched cell wrote, merged the same way; `cells` is `{}` unless the cell is `filled`). A caller who left the organization gets `error {code: 'AUTH.NOT_A_MEMBER'}` (see Server-sent events). On each frame or ping at least 30 s after the last check (`MEMBER_RECHECK_SECONDS`), the stream also checks that the list still exists (#413), and sends `error {code: 'LIST.NOT_FOUND', message}` and ends when it was deleted. After either, the web stops following without reconnecting and the list page shows the code (`LIST.NOT_FOUND` is the not-found page). The Redis stream is `list:{id}:fill` (MAXLEN ~1000, TTL 1 h). The web loads the list, then the rows (so they are never older than the cursor), follows the stream from `fill_cursor` while a column fills, and reconnects with backoff and `Last-Event-ID`. A Redis failure loses frames only (logged `stream.publish_failed`); a reload shows the state.

### Per-row phone search

`POST /v1/lists/{id}/rows/{row_id}/phone` (no body) uses the same path and price as `enrich_phone` (its `Price.credits`, 8): the Apollo then Treg waterfall through `paid_call` with the vendor kill switches. It holds the price first (a `Tab`, `app/billing/tab.py`, with `reference_type` and `tool_name` `enrich_phone`). One transaction stores the answer through the chat's delivery (`app/lists/delivery.py`), which writes the `row_charges` record of a found number, and closes the hold through `settle_hold`. So the click keeps 8 when a number is found (`status: 'found'`, `credits: 8`) and releases the hold otherwise (`credits: 0`), and `credits` is what the close kept. A click killed after that transaction has paid; one killed before it stored nothing, and the reaper releases its hold (see Credits). `status` is `found`; `not_found` (the row gets `phone_status: 'not_found'`); `already` (the row has a phone, nothing searched); `no_input` (the row has no Apollo id, LinkedIn URL, email, or first and last name with a company, so no source can be asked: nothing held, searched or stored, and the web asks for one of them); `unavailable` (vendor not configured or switched off); `failed` (a vendor crash, a source that failed including an unfinished Apollo phone job, or a miss while Apollo is off or unkeyed: the row gets `phone_status: 'failed'`, not `not_found`, so the web offers the search again, #504, #659).

- A person list of the caller's organization only: a foreign or unknown list or row, or a company list, is 404 `ROW.NOT_FOUND`.
- When the reaper closed the hold before the store (a hold older than `RESERVATION_STALE_AFTER_MINUTES`), a found number answers `failed` with `credits: 0` and the row unchanged: no number, no `phone_status`, nothing billed, and the web offers the search again. A miss stores its verdict as usual and bills nothing.
- 409 `ROW.EXCLUDED` for a row excluded in the list or matched by its project's exclusions (#550), before any hold. 409 `ROW.PHONE_RUNNING` while a search for the same row runs (a per-row lock, so two clicks never pay twice). 402 `ROW.NO_CREDITS` or `ROW.PROJECT_CAP` when the balance or the project's hard cap cannot hold the price (the vendor is not called). 503 `ROW.PHONE_UNAVAILABLE` when the lock store is down or the `enrich_phone` tool is not registered.

## Home and streams

Home routes use the active project (#307). `replies`, `running` and `has_memory` are per user where noted.

- **`GET /v1/home/todo`** (#209) lists `approvals`, `replies` and `running` in that order, omitting an item with `count` 0. `approvals` counts `awaiting_approval` messages of the active project's campaigns, with the same rule as `awaiting_approval` in `GET /v1/campaigns` (the person is still `active` on that step, and the hold does not keep them); `title` is the name of the campaign with the most messages, `href` is `/campaigns/<id>`. `replies` counts the caller's unread `reply` and `reply_urgent` notifications (the bell's read state), `title` is `data.name` of the most recent or `null`, `href` is `/inbox`. `running` counts `queued` or `running` jobs updated within `STALE_JOB_MINUTES`, `title` is the session title, `href` is `/?s=<session_id>`.
- **`GET /v1/home/welcome?locale=<language>`** (#210; one of the interface languages in `api/app/core/locale.py`, default `en`, other values 422) returns `null` or the first-access screen. `knows_from` is `website`, `description` or `none`. `segments[].titles` are the first two roles, `employee_range` prints "11,50" as "11–50", `key` is the first 16 hex characters of the SHA-256 of the stored segment's JSON (keys sorted), so it changes whenever the segment does. `message` is `first_list_message(segment, locale)`, the chat's first message. The card does not carry the brief: `POST /v1/chat` with `segment` and `POST /v1/onboarding/complete` build it with `first_list_brief`. The brief is in the segment's language, so its headers match its text (#657); the `locale` query parameter picks the language only for a segment stored without one. `locale` is the language the segment's `name` was written in (`null` on segments stored before #643). The name is not translated: when it differs from the language shown, the web adds a note above the cards (#646). `segments` is `[]` without a profile ("Salta per ora"). `steps` are always `profile`, `list`, `mailbox` in that order. `profile` is done with an onboarding profile or non-empty memory. `list` is done with at least one list of the project that is not deleted and has a row. The empty list of a search that found nothing does not count. `mailbox` is done with a `google` or `microsoft` row with `status = 'connected'` linked to the active project (`project_senders`). The result is `null` when onboarding is not completed (an old account), the screen is closed, or the required steps (`profile` and `list`; `mailbox` is optional) are done. In the last case the GET closes the row (`business_profiles.welcome_closed_at`), so it never returns, even if the user later deletes the list. `POST /v1/home/welcome/dismiss` returns 204, idempotent.
- **`GET /v1/home/overview`** (#298) always carries all keys. `approvals.campaigns` lists the two campaigns with the most messages and omits those at 0, so the web shows "N in other campaigns" as `total` minus their counts. `replies` counts the caller's own unread reply notifications of the active organization (a reply notifies only the campaign owner). `replies.latest.intent` is the reply's label only when it is in `HIGH_INTENT` and the sender is not unverified. `running` lists `queued` or `running` jobs of the project's chats from any member, updated within `STALE_JOB_MINUTES`, newest first. `stages_done` counts `jobs.stages` with `done >= units`, `stage_tool` is the first unfinished stage's tool (`null` with none), `entity` is the entity of `jobs.list_id`'s list (`null` while the job has no list, and the web then reads the noun off `stage_tool`), `rows` counts that list's non-excluded rows, and `new_list` is true when the job created its list. `finished` lists the project's finished searches of the last 2 minutes (`FINISHED_MINUTES`, by `finished_at`), newest first: a job that `succeeded` with no step error (the rule of the session list's `error` status: a `jobs.stages` entry with an `error`, or a failed tool call other than `ask_user` and `set_brief`), on a list that is not deleted and has a row (`FINISHED_SEARCH_SQL`, `app/home/overview.py`); `entity` and `list_id` are never `null` there. A failed, cancelled or `needs_input` job never appears there, nor does a turn that wrote no list, a turn with a step error (even on a list with rows from an earlier run) or a search that found no row, so the web plays the finish only for a run it saw in `running` that reappears in `finished`. `lists` still includes the list of a job in `running`, and the web hides it while the run shows. `lists` holds the five newest by activity (`updated_at` is the later of the list's `created_at` and its newest row; `rows` excludes excluded rows; `verified_emails` counts rows with a non-empty email whose `email_status` is `verified` and is `null` for a company list). `campaigns` holds the three newest `active` or `paused` ones, with `sent` and `replies` from the same SQL as `GET /v1/campaigns`. `campaign_hint` is set only when `campaigns` is empty: the newest person list with `verified_emails > 0` and no campaign on it, else `null`. `started_by` and `owner` are `{id, name}`, or `null` once the creator's account is deleted (#333).
- **`GET /v1/home/stats`** (#826) is the dashboard's numbers for the active project, apart from `overview` so the live stream does not recompute them. `kpis` has five `{value, previous}` pairs: `value` counts the last 30 days, `previous` the 30 before (the web computes the delta): `leads` (non-excluded rows created in non-deleted lists), `contacts` (those rows with an `email` or `phone` cell), `messages_sent` (campaign sends in `sent`, by `delivered_at`), `replies` (inbound messages of kind `reply`, by `received_at`; auto-replies and unsubscribes do not count) and `positive_replies` (replies labelled `interested` or `meeting_request`). The set is our choice, not the design's. `weeks` is always 8 entries, oldest first, the last being the current ISO week (`week` is its Monday 00:00 in the database's zone, UTC): `messages_sent` and `replies` as above, 0 when empty. `funnel` is over the last 30 days: `leads`, `contacts`, `contacted` (distinct recipients of a sent message), `replied` and `positive` (distinct people who replied, by sender address, not messages). The stages are counts of the same period, not one cohort followed through: a person contacted last month can reply this month. `activity` is the latest 10 events, newest first, `{kind, at, title, link}`: `search_finished` (a finished search, with the rule of the overview's `finished`; `title` the session title, `link` `/lists/<id>`), `campaign_started` (`activated_at`; `title` the campaign name, `link` `/campaigns/<id>`) and `reply_received` (`title` the sender's name or address, `link` `/inbox`). `title` can be `null`.
- **Live streams.** `GET /v1/home/stream` sends `event: snapshot` at once and `event: overview` only when the overview changed, both with the full overview body. `GET /v1/home/nav/stream` (#342) sends `snapshot` then `nav` with `{lists, campaigns, approvals, views, replies, sessions}`: `lists` counts the project's lists that are not deleted and have a row (`GET /v1/lists` also returns the empty ones), `campaigns` is what `GET /v1/campaigns` returns for the project, `views` is the length of `GET /v1/saved-views`, `approvals` and `replies` are the overview's `approvals.total` and `replies.count`, and `sessions` is `GET /v1/chat/sessions?project_id=<active>`. The web's sidebar and phone menu share one stream per tab (`web/lib/home/nav.ts`). Both streams: frames carry no `id:` and the stream ignores `Last-Event-ID`, so a reconnect gets a fresh `snapshot` that the web diffs against what it shows. `: ping` every 15 s. Triggers on every table the overview reads (migration `20261007085629_home_notify.sql`; the tables the hold reads, `outreach_stops`, `instantly_leads` and `audience_aliases`, in `20261017143943_home_touch_holds.sql`) NOTIFY the Postgres channel `home` with `p:<project_id>` or `u:<user_id>`. An INSERT or DELETE always notifies; an UPDATE only when it changes a column the Home reads (`WHEN` clause of each `home_touch_update` trigger, `20261022103549_home_touch_columns.sql`), so a backfill of any other column is silent. A new Home query that reads another column adds it to that clause. One `LISTEN` connection per API process (`app/home/live.py`) wakes the streams of that project or user. A woken stream waits 400 ms without a change, 1.5 s at most, then recomputes, so a running search costs one recompute per 1.5 s at most. A stream also recomputes with no write when a run turns stale or a finished run leaves its window. Each recompute, and every 30 s while idle, checks that the project still belongs to the organization, and ends the stream without a frame when it does not. A caller who left the organization gets `error {code: 'AUTH.NOT_A_MEMBER'}` (see Server-sent events); the web refreshes the page and reconnects once into the organization the session moved to, and when that reconnect answers 401 it stops, and the sidebar shows its load error when no `nav` arrived. When Postgres is down the stream ends and the web reconnects. A transaction-mode pooler between the API and Postgres would break `LISTEN`.

## Integrations

- **Mailboxes** (JWT only; the active project's). OAuth: Google `openid email gmail.send gmail.readonly`, Microsoft `offline_access User.Read Mail.Send Mail.Read`. Replies are read from the sending mailbox with that read scope (#1165, see Replies from the mailbox); the signed Reply-To carries them only when `OUTREACH_REPLY_DOMAIN` is set. The read scope also reads the bounces (owner decision on #747, see Bounces). ## Campaigns and inbox

### Campaigns

A campaign belongs to its list's project and sends only from that project's senders (#307), so every member may read and run it (no owner gate). Another organization's campaign is 404. `GET /v1/campaigns` lists the active project's campaigns, newest first, at most 200. `?status=draft` (or another campaign status) keeps only that status, so the add-to-campaign picker sees every draft however many other campaigns exist.

- **Counters** (#216, #218, #346). `failed` counts terminal failures: `refused`, `failed` with no attempt left, or a `sent` email that bounced hard (#747; it stays in `sent` too). `steps_done / planned_sends` is the progress bar, and it measures how far the sequences got, not delivery. A person's step is done once they are past it (sent or skipped) or it ended in a terminal failure, which leaves them on it for good. Planned is every step for a person still in the sequence, and only the done ones for someone who replied, was excluded or is stuck on a terminal failure. `contacted` counts people with at least one `sent` message. `replied_contacted` counts those of them who replied, so the reply rate `replied_contacted / contacted` never exceeds 100%. The raw `replied` can exceed `contacted`: a reply marks the matching targets of the owner in one organization (an opt-out marks them in every organization), including people this campaign never wrote to. `sent_today` counts this campaign's email sends attempted since local midnight in `OUTREACH_SEND_WINDOW_TIMEZONE`. `awaiting_approval` counts the messages waiting for approval whose person is still `active` on that step and not held (#931); `awaiting_approval_held` counts those the hold keeps, which approving would not release. `daily_cap` is the sum of the daily caps, warm-up included, of the connected pool mailboxes, shared with the owner's other campaigns. `interested` counts people with a reply labelled `interested` or `meeting_request`. `unread_replies` counts the campaign's inbound messages not opened yet, any kind (the badge of "Risposte", which opens `/inbox?campaign=<id>`). `invalid_email` counts people with a send `refused` as `INVALID_EMAIL` or an email that bounced hard (#747). `chat_session_id` is the chat that built the list, `null` for an imported list or once the chat is deleted ("Riscrivi con l'agente" opens it). `list_id` and `list_name` are `null` once the list is deleted.
- **`POST /v1/campaigns {name, list_id, block_active_duplicates?}`** makes a `draft` that enrolls the owned person list's delivered rows with their cells (the first 1000 by relevance) as `draft` targets with `source=manual`. The enrollment rules are the saved-search refill's (`app.scheduling.runner.enrollment_verdict`). Skipped are user exclusions, rows with neither email nor LinkedIn, people who replied or are excluded in any of the owner's campaigns, prior contacts under `block_prior_contacts`, and people in another active or paused campaign under `block_active_duplicates`. `block_active_duplicates` (default `true`) is stored before the enrollment, so it applies to it. The new campaign's pool starts with the client's connected Google and Microsoft accounts, 20 at most. The email is dropped unless the row has one the verifier did not call `invalid` (`deliverable` in `app/lists/lookups.py`). The draft makes final every per-row charge still pending on a row it enrolls (#462). 404 `LIST.NOT_FOUND`, 422 `CAMPAIGN.LIST_NOT_PEOPLE`.
- **`PATCH /v1/campaigns/{id}`.** `steps` go through `app.outreach.step_copy.checked_steps` (shared with the agent tool): 422 `CAMPAIGN.INVALID_STEPS` (12 steps at most), 422 `CAMPAIGN.LINKEDIN_NO_INVITE` (a LinkedIn message with no LinkedIn invitation step before it), 422 `CAMPAIGN.LINKEDIN_DM_DELAY` (a LinkedIn message on the same day as the LinkedIn message before it), 422 `CAMPAIGN.COPY_TOO_LONG` (a subject over 300 or a body over 4000 characters, naming the step and field; a field token counts at the length of its fallback, and a required one at the length of the token), 422 `CAMPAIGN.SUBJECT_LINE_BREAK`, 422 `CAMPAIGN.PLACEHOLDER` (a leftover `[x]` or `{{x}}`). Each refusal carries `step` when it names one step. A step may carry `b: {subject, body}`, its copy B (#934). Copy B goes through the same checks on the same shape: a threaded email has no B subject, and a B subject is one line. A refusal in copy B carries `variant: "b"`. A refusal in the step's own copy or shape has no `variant`. A step without copy B is stored and returned with no `b` key. Editing `steps` or `fields` works only on a draft (409 `CAMPAIGN.NOT_DRAFT`). A PATCH with `fields` checks the saved steps again with the new fields. A `stopped` or `completed` campaign takes no edit, even to `name` (409 `CAMPAIGN.INVALID_TRANSITION`). The PATCH does not change the pool: `PUT …/senders` sets it by account. The body field `sender_pool` (a list of provider names) and the response field of the same name were removed in #935. Like any unknown field, a `sender_pool` in the body is ignored. `block_active_duplicates` (#83, #931) may change on a `draft`, `active` or `paused` campaign: it is read at each enrollment (create, add to campaign, refill), at activation and at each plan, so a change applies from the next one. Turning it off adds no one that an enrollment already left out. It never lets Instantly email a person while a native campaign with an email step holds them, and it never narrows a stop: a reply stops the person in every campaign of the project either way.
- **Fields (#933).** `fields` on a campaign is the list of personal fields its copy may use beside the contact tokens: `{token, source: {kind, key}, fallback}`. `token` matches `^[a-z][A-Za-z0-9]{1,39}$` and is not a contact token. The copy writes it as `{{token}}`. `source.kind` is `column` (a list column `key`) or `signal` (`title`, `city`, `country` or `url` of the person's watchlist signal). A column key can never be a vendor id (`*_id`), a vendor name (`source`, `email_source`, `phone_source`) or a raw contact status (`email_status`, `phone_status`). `fallback` (1..200 characters) fills a person with no value. `null` makes the field required. At most 20 fields, each token once. A bad list is 422 `CAMPAIGN.INVALID_FIELDS`.
  - Each person reads a column field from their own list row (`outreach_campaign_targets.row_id`). The read sees only the visible cells (no cell that an unsettled charge holds) of a delivered row in a list of the campaign's project. A row of another project, a row that is no longer delivered, and a person with no `row_id` read as no value. The value becomes one line of at most 500 characters with no `{`, `}`, `[` or `]` (`fields.sanitize`).
  - `GET …/fields` is the field picker's catalog: `{people, contact_tokens, columns, signal}`. `columns` are the visible columns of the campaign's list and of the lists its people come from, without the contact columns. `signal` lists the four signal fields when at least one person has a signal, else it is empty. Each entry is `{token, source, label, ai, filled}`. `token` is the token a new field from that source gets, `ai` marks an AI column, and `filled` counts the people with a value, out of `people`.
  - **Frozen values.** A person's values freeze when they become active: at activation, at the approval of an automation's review run, at an enrollment into an `active` or `paused` campaign (automation, watchlist signal) and at a refill. `app.outreach.freeze.freeze` writes `outreach_campaign_targets.personalization` (`{values: {token: text}, sources: {token: {kind, key, row_id, url, title}}, missing: [token]}`) and `frozen_at`. `values` holds every contact token and alias and every field token, `sources` says where each field value came from (a column value names its list row, a signal value its posting), and `missing` lists the required tokens that a step uses and the person has no value for. A person with a `missing` token stays `draft` and waits: no step goes out to them. The dispatcher renders every step from `values` only, so a cell edited after activation changes nothing that the person receives until a regenerate. The migration adds the two columns and writes no row, so people who were active or paused before #933 have no snapshot. A person with no snapshot (activated by an earlier release, during a deploy or after a rollback) renders from their contact columns, cleaned the same way, and shows no `frozen_at`. Only `freeze` moves a draft person to `active`: the trigger `outreach_target_activates_by_freeze` refuses that UPDATE unless the transaction-local setting `zenbree.freezing` is `on`, which only `freeze` sets around its own UPDATE. An INSERT is not checked. The trigger makes the migration a rollback floor (`docs/migrations.md`). `api/tests/test_only_freeze_activates.py` names a write that would hit the trigger before it runs.
  - Behavior change: contact values go out cleaned by `fields.sanitize`, as the preview shows them. A company named `Acme [EU]` is sent as `Acme EU`; before #933 the send was refused as `PLACEHOLDER_IN_MESSAGE`.
  - **`POST …/targets/regenerate`** freezes the values again from the current cells, on an `active` or `paused` campaign (else 409 `CAMPAIGN.INVALID_TRANSITION`). It reads everyone `active` or `paused` and the `draft` people who wait for a value, re-applying the enrollment rules to the waiting ones first. It answers `{active, renewed, waiting, kept}`: waiting people who start now, people in the sequence with new values, people who still wait, and people in the sequence who keep their earlier values because a required value is gone now (a new snapshot would make their next step a refused claim). A `sending` claim that the provider rate-limits (`INTEGRATIONS.RATE_LIMITED`) goes back to `approved` with the copy planned before the regenerate, and the next beat sends that copy, which the user approved. A plan that read the person before a regenerate claims nothing (`frozen_at` changed). The regenerate starts no AI column fill.

- **Sending accounts (#935).** `GET /v1/campaigns/{id}/senders` lists the Google and Microsoft accounts linked to the campaign's client as `{senders, max_senders}`. When people wait for a value, the error carries `waiting` (how many people miss a value) and `missing` (the tokens they miss, sorted), and the builder names each token by its field's label. Both are absent when nobody waits. `pause` (active to paused) and `resume` (paused to active); other transitions are 409 `CAMPAIGN.INVALID_TRANSITION`. The dispatcher beat turns an `active` campaign `completed` once nobody is left in a sequence: every person replied, was excluded, is past the last step, or is stuck on a terminal failure. A `paused` person keeps it open, and so does a `draft` one who waits for a value (#933), because a regenerate can still start them. Nothing ends that wait by itself: the campaign stays `active`, and refill, watchlists and automations keep enrolling into it, until a member gives the person a value and regenerates, or the person leaves the sequence through a reply, an unsubscribe or a bounce. No route removes one person from a running campaign. The people list says so next to the person. Any other `draft` one (awaiting activation) does not. Before it plans, each beat sets a `paused` person whose `paused_until` has passed back to `active`, so that beat claims their next step (#346), unless meanwhile they replied or were excluded in another campaign of the project, on any alias or the same LinkedIn profile (they end `replied` or `excluded`), or a stop holds them (they stay `paused`) (#931).
- **Copy variants** (#934). A campaign tests two copies while some step has `b`. Channel, delays, threading and the number of steps are shared, so only subject and body differ. `b_percent` (10..90 in steps of 10, default 50) is the share of people who get copy B, and `allocation_paused_at` is set while the allocation is paused. Both are on `GET /v1/campaigns/{id}`. `PUT /v1/campaigns/{id}/allocation` takes exactly one of two bodies and answers the campaign:
  - `{"b_percent": n}` works only on a draft (409 `CAMPAIGN.NOT_DRAFT`). A value off the scale is 422 `REQUEST.INVALID_INPUT`.
  - `{"paused": true|false}` works only on an `active` or `paused` campaign (409 `CAMPAIGN.INVALID_TRANSITION`). A second pause keeps the first `allocation_paused_at`.

  A person gets a variant once, when the freeze makes them active (activation, enrollment into a running campaign, regenerate). The freeze walks the joiners in the order of `sha256(campaign_id:target_id)` and gives copy B while B stays below `b_percent` of everyone the campaign assigned so far. From the first join, the split stays within one person of `b_percent`, whatever the batches. A person who joins while the allocation is paused, or who joins a campaign with no test, gets `variant: null` and copy A for good. A database trigger refuses any other change of `variant`. A joiner who may get either copy waits as `draft` until both copies have their values. Anyone else needs the values of their own copy only. A step without `b` sends copy A to the people in variant B, and a threaded B follow-up replies under the B subject that went out. Copy stays fixed after activation, as all steps do.
- **Targets.** `GET …/targets` returns the first 1000 people, newest reply first then by name. `message_*` is the person's newest inbound message (`/inbox?m=<message_id>` opens it), `last_sent_*` the highest delivered step, `awaiting_approval` a message on the current step that waits for approval and whose person the hold does not keep, and `paused_until` is set exactly while `status` is `paused`. `frozen_at` (#933) is when the person's values were last frozen (`null` before the first freeze), `variant` (#934) the copy the person gets (`a`, `b`, or `null` for copy A outside a test), and `missing` the required tokens a waiting `draft` person has no value for (`[]` for anyone else). `hold` (#931) is what keeps this campaign from the person, read through `app.outreach.holds` with the campaign's channel (`email` when it has an email step, else none): `stop_pending`, `stop_failed` or `stopped` (an Instantly stop of the person, `stopped` once confirmed), `held_by_instantly` (Instantly owns their email; only on a campaign with an email step), else `null`. `email_sender` says which system sends their email: `instantly` while Instantly holds a lead of theirs or a stop is not yet confirmed (also on a LinkedIn-only campaign, through an alias), `native` when the campaign has an email step and the person an email and nothing holds them, `null` when nobody does (no email step, no email, or a confirmed stop). It comes from a second read of the hold on the `email` channel. `sender` (#935) is the address of the account the person's conversation is on (`null` before their first email, or when that account is gone). `sender_hold` says why that account cannot send their next email, so the person waits: the send queue gives the email to no other account. It is `null` when nothing holds the conversation, and always `null` for a person who is not `active`, whose campaign is not `active` or `paused`, or whose next step is not an email. `app/outreach/sender_holds.py` gives the reasons in this order:
  - `send_uncertain`: the email of the current step is `sending`. A send in flight shows it for a few seconds. A send whose outcome is unknown keeps it until a person settles it.
  - `mailbox_unknown`: the conversation started on an account Zenbree no longer knows (deleted, or a thread from before #307).
  - `disconnected` or `needs_reconnect`: the account's status is `disconnected` or `error`. Reconnecting the same account clears it.
  - `unlinked`: the client no longer uses the account.
  - `not_in_pool`: the campaign does not send from the account.
  - `paused` or `throttled`: the account is paused, or it rests after a provider rate limit (the senders page's reasons). A capped account, or one outside its window, waits for time and holds nothing. A kill switch holds nothing either: it is a global switch, shown on the senders page.
- **Activity (#835).** `GET /v1/campaigns/{id}/activity?after=&limit=` (limit 1..100, default 20) is the campaign's recent events, newest first: `{items, next_cursor}`. An item is `{id, kind, at, target_id, first_name, last_name, company_name, step, channel, label}`. `kind` is `sent` (a delivered send, `at` = `delivered_at`), `approved` (a held message the person approved, `at` = `approved_at`; a send approved on creation, as an auto-approved one or a CRM task, has no such event) or `reply`, `auto_reply`, `unsubscribe` (an inbound message, `at` = `received_at`, `id` is the message id and `label` its label). `step` is set for `sent` and `approved`, `label` for inbound ones only, and the name fields are `null` once the person is deleted. `next_cursor` is an opaque keyset on (`at`, `id`, `kind`) when the page is full, else `null`; pass it as `after` for the next page, and nothing is skipped or repeated when events share one timestamp. A bad cursor is 422 `REQUEST.INVALID_INPUT`. `channel` is `email`, `linkedin_connect`, `linkedin_message`, `linkedin` (inbound) or `hubspot_task`. The campaign must belong to the active project (`X-Project-Id`): another project's or organization's campaign is 404 `CAMPAIGN.NOT_FOUND`. - **Campaign report (#942).** `GET /v1/reports/campaigns?from=YYYY-MM-DD&to=YYYY-MM-DD&tz=<IANA zone>` reports what each campaign of the active project (`X-Project-Id`) did in a date range. `from` and `to` are dates in `tz`, both included: the API converts each bound to that zone's midnight on its own, so a range across a DST change keeps its local days. The response is `{window: {start, end, time_zone}, campaigns, instantly}`. `campaigns` lists the native campaigns that ever started (`activated_at` set; a draft is not listed), newest first, then each Instantly campaign the project enrolled people into, by name. A row is `{sender: native|instantly, id, name, status, list, counts, lineage, variants}`. For an Instantly row, `id` is Instantly's campaign id, and `status` and `list` are `null`. `counts` is `{enrolled, contacted, sent: {email, linkedin_connect, linkedin_message}, human_replies, positive_replies, bounced, meetings, deals}`. `enrolled` is the people in the campaign now, whatever the range. `sent` counts delivered sends in the range, not people; a CRM task is not a send. Every other count is people: a person counts once for each measure, on the date of their first event of that kind in the campaign (first delivered send, first reply that is not an auto-reply or an opt-out, first reply labelled `interested` or `meeting_request`), and only when that date is in the range. So two adjacent ranges add up to the range that joins them, and a reply in the range can come from a person contacted before it. For the same reason `positive_replies` can be more than `human_replies`: a person who first replied before the range and first replied positively in it counts only as positive. A reply counts for the campaign that received it. A native reply that matched no person counts by its sender's address, or by its LinkedIn member id when it has no address, and as a person of its own when it has neither. For an Instantly campaign, a person is an address, a reply is human once a vote says human or opt-out (or, when the key may not read emails, with no vote), positive is a lead label of `interested`, `meeting_booked`, `meeting_completed` or `won`, and `bounced` is the first bounce. A webhook send that the API never listed, within 10 minutes of a listed send to the same address, of the same campaign and step (or with the step unknown on either side), is that send retried: `sent` counts it once. `null` means unknown, never zero: native `bounced` (native bounces are not stored yet, #747), and `meetings` and `deals` on every row (HubSpot outcomes are not read yet; an interested label is neither). `lineage` splits `contacted`, `human_replies` and `positive_replies` into rows of `{list, source, signal: {watchlist_id, watchlist_name, type} | null, contacted, human_replies, positive_replies}` that add up to the row's counts. A native row's lineage is the campaign's list, the person's `source` and their signal's watchlist and type; a person deleted since, or a sender that matched no person, is in the row with `source` and `signal` `null`. An Instantly row's lineage is the list each lead came from, with `source` and `signal` `null`. `variants` (#934) splits a native campaign that tests copy B (some step carries `b`) by the copy each person got, in rows of `{group, enrolled, contacted, sent: {email, linkedin_connect, linkedin_message}, human_replies, positive_replies, bounced}`. `group` is `a` or `b` for the person's `variant`; `outside` for a person in the campaign with no variant (they joined while the allocation was paused and got copy A); `unknown` for a send or reply of no person in the campaign (a person deleted since, or a sender that matched no person). `a` and `b` are always listed, in that order, then `outside` and `unknown` only when they count something. Each count summed over the groups is the row's count, and so is each channel of `sent`. The counts follow the row's rules: `enrolled` is the people in the group now, whatever the range, `sent` counts sends, every other count is people on the date of their first event, and `bounced` is `null` (#747). Because of that rule a group's counts are not nested, so the report derives no rate and picks no winner. A native row with no test, and every Instantly row, has `variants: []`. `instantly` is `{mode, complete_until, failing_since, last_error_code}` when the project ever connected Instantly, else `null`: the Instantly counts are complete only up to `complete_until`. An unknown zone, a bad date, `to` before `from` or a range longer than 366 days is 422 `REQUEST.INVALID_INPUT`. Another project's or organization's campaigns are never in the report.
- **Preview.** `GET …/preview?limit=` (default 3, range 1..10) renders like the dispatcher. For an email step `sign_off` is the sign-off of the mailbox that sends this person (`allocation.predict`: the account the person's conversation is on, else a stable pick among the pool accounts with no `blocker`; at send time `allocation.assign` decides), and `footer` is the opt-out lines under the `---` rule exactly as `sending.compose_body` appends them, without the per-person unsubscribe link (a live one would opt the person out). Both are `''` for LinkedIn steps and for a step with an `error`. `error` is `NO_EMAIL`, `INVALID_EMAIL`, `NO_THREAD`, `COPY_TOO_LONG` or `OUTREACH.COPY_*`. `COPY_TOO_LONG` counts the filled copy against the limit of its channel: 300 for a subject, 300 for an invite note, 4000 for any other body. Each item has `missing`, the tokens of the required fields that the person has no value for and that a step's subject or body uses (`OUTREACH.COPY_MISSING_FIELD` in each such step). A field that no step uses is never in `missing`. ### Inbox and replies

The inbox is per project: `GET /v1/inbox` lists the active project's messages, and `counts` cover the active project (or the campaign's project when `campaign_id` is given), within `channel` and `campaign_id`. The thread, relabel and reply routes take any message of the organization by id, for any member (a notification or a campaign links it whichever client is active). A message outside the organization is 404 `INBOX.NOT_FOUND`. A message files under the project of the campaign it answers, else the newest campaign's project of its owner's own organization (else that organization's first project), never a team's. A LinkedIn DM matches the targets of the campaigns of the projects the account serves, and the message's owner is that campaign's owner.

- **Reply address.** Each campaign email and each inbox answer carries a signed `Reply-To` at `OUTREACH_REPLY_DOMAIN` (none until it and `OUTREACH_REPLY_SECRET` are set; production leaves it empty and reads replies from the mailbox, see Replies from the mailbox). The address has one of two forms (`app/core/reply_address.py`):
  - `reply+c<campaign uuid hex>.<hmac12>@<domain>`: the campaign form, minted for every campaign send and for an inbox answer to a message filed under a campaign. A reply to it is filed in that campaign's organization and project, under that campaign, with no ranking. The reply stops the person in that organization's campaigns of the campaign's creator (else its former creator, else its client), and that campaign's matched target, if any, is the message's `target_id`. An opt-out and an autoresponder reach every organization, as below. A campaign deleted (`DELETE /v1/projects/{id}`, `DELETE /v1/campaigns/{id}` of a draft) leaves its key in `outreach_campaign_reply_keys`: the creator, else the creator who deleted their account since, else the client. A reply to its address is matched and ranked as the old form of that key, so an opt-out to its `List-Unsubscribe` mailto still stops and excludes the person in every organization. The key is kept with no expiry, as the mailto has none, and goes only with its organization. A draft keeps its key too, as an inbox answer can mint its address. An address that names no campaign and no kept key (an id never minted) is `ignored`.
  - `reply+<owner or project uuid hex>.<hmac12>@<domain>`: the old form, which names the creator, or the client once the creator's account is deleted (#333). Mail sent before the campaign form carries it, and an inbox answer to a message filed under no campaign still mints it. A reply to it is routed by the ranking below. Its parse is removed 90 days after go-live (sends before go-live are test sends). The ranking stays for a deleted campaign's key. The same change gives an inbox answer to a message with no campaign a reply address of its own: with no `Reply-To`, the person's reply would reach a send-only mailbox and leave the inbox.

  `hmac12` is the first 12 hex characters of HMAC-SHA256 over the id with `OUTREACH_REPLY_SECRET`, prefixed `campaign:` for the campaign form, so a signature of one form never verifies in the other. An address that does not verify is `ignored`.
- **`POST /v1/inbound/email`** (hidden; no JWT) receives Resend `email.received`, signed by Svix with `OUTREACH_INBOUND_WEBHOOK_SECRET`. 401 for a bad signature. 503 when not configured or the content is unreadable, so Resend retries. It answers `{status: ignored}` for mail not addressed to a valid signed reply address, `accepted` or `duplicate` with `kind: reply|auto_reply|unsubscribe` (`accepted` also has `targets`, the number of targets of any owner that the message stopped, or paused for an autoresponder; the LinkedIn webhook answers the same for `message_received`), and `{status: 'excluded', kind}` for an opt-out to the address of a deleted member that matches none of their people or messages (the exclusions are written, the message stored nowhere).
- **Reply handling.** A reply (not an autoresponder) is filed and stops targets: it sets that organization's matching targets of the owner to `replied`, skips their open sends, and emits `contact.replied` to one organization only (#414): the campaign's, for the campaign form of the reply address; for the old form the one of the quoted send, else the one of the newest delivered email to that address, else the one of the newest target. In the project where it is filed, the reply also stops every open target of any owner whose email or LinkedIn URL is one of the person's, aliases included (#937, #931; `app/outreach/coordination.py`), whatever `block_active_duplicates` says, so those campaigns count the reply too. An opt-out applies in every organization: it adds email and LinkedIn exclusions, stops every matching target, and emits `sequence.stopped` (reason `unsubscribed`) but no `contact.replied`; in the filing project it stops the person's other targets as a reply does. A reply and an opt-out queue an Instantly stop for each held lead of the person (see "Native outreach and the hold"). The cap on reply-driven opt-outs is `MAX_OPT_OUTS_PER_DAY` (50) per owner, or per client for an owner-less message (`exclusions.reply_opt_out_at`).
- **`sender_authenticated`** (#421, #986) is the DMARC verdict of an email. The trust root is the `authentication` object of Resend's receiving API (`GET /emails/receiving/{id}`), which Resend documents as computed by the receiving server and not taken from the message headers (https://resend.com/docs/api-reference/emails/retrieve-received-email). A header the sender wrote, `Authentication-Results` included, decides nothing. `true` means `authentication.dmarc` is `pass` (aligned with the From domain). `false` means `fail`. `null` means no verdict: `gray` (no policy or p=none), `processing_failed`, `unknown`, no `authentication` object, LinkedIn, rows from before. Only a `true` email opt-out creates an exclusion (and it still counts toward the daily cap), and only a `true` email reply emits `contact.replied`; LinkedIn replies are not subject to either. A reply with `false` or `null` stops its targets and stays in the inbox, but emits no `contact.replied` (an opt-out creates no exclusion; the owner can exclude by hand). A `false` reply also gets no draft. Its notification is always kind `reply` with `data.unverified: true`, never `reply_urgent` and never the urgent email. The digest still lists it, the bell and the badge count it, and the label task still runs.
- **Autoresponders** (`auto_reply`) are filed in the same one organization and set every matching `active` or `paused` target of the owner in every organization, and in the filing project every such target of any owner of the person's aliases, to `paused` with `paused_until` 7 days ahead, at the opening of the send window (`OUTREACH_SEND_WINDOW_START_HOUR` in `OUTREACH_SEND_WINDOW_TIMEZONE`). Their held sends wait, neither listed for approval nor sent. The label task then reads the last day away from the text and moves `paused_until` to the next day, at least tomorrow and at most 60 days ahead; no date keeps the 7 days. A later autoresponder never shortens a longer pause, and the date it reads moves it again. An autoresponder never moves a `replied` or `excluded` target and queues no Instantly stop. A real reply or an opt-out still stops the person (#346).
- **Labels.** `interested|meeting_request|not_interested|not_now|other`. `label_source` is `llm` or `manual`. A `PATCH` sets `manual`. A reply labelled `not_now` has one reminder (`outreach_reminders`): the day the model read from the reply (a month alone is its 1st, the next one to come), else 90 days ahead, at most a year ahead. A `PATCH` to `not_now` creates it 90 days ahead and keeps one that exists. A `PATCH` to any other label deletes it. The dispatcher beat marks the message unread again (`read_at: null`) on its `remind_on` day in `OUTREACH_SEND_WINDOW_TIMEZONE`, once, and sets `surfaced_at`. No notification is sent.
- **`GET /v1/inbox/{id}?mark_read=`** marks the message read unless `mark_read=false`. `sent` lists the campaign steps that reached this person before the reply, oldest first. `draft` is the agent's proposed answer, written after labelling except for `not_interested` and an unverified sender. It is `null` when the thread cannot be answered, and once an answer to the message is `sent` (#1057), until a member asks for a new draft (`POST /v1/inbox/{id}/draft`). A `failed` or `unknown` answer keeps it. `reply_from` is the mailbox address or `linkedin`. `reply_blocked` is `null` or the code that a reply would fail with (below). `reply_hold` (#935) is why the account of the person's conversation cannot answer, when `reply_blocked` is `INBOX.NO_MAILBOX` and the conversation started: `mailbox_unknown`, `disconnected`, `needs_reconnect` or `unlinked`, as in the targets' `sender_hold`. Otherwise it is `null`. A paused mailbox or Unipile account sends no answer either, and LinkedIn replies are checked against the person's email exclusions too.
- **`GET /v1/inbox?sort=newest|oldest`** orders by `received_at` (default `newest`). `counts` ignore it.
- **`POST /v1/inbox/{id}/draft`** (#836, #970) is limited to 10 a minute per user (429 `INBOX.RATE_LIMITED`, `Retry-After: 60`) and awaits the model on the event loop, holding no threadpool slot. It asks the agent for a new draft answer and overwrites the stored one; it answers `{draft}`. The model call runs in the request and is metered to the caller (`llm_usage.endpoint = reply_draft`). The same rules as the first draft apply: 409 `INBOX.NO_DRAFT` for a reply that gets none (unlabelled, `not_interested`, unverified sender, `auto_reply` or `unsubscribe` kind) or when the model answers off the schema, leaving the old draft; 502 `INBOX.LLM_FAILED` when the provider fails or has not answered within 30 s, with no draft written (the timeout cancels the call before the write); 404 `INBOX.NOT_FOUND` for another organization's message. A client that disconnects may cancel the call before it stores its draft (not guaranteed either way); nothing is billed and the old draft stays.
- **`POST /v1/inbox/{id}/reply`** (#187) sends the answer on the reply's channel: an email from the mailbox that wrote to the person (the project's only mailbox when none is pinned), threaded under their Message-ID with the signed Reply-To and the mailbox sign-off, or a LinkedIn DM from the project's Unipile account. It ignores the campaign window and the pacing gap, but respects the mailbox daily cap, LinkedIn's 30 DMs per day (shared with campaign sends), the kill switches and the exclusions. Errors: 403 `INBOX.UNSUBSCRIBED`; 409 with the `reply_blocked` codes (`INBOX.UNSUBSCRIBED`, `INBOX.EXCLUDED`, `INBOX.NO_MAILBOX`, `INBOX.NO_LINKEDIN`, `INBOX.NO_RECIPIENT`, `INBOX.ACCOUNT_PAUSED`), `INBOX.REPLY_IN_PROGRESS` or `INBOX.MAILBOX_ERROR` (missing send scope leaves the mailbox connected; a grant the provider revokes or refuses, or a stored token that cannot be read, marks it `error`; any other refresh failure answers 503 `MAILBOX.TEMPORARILY_UNAVAILABLE` and leaves it connected); 503 `MAILBOX.TEMPORARILY_UNAVAILABLE` (the provider's token endpoint failed transiently: a retry may succeed, the mailbox stays connected); 422 `INBOX.PLACEHOLDER` or `INBOX.INVALID_CONTENT`; 429 `INBOX.MAILBOX_CAPPED`; 502 `INBOX.SEND_FAILED` (stored `failed`) or `INBOX.SEND_UNKNOWN` (stored `unknown`: maybe delivered, never resent); 503 `INBOX.CHANNEL_DISABLED`. A `sent` answer clears the stored draft in the same transaction, and the agent writes no draft for that message afterwards. A `sending` claim older than 5 minutes becomes `unknown` (`error_code: STALE_CLAIM`) at the next send on that thread. The cap is counted again at the claim, under a lock on the sender's row that a campaign send's slot also takes (#987): with one send left, two competing answers or an answer and a campaign step admit exactly one (the other is `429 INBOX.MAILBOX_CAPPED`, or a lost slot for the campaign). The lock is never held across OAuth or a provider call.

### Bounces

Delivery-status notifications (DSN, RFC 3464) reach the mailbox that sent, and Zenbree reads them there (#747). No polling: the provider pushes.

- **Watch.** Before a send, a mailbox whose grant has the read scope starts or renews its watch once less than 6 days of it are left (`app.integrations.mailbox_watch.keep_watching`): Gmail `users.watch` on `INBOX` to `GMAIL_PUSH_TOPIC`, Microsoft a Graph subscription to `created` messages of the inbox, 7 days less an hour. A mailbox idle for 7 days stops hearing until its next send. `user_oauth_connections` keeps `inbound_subscription_id` (Graph), `inbound_subscription_expires_at` and `inbound_history_id` (Gmail's cursor). A failed watch is logged and the send goes on. Disconnecting a mailbox stops its watch first (Gmail `users.stop`, unless another live row of the same Google account still uses it; Graph deletes the subscription), best effort, and clears the three columns.
- **`POST /v1/integrations/mailboxes/google/push?token=`** (hidden; no JWT) is Pub/Sub's push subscription. 401 `INTEGRATIONS.WEBHOOK_UNAUTHORIZED` for a token other than `GMAIL_PUSH_TOKEN` or when Gmail push is not configured; 204 otherwise, a malformed body included (Pub/Sub would redeliver it forever). The address in `message.data` is matched to the connected Google mailboxes with that `account_label` and a live watch, across organizations (`SystemReason.MAILBOX_PUSH`), and one `read_mailbox_bounces` is queued in each one's organization.
- **`POST /v1/integrations/mailboxes/microsoft/push?c=&o=`** (hidden; no JWT) is the subscription's notification URL, naming its connection and organization. With `validationToken` and an empty body (Graph's check on creation) it answers the token back HTML-escaped, as `text/plain` with `X-Content-Type-Options: nosniff`; the token is at most 512 characters (422 above), and a `validationToken` with a body is 401. Otherwise only notifications whose `clientState` is the HMAC of `c` and `o` with `OUTREACH_REPLY_SECRET` count: none is 401 `INTEGRATIONS.WEBHOOK_UNAUTHORIZED`, else 202 and one `read_mailbox_bounces` with their message ids. 503 `INTEGRATIONS.UNAVAILABLE` when the queue is down, on both routes, so the provider retries.
- **Reading.** The task reads the headers of each new message (Gmail: history since `inbound_history_id`, which then moves; Graph: the notified ids) and fetches whole only a DSN or a reply to our sends (see Replies from the mailbox): a DSN is `multipart/report; report-type=delivery-status`, a `mailer-daemon` or `postmaster` sender, or an `Undeliverable`/`Delivery Status Notification` subject. Nothing of any other message is stored, and a DSN is never also a reply. A DSN counts only when the provider wrote it (anyone can mail a fake one), read with one strict parse that refuses anything ambiguous (`app.outreach.dsn.read`): no `Authentication-Results` or ARC header at all (the provider writes its own report into the mailbox, so a message carrying the receiving server's verdict came from outside, whatever the verdict says); exactly one `From`, one address, Gmail's `mailer-daemon@googlemail.com` or for Microsoft `postmaster` or `MicrosoftExchange…` at the account's own domain or a Microsoft consumer domain; exactly one `Content-Type` and `report-type=delivery-status`, no MIME defects; among the report's direct parts exactly one `message/delivery-status` and one original (`message/rfc822` or `text/rfc822-headers`) with exactly one `Message-ID`; exactly one recipient block with one `Final-Recipient` (`rfc822`, one address), one `Action` and one well-formed `Status`. A refused one is logged as `mailbox_push.dsn_rejected`. Each message is handled on its own: a failure to fetch or parse it (a provider error, a parser failure, a fetch over 12 s) is logged as `mailbox_push.dsn_unparsable` (message id only) and skipped, and a report over 1 MB (Gmail's `sizeEstimate`, or the body read so far) is never fetched whole or parsed. A bounce that matched a send and could not be stored, and the task's time limit, stop the read instead: the task retries up to 3 times, and on its last try logs `mailbox_push.store_failed` (error, message id) and moves past that message, so an error that recurs every time never pins the cursor. Gmail's cursor moves to the last history record whose messages were all handled (history lists the records after it): Gmail's current history id once all are, else that record when a read passes 30 s, reads more than 100 messages or stops on an error. Graph reads past 30 s queue the notified ids left as a read of their own. A recipient block with `Action: failed` and a `5.x.x` status is a hard bounce; `delayed` or `4.x.x` is soft. A DSN in plain text only is not read.
- **Replies from the mailbox** (#1165, `app.outreach.mailbox_replies`). The same read treats a message that is no DSN as a reply when, from its headers alone (`From`, `Subject`, `Content-Type`, `In-Reply-To`, `References`, `Message-ID`, `Authentication-Results`, `Auto-Submitted`, `Precedence`, `X-Autoreply`, `X-Autorespond`), it names a `message_id` or `provider_message_id` of this mailbox's sends in `In-Reply-To` or `References`, or its sender is an active target of a campaign this mailbox has sent for (a message from the mailbox's own address is skipped). Only such a message is fetched whole (up to 5 MB; a larger one is recorded without its text); any other is never fetched and nothing of it is stored. It goes through `app.outreach.replies.record` as the inbound route does (stop, opt-out, label, `contact.replied`), filed under the matched campaign, with `authentication` the `dmarc=` verdict of the topmost `Authentication-Results` header, read only when its authserv-id is the provider's (`mx.google.com`; `*.protection.outlook.com`, so a Microsoft header with no authserv-id gives none) and it is unambiguous (one `dmarc` resinfo whose `header.from` is the domain of the `From`, property values of addr-spec and domain characters only, no quote or nested comment; none means no verdict, so an opt-out stops the person but excludes nobody, as for a Resend `gray`). It is recorded once: the provider message id (`mailbox:<connection id>:<message id>`) and the email's own `Message-ID` are both checked, so a redelivered push, a retried task and the same reply through `POST /v1/inbound/email` add nothing. The message stays in the mailbox as it was: no label, no read flag. A failure to store a matched reply is retried as a bounce is. An opt-out read from the mailbox is matched under `System(OPT_OUT)` like the Resend route's, so it stops and excludes the person in every organization of the owner (#460). Limit: an out-of-office read from the mailbox pauses the person only in the mailbox's organization, because the pause in other organizations needs a system reason that no module of this path holds.
- **After a send** (`app.integrations.mailbox_watch.delivered`), a grant with the read scope reads back the `Message-ID` the provider gave the email (Gmail and Exchange may replace ours) into `provider_message_id`: Gmail's sent message by the id `messages.send` answered (metadata), for Microsoft the sent copy with the `Message-ID` we wrote when Exchange kept it, else the one sent copy of the last 2 minutes (5 read) whose only recipient and subject are the send's (`internetMessageId`); two such copies, or none yet saved, store nothing, and the `Message-ID` we wrote is the match. The same hook rechecks the pause threshold of a campaign that has a hard bounce, so bounces that came before its 20th send count once it has.
- **Match.** The send is the mailbox's `sent` email to the bounced address whose `provider_message_id` or `Message-ID` (the one we wrote) is the one quoted in the DSN's `message/rfc822` or `text/rfc822-headers` part. A DSN that quotes none, or one that names no such send, changes nothing (logged as `campaign.bounce.unmatched`). It gets `bounced_at`, `bounce_kind` (`hard`|`soft`) and `bounce_status`. A soft bounce changes nothing else, and a later hard one replaces it.
- **Hard bounce.** It takes the hard bounce path of Instantly's bounces (#931, `app.outreach.coordination.apply`): the person stops as `excluded` in every campaign of the campaign's client, aliases included, their waiting sends are skipped, their Instantly leads there get a stop, and their email (and the target's LinkedIn URL) are excluded in that client (`origin: 'bounced'`). `sequence.stopped` names reason `bounced` (Instantly's own hard bounces name `excluded`). A verified address (`email_status: 'verified'` on its list row) that bounced within 7 days of its send gets its email credit back once, only when MillionVerifier, asked again at the bounce (owner decision on #919: a bounce report alone can be planted), calls it `invalid`. The check runs in `read_mailbox_bounces`, never on the push request, only for a hard bounce that matches a send in the window, metered like enrichment's (`vendor_calls`, `millionverifier.verify`) and gated by `vendor_disabled:millionverifier`; `ok`, `catch_all`, `unknown`, no key, the switch on, an error or no answer within 15 s refund nothing, and the bounce stands (stop, exclusion, pause). The refund: the newest final email charge of that address on a row of the campaign's own list becomes `refunded`, the cells it bought (`email`, `email_status`, `email_source`) leave that one row while it still holds the bounced address (charge and row locked in the bounce's transaction; a row whose email changed or was found again since keeps it and refunds nothing; rows of other lists or clients with the address are never touched; a campaign with no list refunds nothing) (owner decision 2026-10-16: the refund takes the data back, so a report the user plants in their own mailbox gains nothing; the address stays excluded, and the row's email reads `refunded`), and the ledger gets `type='refund'`, `reference_type='email_bounce'`, `reference_id=<send id>`. A charge whose hold is still reserved is left to its turn. An address typed by hand over the bought one (`cell_meta` status `manual`) is not refunded.
- **Pause.** When more than `BOUNCE_RATE_PERCENT` (5) of at least `BOUNCE_MIN_ATTEMPTS` (20) sent emails of an `active` campaign bounced hard, the campaign becomes `paused` and its owner gets `bounces_high` with `paused: true` (see Notifications). Resuming it is the user's call; a further bounce over the threshold pauses it again.

### Unsubscribe link

Public, no JWT, cookies ignored. Every campaign email carries `List-Unsubscribe: <{one-click URL}>, <mailto:{reply address}?subject=unsubscribe>` and `List-Unsubscribe-Post: List-Unsubscribe=One-Click` (RFC 8058; each part only when configured), and the footer links the page. With `UNSUBSCRIBE_ORIGIN` (#220, such as `https://u.zenbree.com`) both are `{UNSUBSCRIBE_ORIGIN}/x/{token}`: the web serves only that path on that host (GET and the page's server actions render the page, a plain POST is the one-click, forwarded to `POST /v1/unsubscribe/{token}`; every other path is 404), and the app host's `/u/{token}` answers 308 to it for older emails. Without it the one-click is `{API_PUBLIC_BASE_URL}/v1/unsubscribe/{token}` and the page is `{WEB_ORIGIN}/u/{token}`.

`token` is an unpadded base64url Fernet token over (owner uuid, recipient address), with a key derived from `OUTREACH_REPLY_SECRET` and a domain label: opaque (no address in logs), authenticated and stateless, and only the canonical spelling parses. Every bad token is 404 `UNSUBSCRIBE.INVALID_LINK`. The owner is the project once the campaign's creator is gone (#333). Unlike the reply address, the token does not name the campaign: an opt-out stops the person in every organization (#460), so it needs none. A token in a sent email is the person's opt-out and keeps working with no removal date.

- `GET /v1/unsubscribe/{token}` (hidden) answers 303 to the page and never unsubscribes.
- `POST /v1/unsubscribe/{token}?reason=` takes any body (such as `List-Unsubscribe=One-Click`). The optional `reason` is `not_interested|wrong_person|too_many|other`, is only logged, and anything else is 422. It is idempotent (`unsubscribed` or `already_unsubscribed`) and adds email and LinkedIn exclusions as a "no grazie" reply does, sets the person's open targets to `excluded`, sets open sends to `skipped` with `error_code: UNSUBSCRIBED`, and queues an Instantly stop for each held lead of the person in the projects it excludes in. The undo lifts the exclusions only: the stops stay.
- `GET …/state` reads only. `sender_*` and `last_*` come from the newest sent email to that address and its mailbox, `company_name` from the business profile, `unsubscribed_at` is the email exclusion's date. Each is `null` when unknown.
- `POST …/undo` removes exactly the exclusion rows that unsubscribe inserted, by id (kept in Redis for 1 hour per owner and recipient): a rule recreated by hand after the link's was deleted is another row and stays, and adding the same rule by hand or CSV while the link's row is still undoable (inserted by the link, not a reply opt-out, less than an hour old) claims it (`origin` becomes `manual`) so the undo skips it; older link rows and reply opt-outs keep their origin, and a grant stored before ids undoes nothing. Existing manual, CSV or "no grazie" exclusions are never touched, an unsubscribe that inserted nothing has no undo, and there is one undo per unsubscribe. Cancelled sends stay cancelled. 409 `UNSUBSCRIBE.UNDO_EXPIRED` otherwise; 503 `UNSUBSCRIBE.UNAVAILABLE` (Redis).
- `POST …/erasure` emails the owner's account address a data-deletion request. 409 `UNSUBSCRIBE.NOT_UNSUBSCRIBED`; 429 `UNSUBSCRIBE.RATE_LIMITED` (once a day per owner and recipient, whatever the token); 502 `UNSUBSCRIBE.ERASURE_FAILED`; 503 `UNSUBSCRIBE.UNAVAILABLE`.

## Other account routes

- **API keys** (JWT only; organization admins only). `key` (`sbk_…`) is returned once, and only its SHA-256 hash and its last 4 characters (`last4`, for the list's mask `sbk_…4f2a`) are stored. `last4` is `null` for a key issued before it was stored. Keys belong to the organization; an unknown, revoked or other organization's key is 404. Labels are trimmed to 1-120 characters. An organization holds at most 10 active keys (409 at the cap).
- **Memory** (JWT only). One document per user (`user_memory_doc`, 8000 characters, 422 above). `locked` stops only the agent tools `remember` and `forget`, never the user. Every chat run puts the head of the body (whole lines, `prompt_max_chars`) in the system prompt, and `truncated` says the tail does not reach the agent.
- **Exclusions** (JWT or `sbk_` key; the active project's). "Never find, enrich or contact" rules of kind `email`, `domain` (covers subdomains and the email domain), `company_name` or `linkedin_url`, stored normalised like list rows (`app.exclusions.rules.normalise`). `origin` is `profile` (synced from the business profile), `unsubscribed` (a link unsubscribe, a reply opt-out or Instantly's own unsubscribe), `bounced` (a hard bounce in Instantly, #931, or read from the sending mailbox, #747), `own_domain` (the domain of the profile's website, written by `POST /v1/onboarding/profile` when the website changes, under the same `source = 'onboarding'` lock; the old one is removed) or `manual` (by hand or CSV). A profile rule claimed by a manual add or an opt-out takes that origin. `exclusions.source` stays the profile lock and is not returned. `POST` takes 1-5000 items, guesses `kind` from the value when absent (CSV import), and does not re-add duplicates. `invalid` lists the first 50 unparseable values. 422 `EXCLUSIONS.INVALID_VALUE` when no item is valid, 409 `EXCLUSIONS.LIMIT` past 50,000 per project. `DELETE` is 404 for an unknown id or another project's. Exclusions apply when rows are saved from a tool or a scheduled search (dropped before the List; the tool result the model reads gets `excluded_by_user: n`), when enrichment loads rows, in campaign refill and on the send path, which must call `load_rules` and `is_excluded` per recipient. The request body cap of 1 MB limits `POST` for API-key callers.
- **Onboarding** (JWT only; the active project's, so a new project runs it for itself). `needs_onboarding` is false once completed or skipped, or when the project already has a chat. `POST /v1/onboarding/profile` answers SSE (#350) and reads the site with `fetch_page` (SSRF-safe). Before the stream starts it can fail as plain HTTP: 422 when neither field is filled, 429 `ONBOARDING.LIMIT`. Frames, in order: `page {url}` for each page read (none for a description-only study); `drafting {}` once the site read is over and the LLM call starts; `offer {summary}` as soon as the reply's `summary` string is complete (it can be missing); then `profile {profile, pages}` (saved to the project) or `error {code, message}`. The request takes `locale?` like `/segments`, and the profile is written in it. Error codes: `ONBOARDING.SITE_UNREADABLE` (no page is readable and there is no description) and `ONBOARDING.STUDY_FAILED` (the analysis failed; `ONBOARDING.LLM_FAILED` is the segments' code). Either gives the free run back, except `STUDY_FAILED` once the model streamed text (a dropped stream or a reply that did not parse): that output was billed. `AUTH.NOT_A_MEMBER` when the caller left the organization during the study (see Server-sent events): nothing is saved, and the run still counts when the LLM ran. The client cancels by closing the connection: the API stops the study and saves nothing, unless the cancel lands while the profile is being saved, after the reply is complete. A cancel before `drafting` gives the free run back, and a cancel after it still counts, because the LLM ran. The agent reads the profile from the project, not from the user's Memory (#307), so a save no longer writes a Memory bullet. `PUT /v1/onboarding/profile` also syncs the profile's `exclusions` lines into Exclusions (#193): a line that parses as an email, domain, LinkedIn URL or a company name (up to four capitalised words, `app.exclusions.rules.profile_rule`) becomes a rule with `exclusions.source = 'onboarding'`. Descriptions ("competitors") stay brief-only. A save applies only the lines that changed since the last sync (`business_profiles.exclusion_lines`): it adds rules for new lines and deletes onboarding rules whose line is gone, so an unrelated save never re-creates a rule the user deleted. A rule the user already had stays theirs (`source` NULL) and a profile save never removes it. `POST /v1/exclusions` and an opt-out claim an existing onboarding rule (`source` becomes NULL, not counted as added). `POST /v1/onboarding/segments {locale?}` makes segments from the saved profile, in `locale` (the language the user sees; the web sends its cookie) or, without it, in `"user".locale`. A given `locale` is used for that call only and never saved (#795): only an explicit choice writes `"user".locale`. Each segment carries `locale`, the language it was written in (`null` on segments stored before #587), and the segments step of the onboarding page shows a note that offers to propose them again when a stored segment is in another language than the page. Each segment also carries `signal_hint`, a short signal to look for (such as open job postings) that the LLM guesses from the profile (#191). It is a hint, not evidence: it costs no credits and nothing checks it. It is `''` when the model names none and on segments stored before #191. 409 `ONBOARDING.NO_PROFILE` without a profile; 502 `ONBOARDING.LLM_FAILED`, which gives the free run back unless the model replied and the reply did not parse. The segment `criteria` keys are the `search_people` keys. Each filter keeps the form the search takes, not the user's language (#878): `industries` and `locations` are English (the vendor's industry names, English country names); `titles` and `keywords` are in the language of the segment's target market (Italian titles for Italy), with the common English title added where profiles there use it. The segment's text (`name`, `who`, `problem`, `outcome`, `signal_hint`) is in the user's language. The study and the segments are free LLM calls, metered as `endpoint='onboarding'` and capped at 10 per organization through its wallet's `user_credits.onboarding_free_used` (429 `ONBOARDING.LIMIT`); a team a user created counts on its founder's own organization's wallet (#676). `POST /v1/onboarding/complete {segment?, locale?}` takes `locale` like `/segments` (not saved; the first turn writes in it, as `locale` of `POST /v1/chat`) and starts the first list as a normal chat turn (same credits and 409 as `/v1/chat`). The turn's first message is one line that names the segment, and the chat title is the segment's name. The whole brief (`first_list_brief`, with the search filters) goes in `chat_sessions.brief`, and the agent reads it in place of that first message on every turn. Both are in the segment's `locale` (#657) or, for a segment without one, in the user's (`locale` or `"user".locale`). The agent answers in the user's. Without a segment it only marks onboarding done (skip) and `session_id` is `null`.
- **Public API.** `docs/public-api.md` is the guide for `sbk_` callers. `GET /v1/me` carries the balance fields. `plan_credits` (#434) is what the live subscription's plan grants each period (from `BILLING_PLANS` by `plan_id`, any status in `LIVE_STATUSES`), `null` without one; it is the 100% of the sidebar's credits bar. `plan_credits_left` and `plan_credits_reset_at` (the live subscription's `current_period_end`) and `purchased_credits` split the balance (#348): plan credits are the unused part of the current period's allowance, spent first and removed at reset, and purchased credits are the rest and never expire. Without a live plan `plan_credits_left` and `plan_credits_reset_at` are `null` and `purchased_credits` is the whole balance. All are `null` without a wallet. `org_role` is read from `member` with the call.

## Billing

One credit wallet per organization (#306). `user_credits`, `credit_transactions`, holds, `purchases`, `billing_customers`, `subscriptions` and `auto_topups` carry `organization_id`. The credit functions take the wallet then the actor: `deduct_credits` and `reserve_credits(org, user, amount, …)`, `increment_credits(org, user, amount, type, …)`. The hold functions take the reservation id. Every route except `packs`, `plans` and the webhook needs an admin of the caller's active organization (`require_org_admin`, #308): 403 `AUTH.ORG_ADMIN_ONLY`. The web's `/billing` shows members only the balance. Checkout and setup sessions and the subscription and auto top-up invoices carry `metadata.organization_id` and `user_id`, and the webhook credits that organization (one made before #306 falls back to the user's own). Customer events map through `billing_customers.organization_id`. Low-credit and failed-payment notices go to the organization's admins.

- **Packs and plans.** `packs` lists only packs with a configured `stripe_price_id`. `POST /v1/billing/subscribe` with a live subscription is 409 `BILLING.ALREADY_SUBSCRIBED`. The portal keeps cancellation, cards and invoices, and its plan switch is off (#417). `scheduled_plan_id` is a downgrade that starts at `current_period_end`. `cancel_at` (#538) is when a cancelled plan ends, `null` while it renews: Stripe sets it for a cancellation at the end of the period and for one in the portal, which in flexible billing mode leaves `cancel_at_period_end` false, so the subscription no longer returns `cancel_at_period_end`. Every organization admin can open the portal, including pack-only organizations. Checkout: 404 `BILLING.UNKNOWN_PACK`, 502 `BILLING.CHECKOUT_FAILED`, 409 `BILLING.PROFILE_REQUIRED` without a complete billing profile.
- **`POST /v1/billing/plan {plan_id}`** (#417) changes the live plan. `result` is `upgraded` (to a dearer plan: it starts at once, one invoice charges the full difference between the plan prices plus VAT on any day of the period, the renewal date does not change and the renewal charges the new price); `payment_required` (the upgrade invoice needs the user, such as a declined card or 3-D Secure: `payment_url` is Stripe's page to pay it, the plan changes only once it is paid, and a second request meanwhile returns the same invoice); `downgrade_scheduled` (to a cheaper plan: it starts at the renewal through a Stripe subscription schedule and sets `scheduled_plan_id`, which the subscription webhook clears when the plan reaches it or the subscription has no schedule; nothing is charged or granted now); `downgrade_canceled` (`plan_id` equals the current plan while a downgrade is scheduled). Any change replaces a scheduled downgrade. `payment_url` is `null` except for `payment_required`. Credits follow the paid invoice through the webhook: an upgrade tops the period's allowance up to the new plan (new plan credits minus the plan credits granted this period; purchased credits do not change), once per invoice, and only when the invoice charged at least the price difference (a prorated switch grants nothing, logged `stripe.plan.upgrade_underpaid`). The renewal expires the unused plan credits and grants the plan's full allowance. Errors: 404 `BILLING.UNKNOWN_PLAN`; 409 `BILLING.NO_SUBSCRIPTION`, `BILLING.SAME_PLAN`, `BILLING.PLAN_CHANGE_UNAVAILABLE` (judged on Stripe's subscription: not `active`, cancelled (`cancel_at_period_end` or `cancel_at`), its latest invoice is `draft` or `open` or is a period's invoice the webhook has not credited yet, or it is on a price not in `BILLING_PLANS`); 502 `BILLING.PLAN_CHANGE_FAILED`.
- **`POST /v1/billing/stripe-webhook`** (Stripe signature). 400 for an invalid signature, 500 so that Stripe retries. The answer is `{received: true, result: processed|duplicate}`. It handles `checkout.session.completed` (a pack purchase credits `type='purchase'`; `mode=setup` with `metadata.kind=auto_topup` saves the card and switches auto top-up on; `mode=subscription` credits nothing, because credits come with `invoice.paid`), `checkout.session.async_payment_succeeded`, `invoice.paid` (plan period credits, upgrade top-up, auto top-up invoices), `customer.subscription.created|updated|deleted`, `invoice_payment.paid` (stored only, to map a refund to its invoice) and `charge.refunded` (only `purchases.refunded_cents` and a log; **no automatic credit reversal**).
- **Auto top-up** (#94, JWT only). Turning it on with no saved card on the Stripe customer saves `enabled=false` and returns a Checkout `mode=setup` URL in `setup_url` (back to `WEB_ORIGIN/billing?autotopup=saved|cancel`), and its `checkout.session.completed` switches it on. Thresholds are 100, 250, 500 and 1000. 404 `BILLING.UNKNOWN_PACK`, 422 `BILLING.INVALID_THRESHOLD`, 502 `BILLING.CHECKOUT_FAILED`, 409 `BILLING.PROFILE_REQUIRED` when enabling without a complete billing profile. The worker task `on_balance_changed(org_id, refused)` (#243) is queued after every committed balance change, every auto top-up save and every hold refused for lack of credits. It charges an organization whose balance net of open holds (`credits_remaining` plus the wallet's `reservation` rows still `reserved` or `settling`) is below `threshold`, so a hold that is later refunded never charges. After a refused hold it compares the available `credits_remaining` instead (a long job's holds can empty it while the net stays above). One charge at a time per wallet, no daily cap: an off-session Stripe invoice (Stripe Tax, `metadata.kind=auto_topup`) for the pack's price, credited `type='purchase'`, `reference_type='stripe_auto_topup'` once per invoice (the charge and `invoice.paid` share `purchases.stripe_invoice_id`). A failed charge (Stripe error, timeout, any exception) discards the unpaid invoice and sets `enabled=false` and `last_error` (an error code). Only the charge holding the claim releases it, and a card-setup Checkout switches it on only if the user did not save it off meanwhile. Pack checkouts save the card (`setup_future_usage=off_session`).
- **Transactions.** A hard bounce's credit back is `type='refund'`, `reference_type='email_bounce'` (#747, see Bounces). It names the campaign's project, and `project_month_spend` subtracts it (never below 0), so the email no longer counts against the project's monthly cap. `session_id` is the chat the credits were spent in and `list_id` the list of an AI column fill (`reference_type='ai_column'`). Each is `null` when the row names none, names one outside the caller's organization or, for a list, one in the trash. The web links them to `/?s=<session_id>` and `/lists/<list_id>`.
- **Invoices** (`GET /v1/billing/invoices?limit=20&starting_after=in_…`; session JWT only; the shared `require_org_admin` guard on every request). Members get 403 `AUTH.ORG_ADMIN_ONLY`; removed members and callers outside the active organization get 401 `AUTH.NOT_A_MEMBER`; global admin status does not override organization membership. The caller cannot supply a customer id: the customer comes only from `billing_customers.organization_id`, with the lookup checkout and portal use. `limit` is 1-100. A cursor must belong to the organization's Stripe customer, else 400 `BILLING.INVALID_CURSOR`. Amounts use Stripe's currency minor units, not always cents. `tax_amount` is total minus total excluding tax, and unknown `net_amount` and `tax_amount` are `null`. Drafts have no document links. `next_cursor` is passed back as `starting_after` and pagination is independent of ledger `offset`. An organization with no customer gets an empty page without a Stripe call. Missing Stripe configuration is 503 and a Stripe failure is 502, both `BILLING.INVOICES_UNAVAILABLE`. These are Stripe payment documents, not SDI delivery evidence or credit-note and refund reconciliation.
- **Fiscal billing profile** (`GET` and `PUT /v1/billing/profile`; session JWT and live admin membership). The `billing_profiles` row belongs to `organization_id`, so every admin of the organization sees and edits the same profile. `sync_status` is `local` (no Stripe customer yet, saved only), `pending` or `synced`. Country is an ISO alpha-2 code. Italian addresses need a recognized province and a five-digit CAP; US and Canadian addresses need state or province and postal code; other countries may omit postal codes. Individuals need a fiscal identifier, foreign customers too (Italian CF is the 16-character structure or 11 digits), and individual profiles clear business Tax ID fields. Businesses need a native Stripe Tax ID type supported for their country, from `countries` (derived from the installed Stripe SDK), and a value. EU VAT normalises whitespace and separators and checks the country prefix (`EL` for Greece; `XI` for Northern Ireland with `eu_vat`), and Italian VAT needs eleven digits. Other native identifiers keep their punctuation. This is format and type validation, not VIES or identity verification. A country with no supported business ID cannot complete this profile for a business; individual purchases still work. PEC is optional local contact data: A-Cube's Stripe connector does not deliver to PEC. Checkout and enabling auto top-up return 409 `BILLING.PROFILE_REQUIRED` until a complete profile exists. Disabling top-up, the portal and invoice history stay available. Validation errors are sanitised 422 `BILLING.PROFILE_INVALID`, with no echoed inputs or raw provider messages. Edits to an existing Stripe customer sync before success. A provider failure commits `pending`, disables enabled or awaiting-card auto top-up, and returns 502 `BILLING.PROFILE_SYNC_FAILED`; the user saves again, then re-enables top-up. Checkout and card setup sync the saved profile first and fail the same way. A per-organization transaction advisory lock serialises profile saves, Checkout and card-setup creation, and top-up configuration saves. The sync updates native name, email and address, replaces stale native business Tax IDs (an identical ID is kept), clears all Tax IDs on individual profiles, and patches only the `fiscal_code` metadata (individuals; cleared for businesses) and `codice_destinatario` (a given seven-character Italian recipient code, else `0000000` for Italy and `XXXXXXX` abroad). Other metadata is kept and no PEC metadata is invented. Checkout uses the saved fields, disables extra Tax ID collection and omits automatic customer name and address overwrite. Stripe Tax (`automatic_tax.enabled=true`) computes tax, and no flat foreign VAT rate or invented `tax_exempt` or reverse-charge flag is set. Stripe customer changes and external renewal or payment jobs cannot share a database transaction, so a charge in flight or a Stripe-managed renewal may overlap a partial provider update. A failure disables future local top-ups but does not cancel external subscriptions or claim atomic SDI issuance. A-Cube activation, issuer configuration and SDI delivery are separate provider work.

## Back office

Routes under `/v1/admin` use `require_admin`. Costs are in USD, revenue in EUR, `margin_eur = revenue_eur − cost_usd × eur_per_usd`. Dates are `YYYY-MM-DD` in UTC, `to` inclusive, default the last 30 days.

- **Costs.** `credits_spent` is the committed deductions net of refunded slack, excluding admin adjustments and plan expiry. `revenue` is net of refunds. `by_provider` is the hit rate per contact provider, from `contact_lookups`. `users` sorts by `cost_usd` descending, and a `null` `user_id` means vendor calls with no user. `daily` has one element per day, empty days included, and has no `credits_purchased`.
- **Credits.** The amount is a non-zero integer within ±1e9 (else 422, #393; 422 `ADMIN.ZERO_AMOUNT`). A positive amount calls `increment_credits(type='adjustment')`, a negative one `deduct_credits`, both with `reference_type='admin'`, `reference_id=<admin id>` and `description=reason`. 404 for an unknown user, 409 `ADMIN.INSUFFICIENT_CREDITS`. The organization route (#327) does the same on that wallet, with `user_id` the organization's oldest admin, never the back-office admin; 404 `ADMIN.NOT_FOUND`, 409 `ADMIN.ORG_HAS_NO_MEMBERS` (#323).
- **User usage and overview.** `company` is the `company_name` of the business profile of the user's own organization's default (oldest) project, never a client project's (#307, #352). `subscription` is the live plan of the user's own organization. In `users/overview` (200 ids at most) `balance`, `plan_id` and `has_purchases` come from the user's own organization (slug = their id), never from a team they belong to (#682); a user with no own organization gets `null`, `null` and `false`. `last_active_at` is the latest Better Auth session update. `ledger` and `purchases` in the usage are the user's own, in every organization they spent or bought in, so they can differ from the overview's `has_purchases`. `ledger` holds the latest 100 movements, `ledger_total` all of them.
- **Organizations** (#327). `q` matches the name, the slug or a member's email as a literal substring (`%` and `_` are not wildcards, #323). The user usage also carries `organizations`, their own first.
- **Badges.** `jobs_attention` counts `failed` or `needs_input` jobs created in the last 24 hours (#352). `switches_on` counts settings that are `true`.
- **Chat sessions** (#352). `companies` and `people` are the non-excluded rows of the chat's lists that are not deleted. `credits_spent` is the sum of `jobs.credits_spent`, net of refunds. `outcome` is `results` with at least one row, else from the last job: `stuck` if `failed` or `needs_input`, `no_results` if `succeeded` or `cancelled`, `null` with no job or a running one. The detail's `tool_calls[]` is `AdminToolCallRecord`, the same record as the chat route plus `vendors?` (the providers the call used, in order, deduplicated, collected by `record_vendor_call`; absent on older messages and on calls without a vendor). `credits_returned` is the sum of `jobs.result.refunded` (gross spent is net plus returned; 0 for older jobs). `vendor_calls` has no session or job id, so the vendor cost counts the user's calls inside the `started_at`–`finished_at` window of a job of the session. Estimated revenue is credits times the user's average price paid (purchases net of refunds divided by credits purchased), and `revenue_eur`, `margin_eur` and `eur_per_1000_credits` are `null` without purchases.
- **Jobs.** Each item carries every `jobs` column plus `email` and `brief` (the user message that started the turn). `result` of a finished turn also carries `refunded` and `undelivered`, and `stages[]` carry `started_at` and `finished_at` (#352; absent on older jobs). `first_row_at` is when the turn saved its first row, `null` before it. `counts` ignores `status` but respects `user_id` and `job_id`. `job_id` finds a job whatever its age.
- **Settings.** `PUT` sets a value (JSON; `null` deletes the key). `POST` (#338) adds a key set to `false`: 422 `ADMIN.INVALID_SETTING_KEY` unless it is `vendor_disabled:<name>` or `channel_disabled:<name>` (`[a-z0-9_-]+`), 409 `ADMIN.SETTING_EXISTS` when it exists (use `PUT`). `vendor_errors` counts `vendor_calls` with `success = false` in the last 24 hours per vendor, most frequent first (#352). Kill switches are `vendor_disabled:<provider>` and `channel_disabled:<channel>` set to `true`.
- Users, roles, bans and impersonation belong to Better Auth in the web. The Python API only has the hooks `before-delete` and `after-ban`.

## Saved views

`/v1/saved-views` (JWT or `sbk_` key, active project). A saved view (#827) is a name for the filters the list page applies: `tab` (`all`, `delivered`, `pending`, `no_contact` or `excluded`), `query`, the search text (200 characters at most), and `min_fit`, the fit floor: an integer from 0 to 100, or null for no fit filter. `min_fit` follows the rule of `GET /v1/lists/{id}/rows?min_fit=N`: a row is in when its `relevance_score` is at least `min_fit`, and an unscored row is out. The web opens one at `/lists/<list_id>?tab=<tab>&q=<query>&fit=<min_fit>` and leaves out `fit` when `min_fit` is null. A view belongs to the project and to one list; it goes with the list. A view of a soft-deleted list is neither listed nor counted.

- `GET` returns `{views}`, newest first, each `{id, name, list_id, list_name, tab, query, min_fit, created_at}`.
- `POST {list_id, name, tab?, query?, min_fit?}` returns the view (201). `min_fit` defaults to null. A `min_fit` outside 0 to 100 is 422, and so is one that is not a JSON integer: a string, a boolean, or a number with a decimal point such as `80.0`. `name` is trimmed, 1 to 100 characters (422 otherwise). A list that is not in the active project is 404 `LIST.NOT_FOUND`; at 200 views per project, 409 `SAVED_VIEW.LIMIT`.
- `PATCH /{id} {name}` renames and returns the view. `DELETE /{id}` is 204. A view of another project or organization is 404 `SAVED_VIEW.NOT_FOUND`.

## Saved searches

`/v1/saved-searches` (JWT or `sbk_` key). A search runs one deterministic search call (`search_people` or `search_companies`) with no chat or LLM turn, and `budget_credits_per_run` is exactly 1 credit (Zenbree accounting, not the vendor's USD cost). There is no scheduled email enrichment and no outbound send. The chat tools `schedule_check`, `list_schedules` and `cancel_schedule` use the same service. A saved search, its run and a watchlist carry `organization_id`, the organization of its list.

- `POST` needs `name`, `tool_name`, bounded `tool_input` and the matching owned `list_id`. `cadence` is `daily` or `weekly` (default). `next_run_at` is an offset-aware timestamp stored in UTC. Missed slots coalesce into one run, and manual runs leave the schedule alone. Ten undeleted searches per user at most (409 `SAVED_SEARCH.CAP_REACHED`). `PUT` replaces the configuration (409 `SAVED_SEARCH.RUN_IN_PROGRESS` while a run is queued or running), `PATCH {"enabled": false}` pauses, `DELETE` soft-deletes, `POST /{id}/run` queues one run (202; returns the one already queued or running, if any; 409 `SAVED_SEARCH.PAUSED` while paused). A list or campaign that is not the creator's is 404 `LIST.NOT_FOUND` / `CAMPAIGN.NOT_FOUND`, and so is a campaign of another project than the list's (#1086: a project is a client). A run of a search saved before that check enrolls nobody into such a campaign. Its found rows stay in the list. `GET /{id}/runs` returns the latest 100. Timestamps end in `Z` like every other route (before #369 these routes sent `+00:00`).
- **Sharing** (#323). `GET` lists every member's searches whose list is in the caller's active organization, and `GET /{id}/runs` reads any of them. Changing one (`PUT`, `PATCH`, `DELETE`, `POST /{id}/run`) is for whoever saved it or an admin; any other member gets 403 `SAVED_SEARCH.NOT_OWNER`. An admin's edit or manual run keeps the search its creator's: runs spend as the creator, from the creator's list and campaign (`saved_searches.user_id` does not change), and fail closed once the creator has left the list's organization. Cross-organization resources are 404 (`SAVED_SEARCH.NOT_FOUND` for the search).
- **Refill** (person searches with an optional owned `campaign_id`). New identifiable people become campaign targets with `status=active` (the refill runs only on an `active` campaign, so the dispatcher contacts them), `source=refill`, deduplicated by email or LinkedIn identity, at most 1000 targets in the campaign: a person past the cap stays in the list only, the refill is done, and a campaign already full skips the run's refill (a running campaign never frees room). A missing email stays missing: an email step skips that person. Rows with neither identity are skipped. A row with a per-row charge still pending (#462: its hold is still `reserved`) is held like a duplicate: it stays in the pending ids and enrolls with the cells its turn kept once that turn settles. Excluded list rows and excluded or replied campaign targets are never revived. Paused or draft campaigns keep the pending ids for a later free refill, and active-campaign duplicate holds are retried fairly. Stopped or completed campaigns discard pending refill. Existing occurrences keep their original list and campaign configuration when a search is edited, and pending refill follows that snapshot.
- **Execution.** Beat runs once a minute (`dispatch_saved_searches`). The database occurrence and worker claim prevent duplicate paid executions. Rows, the occurrence result and credit settlement commit together. `search_people` and `search_companies` are free, so a run holds no credits and runs with an empty wallet or a project at its hard cap, but it counts against the organization's 1000 free rows of the day like a chat search (`app/agent/free_rows.py`): past them the run fails `over_budget` before any vendor call, and the run settles the rows it returned; before 2026-10-14 it held 1 credit and failed `insufficient_credits` or `project_cap_reached`. A search tool with a `Price` holds its quote at the claim. A quote above 1 credit fails the run `tool_contract_changed` before any hold or call. Such a run stores its found rows up to the quote, writes one `row_charges` record for each one that lands new, and closes its hold in the same transaction. Broker failures leave durable queued work. A crashed worker's uncertain run is marked `unknown`, refunded if still held, and never replayed automatically; a later scheduled occurrence or an explicit run is a new execution. An empty or failed result refunds the hold. Pause or delete stops the next call and the result and refill publication, but an in-flight provider request cannot be recalled. A late result whose hold expired is discarded. A run runs as its creator: the beat queues none for a creator who is not a live member of the search's organization, and a run queued before the creator left fails `creator_left` (banned: `cancelled` `user_banned`, and the search resumes when the ban ends; deleted account: `cancelled` `creator_deleted`), before any hold. A creator who leaves mid-run gets nothing written, and the hold goes back. `Run.status` is `queued|running|succeeded|failed|cancelled|unknown`, and `error_code` is a fixed code, never a vendor exception or credentials.

## Segments

`/v1/segments` (JWT or `sbk_` key, active project; #938). A segment is a saved rule over the people (`entity: person`) or the accounts (`company`) of the project. A published segment keeps its members: the identities (see Audience identity) that match the rule. A draft has a rule and no members. Evaluation runs on request (publish, refresh, a rule edit) and after each change of the data it reads. Each change of membership is recorded, and an entry is the event automations read (#1029).

- **Rule.** A `group` (`op: and | or`, 1 to 20 `children`) of conditions and groups, 3 groups deep at most, 20 conditions in all. A field is `{kind: canonical, key}`, a key of the entity's canonical fields that means the same in every list (vendor plumbing such as `source` is not one), or `{kind: column, list_id, key}`, one column of one list of the project (an AI column's key means something only in its list). Conditions: `text` (`eq`, `neq`, `contains`, `not_contains`, one value; `in`, `not_in`, 1 to 50 values; compared trimmed and case-blind), `number` (`gt`/`gte` take `low`, `lt`/`lte` take `high`, `between` both; a cell that is not a plain number, such as `51-200`, never matches), `fit` (the best `relevance_score` of the person's rows, 0 to 100; `gte`, `lte`, `between`, `is_missing`, `is_filled`), `presence` (`is_missing`, `is_filled`) and `in_list` (`in_list`, `not_in_list`). There is no NOT group.
- **Judged per identity.** A condition reads every row of the identity in the project's live lists of the entity, excluded rows left out, and a column field only the rows of its list. A positive operator matches when any row matches. A negative one (`neq`, `not_contains`, `not_in`, `not_in_list`) matches when a row has the field and no row matches the positive form, so an unknown value never matches by negation. A cell whose fill failed is missing. A row with no identity yet is in no segment. A cell still under a held per-row charge is unknown: an identity with one such row neither joins nor exits until the charge settles.
- **Membership.** `segment_members` holds one record per segment and identity, with the representative row (the best fit, then the oldest row), `entered_at`, `exited_at` and `episode` (1 at the first join, +1 at each join after an exit, never reused). An evaluation writes only what changed and runs under the project's lock, so two at once give the result of one, and running it again writes nothing. It reads cells only: no vendor call and no credit.
- **Transitions.** `segment_transitions` records each change of membership, append-only, ordered by `seq`: a join is `enter` (an entry event) or `baseline` (a silent join), a leave is `exit`, and a merge is `merged`. A join that a user action causes asks first: the people who match at the first publish are entries only with `include_current: true`, and the people a rule edit adds only with `include_new: true`; with no answer they join as `baseline`. A join that a change in the data causes (a refresh, or publishing a published segment again) is always `enter`. A rule edit of a published segment judges the old rule and the new rule in one statement, so a change that commits while the edit runs falls on the same side of both. A join that the old rule also makes is the data's: an `enter` at the old version, outside `joining`. An exit that the old rule also makes is outside `leaving`. Only the joins that the new rule alone makes take the answer. A person whom the data and the edit move in opposite directions keeps their membership, with no record. A frozen rule (see Problems) judges nobody, so the edit that fixes it cannot tell a join the data caused while it was frozen from one the new rule causes: its answer decides every join it makes. When a merge of identities (see Audience identity) folds a member into another identity, the membership follows `audience_live()`: the folded identity's record closes with `exit`, the identity left standing is a member with the higher of the two episodes and a `merged` record, and no entry is written. A later join after an exit takes that episode + 1. The members that joined before transitions existed have one `baseline` record each, at their episode.
- `POST /preview {entity, rule}` returns `{count, pending, unidentified_rows, linking_rows, sample}`: the identities that match now, those deferred by a held charge, the rows with no identity and the rows waiting to link (`audience_link_queue`), and up to 25 matches with their representative row. With `segment_id` (`{entity, rule, segment_id}`), it also returns `joining`, `leaving` and `max_credits`: what `PATCH /{id}` of that segment to this rule would answer now, with no write (0, 0 and 0 for a draft). Without `segment_id` they are `null`. A segment of another project or organization answers 404 `SEGMENT.NOT_FOUND`, and an `entity` that is not the segment's answers 422 `SEGMENT.INVALID_RULE` with `reason` `entity_mismatch`.
- `GET` lists the project's segments, newest first. `POST {name, entity, rule}` returns the draft (201). `GET /{id}`, `PATCH /{id} {version, name?, rule?, include_new?}` returns `{segment, joining, leaving, max_credits}` (a new rule of a published segment applies at once: `joining` people join, `leaving` people exit, both counting the edit's change only, not the data's change since the last evaluation, and `max_credits` is as for publish, for the people joining; a draft or a rename has 0 and 0; 409 `SEGMENT.STALE_VERSION` with the current `version` when another edit came first) and `DELETE /{id}` (204, soft). A segment carries `version`, `members` (the live count) and `problems`.
- `POST /{id}/publish {include_current?}` starts membership and returns `{segment, applied: {joined, entered, exited, merged, members}, max_credits}`; publishing again refreshes. `max_credits` is the most the automations that read the segment can spend if every person who joined entered (`app.segments.cost.max_entry_credits`). It is 0 until #1029 replaces that function's body with the sum of `max_credits` from `app/automations/preview.py` over the automations that use the segment. `POST /{id}/refresh` evaluates again (409 `SEGMENT.NOT_PUBLISHED` on a draft). `GET /{id}/members?after=&limit=` pages the live members by identity id, 50 by default and 200 at most; pass `next_cursor` as `after` until it is `null` (409 `SEGMENT.NOT_PUBLISHED` on a draft). `GET /{id}/members/{identity_id}/why` returns how the rule judges that identity now, node by node, with each row that has the field and whether it matched. A row of a condition on a `field` also carries the cell's `value` and its fill record from `cell_meta[key]`: `at`, `status` and `source`, which is `{url, title}` for an AI fill and `null` otherwise. A row of a fit condition carries `relevance_score`. It also returns the segment's `problems`: when there are any, the segment is frozen, so `member` can differ from `matches`, which judges a rule that names a deleted list or column.
- **Event `segment.entered`.** An entry is a `segment_transitions` record of kind `enter`, read by pull, never pushed: `app.segments.entries.entries_after(conn, segment_id, after_seq, limit)` returns the entries after the cursor in `seq` order (none once the segment is deleted), each `{seq, segment_id, project_id, identity_id, entity, episode, list_row_id, segment_version, entered_at}`. `list_row_id` is the representative row at the entry, for display only, and `null` once that row is deleted. Pass the last `seq` back as the cursor. Every writer holds the project's lock, so `seq` commits in order inside a project and a cursor never skips an entry. `baseline`, `exit` and `merged` records are history, not events.
  - The idempotency key is `(segment_id, identity_id, episode)`: the database refuses a second `enter` or `baseline` with the same key. A person who exits and joins again is a new entry, with the next episode.
  - A consumer (#1029) runs a person at most once for each automation: it dedupes on `(automation_id, identity_id)` with the identity taken through `audience_live()`, never on the row, because the representative row can change and a merge moves a person to another identity.
  - The consumer resolves the identity to a row of its own list through `audience_row_links`. When that list has no row of the person, it drops the entry with the reason `not_in_list`, as a delivery is dropped.
  - An automation reads only the entries after the `seq` it saw when it attached: entries made before are never replayed. Whether it also runs for the current members is its own question, which reads `segment_members`.
- **Updates after a data change.** A write that can change who matches leaves a mark in `segment_dirty`, from statement-level triggers: a `list_rows` update of `cells`, `cell_meta`, `relevance_score`, `excluded` or `list_id`, a new, moved or deleted `audience_row_links` row (also a merge of identities), and a change of `lists.deleted_at`. A project with no published segment gets no marks. The beat `evaluate_segments` (every 30 s, `app.segments.drain`) judges the marked people again for every published segment of the project, 500 at a time, and records each join as `enter`. A person whose cell is under a held charge keeps a mark and is judged again after 60 s. Above 5,000 marks in a project, the beat runs one full evaluation of each segment instead, which leaves a catch-up below still owed. The marks of held people judged again do not count toward the 5,000. The beat works the projects of an organization oldest mark first. A frozen segment (see Problems), or one whose evaluation fails, is skipped and owes one full evaluation 5 minutes later, retried until it runs. A later batch that fails it again does not move that time later. In the beat, each statement of an evaluation runs at most the time left until 10 s after the 35 s budget, counted when the evaluation starts. A statement that runs longer is cancelled and the evaluation counts as a failure, so one slow statement does not reach the task's 50 s soft limit, which rolls the whole beat back. A failure logs `segments.drain.segment_failed`, and the other segments go on. A publish and a rule edit of a published segment set `full_due_at` 20 minutes later, and the beat then runs one more full evaluation of that segment, which joins a write that committed after the first one read the rows. A person enters about one beat after the write commits.
- **Pause.** The admin setting `segments_evaluation_paused` (`PUT /v1/admin/settings`, off by default) stops the beat. The marks and the owed full evaluations wait and run when the setting is off again. While it is on, `POST /preview`, `POST /{id}/publish`, `POST /{id}/refresh` and a `PATCH` that changes the rule of a published segment return 503 `SEGMENT.EVALUATION_PAUSED`. A rename, a draft edit and the reads still work, `why` included: it judges one person and writes nothing.
- **Problems.** A rule names lists and columns that can be deleted later. A saved segment that names one has `problems: [{path, reason, list_id, key}]` (`list_not_found`, `column_not_found`) and is frozen: an evaluation writes nothing and the members stay until an edit fixes the rule, or until the beat's next full evaluation after the list or column is restored.
- **Errors.** 404 `SEGMENT.NOT_FOUND` (a segment of another project or organization too) and `SEGMENT.IDENTITY_NOT_FOUND` (`why` for an identity outside the project or the entity). 422 `SEGMENT.INVALID_RULE` with `path`, the JSON pointer of the node in the rule, and `reason` (pydantic's error type, or `too_deep`, `too_many_conditions`, `unknown_field`, `list_not_found`, `column_not_found`, `entity_mismatch`). 409 `SEGMENT.LIMIT_REACHED` at 50 segments per project, `SEGMENT.STALE_VERSION` and `SEGMENT.NOT_PUBLISHED`. 503 `SEGMENT.EVALUATION_PAUSED` while an admin pauses member updates.

## Watchlists and signals

`/v1/watchlists` (JWT or `sbk_` key; E13.3, #647). A watchlist watches the accounts of a company list for a kind of change, on a cadence, and records each change once as a signal. The first signal type is `job_posting`: a new open posting in one of the watched functions, read from Apollo job postings. Job changes and promotions are not built. A signal can add the account's people to a campaign (#648, below); writing signals to HubSpot is #529.

- **Watchlist.** `POST` needs `name`, the `list_id` of a company list of the active project (any company list, a CSV import included; 404 `WATCHLIST.LIST_NOT_FOUND` otherwise) and `job_titles` (1 to 20; trimmed, duplicates dropped). `cadence` is `daily` or `weekly` (default); the first run is due at once. Ten watchlists per project at most (409 `WATCHLIST.LIMIT`). `PATCH` changes `name`, `job_titles`, `cadence`, `enabled` or the campaign pair; `enabled: false` pauses and cancels a queued run. `DELETE` removes the watchlist with its runs and signals. `POST /{id}/run` queues one run (202; the live one when there is one; 409 `WATCHLIST.PAUSED`). `GET` lists the project's watchlists with `accounts` (rows of the list not excluded), `signals` and `last_run`.
- **Sharing.** As for saved searches: every member of the organization reads a watchlist, its runs and its signals; changing or running it is for whoever made it or an admin (403 `WATCHLIST.FORBIDDEN`). A watchlist of another organization or project is 404 `WATCHLIST.NOT_FOUND`. Runs spend as the creator. While the creator is not a live member (left, banned, or deleted the account), the beat queues none: the watchlist waits, and a return or the end of a ban resumes it. A run queued before the creator left fails `creator_left` (banned: `cancelled` `user_banned`; deleted account: `cancelled` `creator_deleted`), before any hold.
- **A run** (`GET /{id}/runs`, latest 100; beat `dispatch_watchlists` once a minute, task `run_watchlist`). It takes the accounts checked longest ago first, up to 300, and holds `min(100, accounts)` credits. For each account it reads the open postings: the account is the row's `apollo_id`, else it is resolved once from its `domain`. An account with no domain (`no_domain`) or one Apollo does not know (`not_found`) is skipped and goes to the back. The run stops when 100 accounts with postings were read: 1 credit per account that has any posting, nothing for the others. Accounts it did not reach are first in the next run (`accounts_left`: the list's accounts less the ones this run read or skipped). Signals, the rotation, one `row_charges` record for each account with postings that is still on the list, the close of the hold and the run's status commit together. The run never stores or bills an account past its quote: the accounts after the one that fills it stay unchecked, first in the next run. An account deleted during the run is not billed. A vendor failure ends the run `failed` (`vendor_failed`) with what it read kept and charged, and the account it failed on goes to the back like a skipped one; `vendor_disabled:apollo` or a missing key fails it before any call (`vendor_disabled`, `vendor_not_configured`) and charges nothing. Without credits it fails with `insufficient_credits` or `project_cap_reached`. A worker that died leaves the run `unknown` (`worker_outcome_unknown`) with the hold released and nothing written.
- **Signals** (`GET /{id}/signals`, strongest first, 500 at most). One per posting, account and watchlist: a posting is the same when its link is, or its title and place when it has no link, so a later run records nothing for it. Fields: `type`, `row_id`, `account_name`, `account_domain`, `title`, `city`, `country`, `url`, `occurred_at` (when the posting went up, or when it was first seen if Apollo does not say), `first_seen_at` and `score`. A posting starts at 100 and the score halves every 30 days from `occurred_at` (SQL `signal_score`), so the first run of a watchlist records the postings already open with the score of their age.
- **Signal to campaign** (#648). `campaign_id` and `campaign_threshold` (> 0) on `POST`/`PATCH` go together (422 otherwise; `PATCH` with both `null` stops it, 422 `WATCHLIST.CAMPAIGN_PAIR` when only one is sent). The campaign must be an unfinished one of the active project (404 `WATCHLIST.CAMPAIGN_NOT_FOUND`); a deleted campaign clears the pair's campaign. At the end of each run (`app.watchlists.enroll`), for each account whose unconsumed signals have a summed live score (`signal_score`) at or over the threshold, the people of that account already in a person list of the project (not excluded, delivered; matched domain to domain, else by company name, as `people_count`) enter the campaign with `source = 'signal'`, through `enroll_rows` (exclusions, existing targets, replied or contacted before, `block_active_duplicates`; at most 1000 targets). No search, no credits. They enter as `draft` in a draft campaign (activation makes them active) and as `active` in an active or paused one, so the campaign contacts them (a paused one when it resumes). Their values freeze then (#933): one with no value for a required field waits as `draft`. A stopped or completed campaign receives nobody. The link is re-read under a lock in the enrolling transaction: a `PATCH` that cleared or moved it before that commit stops the run, so nobody enters through the old link. The account's signals are then consumed (`signals.enrolled_at`, set in the same transaction), so nobody enters twice for the same signal whatever is retried; a later posting is a new signal. An account with no known person keeps its signals and is counted in the run's `accounts_without_people`; a person who joins a list later enters on the next run. A person left out by a rule (`excluded`, `duplicate`, `no_contact`, `stopped`) is not retried for that signal. When nobody of an account was enrolled and some were left out for want of room (`over_limit`) or because they are in another active campaign (`in_other_campaign`) or held by Instantly (`held_by_instantly`), its signals stay unconsumed and the next run tries again. The run carries `people_enrolled`, `accounts_without_people` and `people_left_out` (everyone kept out, whatever the reason). `GET /v1/campaigns/{id}/targets` adds `signal_title`: the posting title of the signal that enrolled the person (the strongest of the account), `null` for anyone else; the web shows it under the person's name.

## Automations

`/v1/automations` (JWT or `sbk_` key; #939). An automation is a stored, ordered definition that a manual run, a schedule, a signed webhook call or the signals of a watchlist start, through the durable run model of saved searches and watchlists. It belongs to the active project. Every member of the organization sees it; its creator or an admin of the organization changes it (403 `AUTOMATION.FORBIDDEN`). Runs spend and write as the creator. HubSpot and segment triggers are **Not done (decision: later)**: the trigger is `{kind: manual}`, `{kind: schedule, cadence: daily|weekly}`, `{kind: webhook}` or `{kind: signal, watchlist_id, min_score}` (see **Signal**). A trigger without `kind` is manual, and manual and webhook also accept `cadence: null`. Any other field is 422 `REQUEST.INVALID_INPUT`.

- **Definition.** `{list_id, steps}`: `list_id` is a person list of the project that the automation works on. `steps` run in this fixed order, each at most once: `find_people` (`accounts_list_id` of a company list, `titles`, optional `seniorities`, `per_account` 1 to 5; Apollo previews, free), `qualify` (`brief`, `min_score` 0 to 100; the model scores each person against this brief, 1 credit a person scored once for each version of the automation; the score is kept apart from the chat's `relevance_score`, which the step never reads or writes), `find_emails` (1 credit for each email found, as `enrich_email`), `add_to_campaign` (`campaign_id` of a campaign that has not ended), `add_to_instantly` (`campaign_id` of a campaign of the project's Instantly workspace; see **Instantly step**) and `write_hubspot` (the contact and its company, through the write-back of `app/crm/contacts.py`: only with write-back on and a grant that may write, never a person the read gate holds, and a person already in `crm_contact_writes` is not written twice). A definition has `add_to_campaign` or `add_to_instantly`, not both (422 `REQUEST.INVALID_INPUT`): one system owns a person's outreach. No step activates a campaign or buys a phone number, and no Zenbree step sends a message. Instantly sends to the people of an `add_to_instantly` step when its campaign is active. `credit_cap` is 1 to 100 credits for each run (the watchlist cap), set by the user.
- **Checks.** `POST` and `PATCH` check what the definition names, as the creator: 422 `AUTOMATION.CREATOR_GONE` (the creator deleted their account, left the organization or is banned: no run starts until a ban ends, so a member makes a new automation), `AUTOMATION.LIST_NOT_FOUND`, `AUTOMATION.ACCOUNTS_NOT_FOUND`, `AUTOMATION.CAMPAIGN_NOT_FOUND`, `AUTOMATION.HUBSPOT_OFF`, `AUTOMATION.INSTANTLY_NOT_CONNECTED` (the project has no connected Instantly workspace with a key). A signal trigger adds `AUTOMATION.WATCHLIST_NOT_FOUND`, `AUTOMATION.SIGNAL_ACCOUNTS_LIST` and `AUTOMATION.WATCHLIST_PAUSED` (see **Signal**). These read only the database: no check calls Instantly. An enabled automation is checked on every edit, and the run checks again at its claim (`invalid_configuration`). Ten automations for each project at most (409 `AUTOMATION.LIMIT`).
- **Preview.** `POST /v1/automations/preview` with `{definition, credit_cap, automation_id?, trigger?, trigger_kind?}` answers 200 with what a run of that definition would do now. It only reads: it writes no row, holds no credit and calls no vendor, model or HubSpot, so an unsaved definition creates nothing. The one exception is an `add_to_instantly` step with a connected workspace: the preview reads its campaign from Instantly once. `problems` lists every check of **Checks** that fails, in the order of the definition, as `{code, message}`. A save or an enable refuses on the first of them. The creator and HubSpot checks use the automation's creator when `automation_id` names one, else the caller: runs spend and write as the creator. `AUTOMATION.HUBSPOT_OFF` is not listed with `AUTOMATION.CREATOR_GONE`. Any member may preview an automation of the project. An `automation_id` of another project or organization answers 404 `AUTOMATION.NOT_FOUND`. `trigger` is the trigger the draft would save. `trigger_kind` (`manual`, `schedule` or `webhook`) names only its kind, and a body with both is 422 `REQUEST.INVALID_INPUT`. Without either, the preview uses the saved automation's trigger, else `manual`. `steps` repeats each step with `credits_each`, its price for each person it bills (`qualify` and `find_emails` 1, the others 0). `people` counts the rows of the person list that are not excluded and that the automation has not taken in yet. With `add_to_campaign` or `add_to_instantly`, `with_email` counts those with an address a campaign sends to (found and not `invalid`) and `with_contact` those with that address or a LinkedIn URL, which enrollment needs. With `find_people`, `accounts` counts the company list's rows that are not excluded. `campaign` is `{id, name, status}` of an `add_to_campaign` campaign that has not ended. When it is `active`, an approved run enrolls people as `active` and the campaign sends to them. `instantly` is `null` without an `add_to_instantly` step, else `{connected, campaign, unreadable}`. `connected` is false when `AUTOMATION.INSTANTLY_NOT_CONNECTED` is one of `problems`, and then nothing is read. `campaign` is `{id, name, status, may_send, url}` as Instantly has it now; when `may_send` is true, Instantly starts to send to the people of the batch on its own schedule once the batch adds them. Instantly answering that the campaign does not exist adds the problem `AUTOMATION.INSTANTLY_CAMPAIGN_NOT_FOUND`. It is a preview problem only: `POST` and `PATCH` do not read Instantly, and a run of that campaign fails with `instantly_campaign_not_found`. Any other failed read sets `unreadable` to the error code and is never one of `problems`: the run reads the campaign again. A code such as `INSTANTLY.UNKNOWN_OUTCOME` or `INSTANTLY.RATE_LIMITED` may pass then. The codes of the **Instantly step**'s permanent failures fail every run until they are fixed: `INTEGRATIONS.CRYPTO_FAILED` (connect Instantly again) and `INTEGRATIONS.NOT_CONFIGURED` (the server has no encryption key) fail it with `instantly_not_connected`, `INSTANTLY.INVALID_KEY`, `INSTANTLY.PLAN_REQUIRED`, `INSTANTLY.MISSING_SCOPE` and `INSTANTLY.REJECTED` with `instantly_refused`, and `INSTANTLY.DISABLED` with `vendor_disabled`. A count is `null` when no step uses it or its list is one of `problems`. The exclusions, opt-outs and campaign rules that a run applies to each person are not counted: the run's `summary` reports them. `signals` is `null` without a signal trigger or when its watchlist is one of `problems`, else `{accounts, recent}`: how many accounts of the watchlist have unused signals first seen in the last 30 days that reach `min_score` together, whatever `since` says, and the 5 of them with the newest signal as `{account_id, name, title, score, seen_at}` (`title` of the strongest signal, `score` the sum of the live scores, `seen_at` when the newest signal was first seen). An unsaved draft counts every signal as unused. `people_per_run` is 25, and 1 for a `webhook` trigger: a webhook run works on the one person its call named. `accounts_per_run` is 10: one run's `find_people` looks at that many companies of the list, the next run goes on from there, and starts again from the first company after the last one. It is 1 for a `signal` trigger. `max_credits` is `min(credit_cap, people_per_run × the sum of credits_each)`: the most one run spends, 0 for a definition with no paid step.
- **Versions.** `version` starts at 1; an edit of `definition` or `credit_cap` that changes it adds 1 and cancels a queued run (`automation_edited`). A run keeps the `version`, `definition` and `credit_cap` it was queued with. Changing the accounts list of `find_people` restarts that step from the first account.
- **Run.** `POST /{id}/run` answers 202 with the live run, or a new queued one; 409 `AUTOMATION.PAUSED` when the automation is disabled. The next minute's beat (`dispatch_automations`) hands it to `run_automation`. A schedule queues its run at `next_run_at` and moves to the next slot. `status`: `queued`, `running`, `succeeded`, `failed`, `cancelled`, `unknown` (the worker died: the hold is settled from the charges recorded). `GET /{id}/runs` lists runs; `GET /{id}/runs/{run_id}` adds `steps`. A step has `status` `pending`, `running`, `succeeded`, `skipped`, `failed` or `uncertain` (the worker died while it ran, so what it did outside our database is not known; it is never replayed by itself), a `decision`, `input` and `output` (counts, never a name, email or phone), `credits`, `attempts` and `error_code`. A step that failed before any charge or write is tried again, up to 3 attempts with a growing wait; a step that wrote outside our database (`write_hubspot`) is not. A cancel or a pause that lands while `write_hubspot` writes to HubSpot ends that step `succeeded`, with `output` counting the people it wrote, and the run `cancelled`. A step that wrote nobody is `skipped`.
- **Instantly step** (#1032). `add_to_instantly` reads the campaign from Instantly (free) and judges the run's people with the rule of an Instantly batch (**Who goes**). It reads the cells the run bought: the step makes the run's held charges final first, as the run's end does at the same price, so an email that `find_emails` found on a row that misses a required column counts. Its `output` is `{held, eligible, skipped: {reason: count}, campaign: {id, name, status, may_send}}`. The step makes no batch and calls no other Instantly route. A run that succeeds holds the people who would go, in the transaction that marks them taken (`automation_instantly`); a run that fails, is cancelled or dies holds nobody, and the next run takes them again. A run with nobody to send holds nothing. The hold becomes one Instantly batch (**Enrollment**, `created_by` the automation's creator, every field from its default column) when the run ends, or at its approval for a run in review. The batch judges every person again before it sends.
  - The batch waits while the run waits for its approval, the automation is paused, its creator left, the project's Instantly is not connected or is another workspace than the step read, or another batch of the project is live. The minute beat makes it once nothing blocks it. Each minute the beat takes up to 100 holds whose project has a usable connection to the workspace the step read and no live batch, the oldest hold of each project, so a hold that waits never delays another project. A hold whose people all left the list is dropped. A hold whose automation creator left waits (`creator_gone`): it makes no batch, and its people stay taken. Disconnecting Instantly (`DELETE /v1/integrations/instantly`) cancels the project's live batches, the automation batches too, and those people stay taken: the automation does not take them again (owner decision). The beat also sends again a queued batch nobody claimed for 2 minutes (its message was lost), and cancels a queued batch whose creator left, so it does not block the project's next batch.
  - `GET /{id}/runs/{run_id}` shows `instantly`: `null` when the run holds nobody for Instantly, else `{people, batch_id, waiting_for, campaign}`. `people` counts the people held, or the batch's leads once it is made. `waiting_for` is `null` once `batch_id` is set, else `approval`, `paused`, `creator_gone`, `connection`, `other_workspace`, `other_batch` or `starting` (nothing blocks it: the batch is made at once or by the next beat). The batch's own progress is `GET /v1/integrations/instantly/enrollments/{batch_id}`.
  - The step fails with `error_code` `instantly_campaign_not_found`, `instantly_not_connected` (also when the stored key cannot be decrypted: `INTEGRATIONS.CRYPTO_FAILED` or `INTEGRATIONS.NOT_CONFIGURED`), `instantly_refused` (a key Instantly refuses, a missing scope or plan) or `vendor_disabled`, with `output.instantly_error` the Instantly code, and is not tried again. `instantly_unreachable` (any other failed read) is tried again, up to 3 attempts.
- **Webhook** (#1031). A webhook automation starts one run for each signed call that names one person of its list. `POST /{id}/webhook/secret` (its creator or an admin) answers `{url, secret, rotated_at}` with `Cache-Control: no-store`. That is the only time the secret is shown. Each call makes a new secret, and the old one stops working at once; the URL stays. 409 `AUTOMATION.NOT_WEBHOOK` when the trigger is not `webhook`, 503 `AUTOMATION.WEBHOOK_UNAVAILABLE` when secrets cannot be stored. The automation shows `webhook` `{url, rotated_at, pending, waiting_for_approval}`, or `null` before its first secret; `url` is `null` while the API has no public base URL. The sender calls `POST /v1/automation-hooks/{hook_id}` with the Standard Webhooks headers `webhook-id` (1 to 200 characters, the idempotency key), `webhook-timestamp` (Unix seconds, within 5 minutes) and `webhook-signature` (`v1,` + base64 HMAC-SHA256 of `{id}.{timestamp}.{body}` with the base64 key after `whsec_`; several space-separated values are accepted). The body is a JSON object of at most 16 KiB with `email`, `linkedin_url` or both. Other fields are ignored, and nothing of the body is stored. The person is looked up in the automation's list (LinkedIn URL first, then email, then the audience identity that holds either), never created. 202 `{delivery_id}`: the next minute's beat starts the run when no run of the automation is live and no run waits for approval (`waiting_for_approval`: a review run of this version left drafts or held HubSpot people; approving it releases the queue). The run works on that one person only (`trigger_kind: webhook`); a row deleted since gives the run nobody. A call that repeats a stored `webhook-id` gets the stored answer and starts nothing. The answers:
  - 401 `AUTOMATION.WEBHOOK_UNAUTHORIZED`: a header is missing, the signature is wrong, the hook is unknown, or the trigger left `webhook`. 401 `AUTOMATION.WEBHOOK_STALE`: the timestamp is more than 5 minutes off. 413 `REQUEST.TOO_LARGE`. 429 `AUTOMATION.WEBHOOK_RATE_LIMITED` (over 60 calls a minute for the automation or 300 for the organization) and 429 `AUTOMATION.WEBHOOK_BACKLOG` (100 calls wait already), each with `Retry-After`. 503 `AUTOMATION.WEBHOOK_UNAVAILABLE`. These store nothing, so a retry with the same `webhook-id` can still succeed.
  - 409 `AUTOMATION.WEBHOOK_PAUSED` (the automation is disabled), 409 `AUTOMATION.WEBHOOK_NOT_ACCEPTING` (its creator deleted their account, left or was banned), 422 `AUTOMATION.WEBHOOK_INVALID_BODY` (not a JSON object, or a field that is not a string), 422 `AUTOMATION.WEBHOOK_NO_IDENTIFIER` (neither field), 422 `AUTOMATION.WEBHOOK_NO_MATCH` (nobody of the list), 409 `AUTOMATION.WEBHOOK_ALREADY_WORKED` (the automation took the person in, or a waiting call or the live run has them). These are stored: a replay gets the same answer.

  `GET /{id}/runs/{run_id}` of a webhook run shows `delivery` `{id, webhook_id, received_at, matched_by, row_id}`, never the email or the URL. A waiting call is dropped after 7 days, when the automation is paused, or when it leaves the webhook trigger. Leaving it also deletes the hook: a switch back makes a new URL and needs a new secret. Refused and dropped calls are deleted after 30 days. A cancelled, failed or dead run keeps its call, and the person can be called again. `find_people` is refused with a webhook trigger (422 `AUTOMATION.WEBHOOK_FIND_PEOPLE`, on every save and at the claim), and `POST /{id}/run` with 409 `AUTOMATION.WEBHOOK_TRIGGERED`.
- **Signal** (#1030). A signal automation starts one run for each account of its watchlist whose signals reach `min_score` (> 0, at most 10000). `watchlist_id` names a watchlist of the project (422 `AUTOMATION.WATCHLIST_NOT_FOUND` otherwise, on every save). The automation shows `signal` `{watchlist_id, watchlist_name, min_score, since}`, or `null` for another trigger. `since` is when the trigger became `signal`, the watchlist changed, or the automation was last resumed: only signals first seen from then on start runs, so a pause skips the signals that came during it. A change of `min_score` or of the definition keeps `since`.
  - Each minute the beat (`dispatch_automations`, after the webhook calls) takes up to 100 enabled signal automations that have no live run, no run that waits for approval, a running watchlist, a live creator, and a signal first seen since their last evaluation that found no ready account (10 minutes before it, for a watchlist run that commits late) or an account whose wait after a failed run (below) ended since then, those it tried longest ago first, so automations with a problem of **Checks** never hold the batch. A change of `since` or `min_score` clears that evaluation. Only a new signal can raise an account's sum, so an account row that stops being excluded starts a run at the next signal of the watchlist. An account is ready when the live scores (`signal_score`, as **Signal to campaign**) of its signals that the automation has not used add up to `min_score` or more. Its signals are first seen since `since`, at a row of the watchlist's list that is not excluded. One run starts for the ready account whose oldest unused signal is the oldest (`trigger_kind: signal`). The run and its signals' use (`automation_signals`) commit together, so a signal starts at most one run of an automation, whatever beat or retry comes. An automation with a problem of **Checks** starts nothing and keeps its signals for the fix. The run holds its signals until it takes its people, or until it succeeds when `find_people` is its only step. Then they are used, whatever the run's end. A run that takes nobody because nobody is at the account also used them, and so did a run the user cancels. A run that ends `failed` or `unknown` before it takes anyone (a claim refusal, a step that fails before the take, a worker lost) gives them back, and its account starts no run for 15 minutes, so a lasting failure does not fail a run each minute. The automation's other ready accounts start their runs meanwhile, and the account starts its next run when the 15 minutes end, with no new signal. At the third such run in a row for the account, its signals are used instead, and that run's `summary.signals` is `{given_up: true, failed_runs: 3}`: the account starts a run again only when new signals reach `min_score`. A run that uses the account's signals, or a change of `since`, starts its count of failed runs again. A run cancelled by an edit, a pause or a claim check before it takes anyone gives its signals back with no wait and counts no failed run. Only a cancel by a new version keeps `since`, so only then does the next beat count them again. A pause, a change of the watchlist and a switch away from `signal` move or clear `since`, so the signals given back never count again. A run that gives its signals back gets `summary.signals` `{given_back: true}`, written by the API, so the run page can tell signals given back from signals deleted with their watchlist or company. The beat queues no run while the creator's wallet or the project's hard cap cannot hold 1 credit for a definition that spends: its signals wait for the top-up. Signal to campaign (`signals.enrolled_at`) and each other automation use the same signal on their own.
  - A signal run works on its account only. With `find_people`, it searches that account (the step must use the watchlist's company list: 422 `AUTOMATION.SIGNAL_ACCOUNTS_LIST`) and adds the people found to the list, stamped with the account's domain, and does not move the rotation of other runs. Then, as without `find_people`, it takes the people of the list it has not taken in yet who work at the account (matched domain to domain, else by company name, as **Signal to campaign**), the best first, at most 25. When it takes nobody, `summary.taken.nobody` says why: `account_gone` (the row was deleted or excluded), `no_new_person` or `all_refused`.
  - `GET /{id}/runs/{run_id}` of a signal run shows `signal` `{account_id, account_name, signals}`: each signal it used as `{type, title, score, occurred_at}`, `score` the live score at the start, strongest first. `account_name` is `null` once the row is deleted. Other runs show `signal: null`.
  - 422 `AUTOMATION.WATCHLIST_PAUSED` refuses an enable or a create while the watchlist is paused, and fails a queued run at its claim (`invalid_configuration`). An edit of a disabled automation accepts it. A deleted watchlist leaves `watchlist_id` `null`: the automation starts nothing, and its preview lists `AUTOMATION.WATCHLIST_NOT_FOUND`. An edit that leaves the signal trigger or changes its watchlist cancels the queued run (`automation_edited`). A queued run's claim checks the automation's current trigger. `POST /{id}/run` is 409 `AUTOMATION.SIGNAL_TRIGGERED`.
- **People.** A run takes at most 25 people the automation has not taken in yet, the best score first. A person the project's exclusions, a HubSpot opt-out, the hold (#931), a reply, a prior contact or another campaign refuses is refused before any credit is spent and is not offered again. With `add_to_instantly`, the same holds for a person the batch would refuse for good: `excluded`, `already_handled` (a reply or a prior contact), `in_other_campaign` (a native campaign has them), `held_by_instantly` (an Instantly lead of the project) and `stopped`. A person with no email yet is not refused, so `find_emails` can look for one. An address found that a rule refuses is neither stored nor billed. The rules follow the other aliases of an excluded or opted-out person (#937). The person goes on to no later step and is taken in, so a later run does not search them again. Each person is worked on once: one the run did not reach (credit cap, a lookup that got no answer) stays for the next run.
- **Credits.** A run that spends holds up to `credit_cap` credits on one `Tab` (kind `automation`), at least 1. Each step bills only the results it stores, inside the credits the hold still has, and the close settles the hold from those charges. A run that reaches the cap stops spending and ends `succeeded` with `error_code: credit_cap_reached`; `summary` shows each step's counts and `credits_left`.
- **Approval.** `review` is true on a run whose `version` the user has not approved: its people enter the campaign as `draft`. `POST /{id}/runs/{run_id}/approve` (a finished run in review, or one that died, was cancelled or failed after it added people, else 409 `AUTOMATION.NOT_IN_REVIEW`; an edited automation 409 `AUTOMATION.RUN_OUTDATED`) records `approved_version`, so later runs add people with the campaign's normal status (`enrolled_status`). It also promotes the run's draft people to `active` when the campaign is running, after the enrollment rules are checked again (`summary.promoted`); in a draft campaign they stay drafts until the user activates it. A run in review writes nobody to HubSpot: its `write_hubspot` step succeeds with `output.held_for_approval` and the run keeps those people. The approval answers at once and queues a task (`write_held_hubspot`, as the approver) that writes them as the automation's creator. The task takes a claim on the held people first, so a second approval or a redelivery that overlaps it writes nobody twice, and a claim older than 17 minutes counts as dead. It checks the rules again before it writes, as the run did: exclusions, opt-outs, a reply or a message from another campaign, a place in another campaign; the automation's own campaign never refuses a person. Its result is `summary.hubspot_after_approval` (`created`, `existing`, `already_written`, `held_by_hubspot_gate`, `refused_since`, `error_code`), which is absent until the task ends. When the write fails (`hubspot_failed`, `hubspot_off`, `vendor_disabled`, `hubspot_token`, or `write_crashed` for any other error), the approval stands and the people stay held: approving the run again queues the task again, and a person already written is not written twice. Approving a run also promotes the drafts of every run that died, was cancelled or failed after it added people, of any version the user approved (this one included), when they went to the campaign the automation adds to now. Only the current version can be approved, so an edit that bumps `version` (also a pause that edits) removes from the campaign the `draft` targets that unapproved review runs of older versions added, except the drafts of a run that died, was cancelled or failed in a version the user approved and that went to the campaign the automation still adds to, which any later approval promotes (never a target that was sent anything); a run that succeeded unapproved loses its drafts and forgets those people: the next run takes them again under the new rules, and its approval promotes them. A run of an older version that ends after the edit gets the same cleanup when it ends, and each approval repeats it. The campaign beat does not complete an `active` campaign that still has `draft` targets of an unapproved review run of the automation's current version, unless that version is approved. An edit that bumps `version` sends the next run back to review. Each message still follows the campaign's `approve_before_sending`. Nothing here changes a campaign's status.
  - A run in review holds its `add_to_instantly` people and makes no batch. Instantly has no draft state: approving the run is the user's agreement that an active Instantly campaign sends to them. The approval answers at once and makes the batch after it commits, as the automation's creator; approving again makes no second batch, but tries again a batch that waits. An edit that bumps `version` drops the hold of an unapproved review run, and the next run takes those people again. An edit that replaces the `add_to_instantly` campaign, or removes the step, drops every hold of the older campaign whose batch is not made yet, approved or not, and the next run takes those people again into the new campaign. The same happens to a run that was going at the edit, when it ends. An edit that keeps the campaign keeps the holds. A review run that holds people keeps the webhook queue waiting, as one that holds HubSpot writes does.
- **Pause and cancel.** `PATCH {enabled: false}` cancels a queued run (`automation_paused`) and stops a running one before its next write. `POST /{id}/runs/{run_id}/cancel` ends a queued run and sets `cancel_requested` on a running one, which stops at its next store: the step that is going stores and charges nothing and ends `skipped`, as do the steps after it. The one exception is a `write_hubspot` step that wrote to HubSpot before the stop: it ends `succeeded` with its counts (see **Run**). `DELETE` removes the automation with its runs and gives a running run's hold back.
- **Error codes.** 404 `AUTOMATION.NOT_FOUND`, `AUTOMATION.RUN_NOT_FOUND`. The `AUTOMATION.WEBHOOK_*` codes and `AUTOMATION.NOT_WEBHOOK` are in **Webhook**. `AUTOMATION.WATCHLIST_NOT_FOUND`, `AUTOMATION.WATCHLIST_PAUSED`, `AUTOMATION.SIGNAL_ACCOUNTS_LIST` and `AUTOMATION.SIGNAL_TRIGGERED` are in **Signal**. 422 `AUTOMATION.INSTANTLY_NOT_CONNECTED` is in **Checks**. `AUTOMATION.INSTANTLY_CAMPAIGN_NOT_FOUND` is a `problems` code of the preview only. A run ends with `error_code` `vendor_failed`, `vendor_disabled`, `llm_failed`, `hubspot_off`, `hubspot_token`, `hubspot_failed`, `campaign_ended`, `instantly_campaign_not_found`, `instantly_not_connected`, `instantly_refused`, `instantly_unreachable`, `invalid_configuration`, `insufficient_credits`, `project_cap_reached`, `creator_left`, `creator_deleted`, `user_banned`, `reservation_expired` or `worker_outcome_unknown`.

## Notifications

All JWT, scoped to the caller. Notifications stay per user, but each is about one organization (`notifications.organization_id`, #323: the chat's, campaign's, inbound message's or wallet's) and disappears from the panel, the unread count and the digest once the user is no longer a member of it. Every notification names its organization (`organization_id` is NOT NULL); a turn on a teammate's chat names the chat's. A notification about an organization the user is not a member of (an active ban counts as not being one), such as a campaign whose owner was removed, is never created (#412): no row, no stream frame, no push, no email. The bell loads `GET /v1/notifications` once, then follows the stream.

- **Kinds.** `reply_urgent` (interested or meeting request), `reply` (other labelled replies), `search_done`, `low_credits`, `payment_failed` (an auto top-up charge failed), `approval_needed` (#215: a campaign holds messages), `search_failed` (#215: a plan stage stopped on its provider or a crash), `agent_question` (#215: the turn waits for the user: a question, the funnel or a plan), `linkedin_accepted` (#343), `bounces_high` (#343: a campaign's refused addresses passed the threshold; #747: its hard bounces paused it), `mailbox_error` (#343: a sender went from connected to error), `plan_renewed` (#343).
- **`href`** is an in-app path that opens the notification's own organization first (#743): `/switch?org=<organization id>&next=<url-encoded path>`, a web route that makes that organization the active one when the user belongs to it (and it is not already), then opens `next` (kept on the app's own origin). The path is `/inbox?m=<message id>`, `/?s=<chat session id>`, `/campaigns/<id>` or `/settings/integrations` (`mailbox_error`). `GET /v1/notifications`, the `notification` frame and the push carry this form; the row keeps the plain path. For `low_credits`, `payment_failed` and `plan_renewed` it stays `/billing/switch?org=<organization id>` (#323), which opens `/billing`. Emails link the same form with the app's origin in front.
- **`data`** by kind. Replies: `{message_id, name, label, channel, campaign}` (`message_id` is absent on rows from before #343; `campaign` is the campaign's name or `null`; never the reply's text, which is `quote`). `low_credits`: `{credits, organization}`. `payment_failed`: `{organization}`. `search_done`: `{chat, refunded, people?, companies?}` (`chat` is the title, `''` when untitled; `refunded` is per-row credits given back). `search_failed`: `{chat, done, units}`. `agent_question`: `{chat, reason: 'plan'|'funnel'|null}`. `approval_needed`: `{count, campaign}` (messages waiting when it fired). `linkedin_accepted`: `{name, campaign, channel: 'linkedin'}`. `bounces_high`: `{campaign, invalid, attempted}` (`attempted` is the people the campaign planned to write to, queued, awaiting approval or sent, plus the addresses refused; `invalid` is those refused as `INVALID_EMAIL`), or `{campaign, invalid, attempted, paused: true}` when hard bounces paused the campaign (`attempted` is its sent emails, `invalid` those that bounced hard). `mailbox_error`: `{mailbox, provider}` (`provider` `unipile` is a LinkedIn account, and the email and panel word it so; a Unipile status other than `ERROR`, `STOPPED` and `CREDENTIALS` raises none). `plan_renewed`: `{credits, plan, expired, organization}` (`expired` is last period's unused credits that were removed). Rows written before #215 lack the newer fields.
- **`browser`** says to show it as a browser notification: the user's setting for that kind's row, off under do-not-disturb, and never for `mailbox_error`, `payment_failed` and `plan_renewed`.
- **`cursor`** is the caller's newest stream entry id (`'0-0'` when none, `null` when Redis is down), read before the rows. Pass it as `Last-Event-ID` so nothing falls between the load and the stream.
- **`quote`** (#343, reply kinds only) is the opening of the reply's text, whitespace collapsed, 140 characters plus `…`. It is computed at read time from `outreach_inbound_messages.body` of the caller's own message `data.message_id` and never stored. It is absent when the message is gone or erased, belongs to another user, or the row has no `message_id`. The `notification` stream frame carries the same `quote`. Email, digest and push never carry it.
- **`POST /v1/notifications/read`** with no `ids` marks all of the caller's. When `updated > 0` it pushes a `read` frame to the caller's stream.
- **Stream** (`GET /v1/notifications/stream`, #242). Opening it never writes `"user".locale` (#795); a `locale` parameter is ignored. The language is saved only by an explicit choice: Settings → Profile (`setLocaleAction`, which skips an impersonated session), and the notification emails, the digest and the Web Push alerts (#436) use it; English until one is saved. `Last-Event-ID: <redis entry id, such as 1791209317734-0>` replays the frames after it (none or invalid means from now). 503 `NOTIFICATIONS.STREAM_UNAVAILABLE` when Redis is down. The `id:` is a Redis stream id (`<ms>-<n>`), not an integer. Every `notification` frame, live or replayed, is re-read by its item id through the panel's query before it is sent (#975): `item` and `unread` are the panel's now, `quote` included, and a frame whose item the caller no longer sees (they left its organization, the row is gone) is skipped. Frames: `notification {item, unread}` after a notification commits (`unread` is the bell's count, of every organization where the user is a live member; a user who left the item's organization since gets no frame); `read {ids: [uuid]|null, unread}` after a mark-read (`null` means all). `: ping` every 15 s. A caller who left the organization gets `error {code: 'AUTH.NOT_A_MEMBER'}` and the stream ends (see Server-sent events); the bell keeps the panel it has (notifications are the user's, across organizations) and reconnects once into the organization the session moved to. Backed by the Redis stream `user:{id}:notifications` (MAXLEN ~200, TTL 1 day; older frames are only in the panel reload). While a stream is open the server refreshes `user:{id}:open` (TTL 45 s), which means "a Zenbree tab is open". The web holds one stream per tab, reconnecting with backoff and `Last-Event-ID`. It fires the in-page browser notification for a `notification` frame with `item.browser`, unless this browser holds a push subscription of the user (the service worker shows it instead; both use `tag: item.id`) or the user turned push off on this browser.
- **Settings.** Rows with an email toggle are `{email, browser}`: `reply_urgent` (on, on), `reply` (on, off), `linkedin_accepted` (off, off), `approval_needed` (on, off), `search_done` (off, off), `search_failed` (on, on). `bounces_high` (browser off) and `low_credits` (browser on) are `{browser}` only, because their email is always sent. Defaults: `digest: {frequency: 'daily', hour: 9}`, `dnd: false`. `PUT` takes the same shape: `events` may omit any row (it keeps its saved value), an `email` sent for an `always` row is ignored, and any other key (such as `payment_failed`) is 422, as is a `frequency` outside `daily|weekly|off` or an `hour` outside 0-23. In-app is always on. Payment, mailbox and bounce emails and Better Auth's security emails cannot be turned off. The old `digest` boolean is gone: the migration turned `false` into `frequency: 'off'` (that migration is a rollback floor).
- **Rules.** Only system events are notified (a manual relabel, a purchase or a search the user is watching get the page's own feedback). `search_done` fires for a succeeded turn that added rows when it ran more than 5 minutes or no Zenbree tab holds the bell stream (`user:{id}:open`; Redis down counts as closed). The end of a turn notifies at most one kind: `search_failed` if a plan stage has error `provider`, `failed`, `crashed` or `disabled` (not `no_credits` or `over_budget`, the chat's credit card), else `agent_question` for a `needs_input` turn, else `search_done`. `approval_needed` fires after a dispatcher beat holds new messages of a campaign (`approve_before_sending`), once while an unread one for that campaign exists, and not when the campaign was activated less than 5 minutes ago with a tab open.
- **Email delivery.** One registry (`app.notifications.service.KINDS`) says per kind which settings row controls it, whether its email is `urgent` (now, capped), `now`, `digest`, `always` (no toggle, never held, not even by do-not-disturb) or `never`, and whether it has a browser. `always`: `bounces_high`, `low_credits`, `mailbox_error`, `payment_failed`. `never`: `plan_renewed`, `agent_question`. `search_failed` is urgent like `reply_urgent`: its own email and browser setting (both on by default) and the same 30-minute email cap, shared with urgent replies (the overflow goes to the digest as "ricerche ferme"). `agent_question` never emails and takes the `search_failed` row's browser choice. `approval_needed` emails through the digest only. Urgent reply emails: at most one per 30 minutes per user. The overflow, `reply`, `linkedin_accepted`, `approval_needed` and anything held by `dnd` are queued (`email_pending`) for the digest. Email needs `RESEND_API_KEY` and `EMAIL_FROM` (empty means inert).
- **Digest** (#343), per user. `digest.frequency` is `daily` (Monday to Friday), `weekly` (Monday) or `off`, at `digest.hour` (0-23) in `DEFAULT_TIMEZONE` (Europe/Rome). The hourly beat takes the queue of the users due that hour, so it goes out only with queued items. It then adds live lines read at send time: the messages awaiting approval over the user's campaigns (replacing the queued `approval_needed` count; with none left and nothing else queued, no email) and the credit balance of each organization the user administers. The subject comes from the counts (`12 messaggi da approvare e 3 risposte · venerdì 2 ott`), counts only, no names. Turning the digest `off` drops what was queued.
- **New triggers** (#343), all only for what the system causes. `linkedin_accepted` goes to each campaign owner whose target the acceptance dated (once per target; a campaign with no owner tells nobody). `plan_renewed` goes to the organization's admins on a paid `subscription_cycle` invoice, not on `subscription_create` or `subscription_update`. `mailbox_error` goes to the connection's user when a sender goes `connected` to `error` (a refused token or send permission, or Unipile's unhealthy account status), never again while it stays in error and never for the user's own disconnect. `bounces_high` fires once per campaign (a `bounces_high` notification for that campaign exists, read or not) when at least 20 email people were tried and more than 5% were refused `INVALID_EMAIL` (refused at send, or skipped at planning for an address that is not exactly one valid one). Nothing was sent to those addresses, so the campaign is not paused. Bounces read from the mailbox (see Bounces) pause it and send their own `bounces_high`, with `paused: true`, each time they pause it.
- **`low_credits`** fires once per drop below 200 credits (re-armed at 200 or more), armed per admin and organization (`low_credit_alerts`, #323), never while auto top-up is enabled. It is judged on the balance net of open holds and checked by `on_balance_changed` after each balance change (#243), not by a beat. `notification_settings.last_seen_at` and `low_credits_armed` are no longer read.
- **Web Push** (#343, `app/notifications/push.py`): a browser alert with no Zenbree tab open. Config is `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY` and `VAPID_SUBJECT` (`mailto:` or `https:`); any one empty makes push inert. Table `push_subscriptions(endpoint PK, user_id, p256dh, auth, created_at)`: the endpoint is the identity, so a `PUT` by another user with the same `auth` (the same browser) moves the row to them. `GET` returns `public_key` (`null` means inert: the web's enable button only asks for the notification permission, which the in-page alert needs) and `subscribed` (so a browser can tell its own subscription from one another account holds). `PUT` upserts by endpoint: 409 `NOTIFICATIONS.PUSH_TAKEN` when another user holds the endpoint and the `auth` differs (knowing an endpoint is not being that browser); 422 `NOTIFICATIONS.PUSH_ENDPOINT` unless the endpoint is https, port 443, has no credentials, and its host is `fcm.googleapis.com`, `updates.push.services.mozilla.com`, `web.push.apple.com` or `*.notify.windows.com` (SSRF: the server posts to this URL, and redirects are not followed); 503 `NOTIFICATIONS.PUSH_UNAVAILABLE` when inert. `DELETE` removes the caller's own only. `POST …/test {endpoint}` sends a test alert to that one browser: 409 `NOTIFICATIONS.PUSH_NO_SUBSCRIPTION` when the caller has no such subscription (or the push service just said it is gone), 502 `NOTIFICATIONS.PUSH_FAILED` when the push service refuses it, 503 when inert, 422 without an `endpoint`. `deliver()` pushes to each of the user's browsers when `item.browser` is true. A 404 or 410 from the push service deletes that subscription. Any other failure on one browser is logged by error type and the others still get the alert. No database connection is held while a push service answers, and it never raises. The payload is `{id, title, body, href}` rendered server-side in the user's `"user".locale` (the test alert too): the kind, the name and campaign, and counts, never a reply's text.
- **Web side of push.** The web keeps a granted browser's subscription current on every signed-in page (the bell, no prompt): it replaces a subscription made with a key other than `public_key` (a `DELETE` of the old endpoint, then a new subscription) and `PUT`s one that is not in `subscribed`. Sign-out sends `DELETE` while the session is still valid, then unsubscribes the browser, and a failure never blocks the sign-out. "Disattiva su questo browser" on the settings card does the same and keeps that browser off (no push, no in-page alert, no re-sync; `localStorage` key `zb-push-off`) until the user turns it on there. The web serves the worker at `/sw.js` (a route handler, no auth): `push` shows `{title, body, tag: id, data: {href}}` and `notificationclick` focuses a Zenbree window and navigates it to `href`, else opens one. The `href` is resolved against the app's origin and followed only when it stays on it, so `//host`, `/\host` and a path with a tab or newline in it open `/`. The bell panel applies the same rule.

## Webhooks

Outbound and signed (E9.3 #93). JWT or `sbk_` key of an admin of the organization (403 `AUTH.ORG_ADMIN_ONLY` for a member, #308). Endpoints belong to the organization (#323, `user_webhooks.organization_id`; `user_id` is the admin who made it): every admin of the active organization lists, tests and deletes all of them, and they receive the events of every member's lists, campaigns and replies. The web manages them on Settings › Webhooks (`/settings/webhooks`, admins only).

- `GET /v1/integrations/webhooks` returns the organization's endpoints, never their secrets (a receiver-revoked one carries `gone_at`, else `null`), and `events`, the subscribable names.
- `POST` returns `secret` (`whsec_…`) only there; a lost secret means delete and create. `url` must be `https://`, at most 2000 characters, and must not resolve to a private, loopback, link-local or metadata address (422 `WEBHOOKS.INVALID_URL`; re-checked with DNS pinning on every delivery, and redirects are not followed). `label` is 1-120 characters. `event_names` holds 1 or more of the events below (422 otherwise). At most 10 live endpoints per organization (409 `WEBHOOKS.CAP_REACHED`). Without `OAUTH_TOKEN_ENCRYPTION_KEY` the create answers 503 `WEBHOOKS.NOT_CONFIGURED`.
- `DELETE` returns 204 and deletes the endpoint's history (a receiver-revoked endpoint is deleted the same way and counts toward the cap until then); 404 `WEBHOOKS.NOT_FOUND` when unknown, already deleted or another organization's.
- `POST …/{id}/test` sends a signed `webhook.test` (`data: {}`) now through the webhooks worker, whatever the subscriptions, and never retries it. `status` is the endpoint's HTTP status, `null` when it did not answer. The route waits up to 45 s for its delivery; the task expires after the same 45 s, so a test nobody waits for is dropped. 10 tests a minute per user, past it 429 `WEBHOOKS.RATE_LIMITED` with `Retry-After: 60`; at most 1 test in flight per organization and 4 in the API process (the route pins a threadpool slot while it waits), past either 429 `WEBHOOKS.TEST_BUSY` (#966). 409 `WEBHOOKS.REVOKED` for an endpoint with `gone_at`.

- `GET …/{id}/deliveries` (#943) returns `{deliveries}`: the newest attempts to one endpoint, newest first, at most 50 (404 `WEBHOOKS.NOT_FOUND` as above). Each is `{id, event_id, event_type, is_test, attempt, attempted_at, status_code, category, will_retry}`. `event_id` is the `webhook-id` header, so the retries of one event share it. `attempt` starts at 1. `is_test` is true for `webhook.test`, which is never a production event and never retried. `status_code` is `null` when the receiver did not answer. `category` is `null` on a 2xx, else `timeout` (no answer within the 10 s connect/read timeout or the 30 s deadline), `blocked` (the SSRF guard refused the host), `unreachable` (DNS or connection), `rate_limited` (429), `server_error` (5xx), `gone` (410) or `rejected` (any other status, not retried). `will_retry` is true when a retry was queued after the attempt. A row never holds the payload, the URL, the secret or the receiver's answer. The 50 newest rows of an endpoint stay: each attempt prunes the older ones, and an admin's delete deletes the history. A row is written only while the endpoint is live: a delivery that ends after the delete or the 410 leaves none. There is no manual retry: a resend must repeat the exact body (and so the same `webhook-id`), which would mean storing the payload with its emails and names.

Which endpoints an event reaches (#323): those of the organization of the list (`list.completed`), the campaign (`campaign.finished`, `sequence.stopped`, `contact.replied`) or, for a reply that matched no campaign, the inbound message's project. Never another organization's.

**Delivery** follows [Standard Webhooks](https://www.standardwebhooks.com), so any of its libraries verifies it, as for Svix. `POST <url>` with body `{type, timestamp, data}` (`timestamp` is the event's ISO 8601 time) and headers `webhook-id`, `webhook-timestamp` (unix seconds) and `webhook-signature: v1,<base64(HMAC-SHA256(key = base64-decode(the secret after whsec_), msg = "<webhook-id>.<webhook-timestamp>.<raw body>"))>`. Compare in constant time and reject a timestamp more than a few minutes off. `webhook-id` is stable across retries of one event, so dedupe on it. Any 2xx is success. No answer within 30 s (the whole request), 429 or 5xx is retried after 30 s, 5 minutes and 30 minutes. 410 revokes the endpoint: it sets `gone_at`, nothing more is sent, and the endpoint stays listed with its history until an admin deletes it. Any other status (3xx, 4xx) is not retried. Delivery is at least once with no ordering. The secret is stored encrypted (`OAUTH_TOKEN_ENCRYPTION_KEY`). Deliveries run on the Celery queue `webhooks`, consumed only by the compose service `worker-webhooks`.

**Example receiver** (Node 20+, no library; a Standard Webhooks library does the same). Verify against the raw body, answer 2xx fast, and dedupe on `webhook-id`, because a retry repeats it:

```js
// receiver.mjs: WEBHOOK_SECRET=whsec_… node receiver.mjs
import { createHmac, timingSafeEqual } from 'node:crypto';
import { createServer } from 'node:http';

const key = Buffer.from(process.env.WEBHOOK_SECRET.replace('whsec_', ''), 'base64');
const seen = new Set(); // use a store with an expiry in production

createServer((req, res) => {
  const chunks = [];
  req.on('data', (c) => chunks.push(c));
  req.on('end', () => {
    const body = Buffer.concat(chunks);
    const id = req.headers['webhook-id'];
    const ts = req.headers['webhook-timestamp'];
    const want = createHmac('sha256', key).update(`${id}.${ts}.`).update(body).digest('base64');
    const ok = String(req.headers['webhook-signature']).split(' ').some((sig) => {
      const got = Buffer.from(sig.replace('v1,', ''));
      return got.length === Buffer.byteLength(want) && timingSafeEqual(got, Buffer.from(want));
    });
    if (!ok || Math.abs(Date.now() / 1000 - Number(ts)) > 300) return res.writeHead(401).end();
    if (!seen.has(id)) { seen.add(id); console.log(JSON.parse(body).type); }
    res.writeHead(200).end();
  });
}).listen(8080);
```

| `type` | When | `data` |
|---|---|---|
| `list.completed` | A chat or API run ends `succeeded` after adding rows to a list. One per list that grew. | `{list_id, entity: 'company'\|'person', chat_session_id, job_id}` |
| `contact.replied` | A reply arrives (email or LinkedIn). Not autoresponders, opt-outs or a reply whose `sender_authenticated` is `false` (#421). Sent before the reply is labelled. | `{message_id, channel: 'email'\|'linkedin', from, name, campaign_id}` (`campaign_id` is `null` when no campaign matched). Never the reply's text. |
| `campaign.finished` | The dispatcher marks a campaign `completed`: every sequence ended. | `{campaign_id, name}` |
| `sequence.stopped` | A person's sequence stops early. One per campaign target, also for the campaigns of other owners in the project that a reply reaches through the person's aliases (#931). A `replied` reason can come from a reply whose `sender_authenticated` is `false` (#421). | `{campaign_id, target_id, reason: 'replied'\|'unsubscribed'\|'excluded'\|'bounced', email, linkedin_url}` |

## Audience identity

An identity (#937) is one person or account that several list rows, a CRM record or an external sequencer lead stand for. Rows still deduplicate inside their list, and billing and delivery count rows as before: the same email in two lists is two rows and two charges. An identity only lets a check follow every exact alias we know.

- **Visibility.** An identity, its aliases and its conflicts belong to one project (a client) and are never read, matched or written across projects or organizations, so another project's fields stay private. The routes act on the active project (`X-Project-Id`); a row or conflict of another project or organization is 404.
- **Aliases** (`audience_aliases`): an exact `email`, `linkedin_url` or `domain` (a company's `domain`, else its `website`), or a provider id. A name is never an alias: two people or companies with the same name never merge, and a row with no exact alias has no identity. A value belongs to one identity of its entity in a project: a company page and a person can hold one LinkedIn URL, each in its own identity (the key is project, entity, kind, namespace and value). Aliases are append-only with their `source` and `observed_at`: a changed cell adds an alias, and a provider refresh never rewrites the source or time of one already stored, so a trusted value stays. The stored form is the exclusion normalizer's (`app.exclusions.rules.normalise`), so a followed alias matches a cell exactly as an exclusion rule does: email lower-cased, LinkedIn URL without scheme, `www.` after a scheme, query and trailing slash, domain without scheme, `www.` and path and never a shared social host. A LinkedIn URL is an alias only when it is the page of the row's entity, with a slug: `/in/<slug>` for a person, `/company/`, `/school/` or `/showcase/<slug>` for an account (`audience_linkedin_fits`, `aliases.linkedin_fits`; one rule in SQL and Python, compared by a test). A company page on a person row, or `linkedin.com/in` with no slug, is no alias: it would put every employee of a company in one identity. A role address (`info@`, `sales@`, `contact@`, `hello@`, `support@`, `admin@`, `office@`, `team@`, and the like; `ROLE_LOCAL_PARTS`) is never an alias: everyone behind it would join one identity.
- **Provider ids** use `kind` `crm_object` (`namespace` `hubspot:<portal>:contact` or `hubspot:<portal>:company`) and `external_lead` (`namespace` `<provider>:<workspace>`, `value` the lead id). `app.audience.link.attach_alias` records one on an identity (a kind the identity's entity cannot hold, such as an email on a company, raises), `attach_new_alias` links a person or account that no list row holds (the identity that has the alias, else a new one) and `app.audience.follow.find_identity` reads it; HubSpot import (#923) and Instantly (#929) call them. No other schema change is needed.
- **When a row links.** A writer never links in its own transaction. `add_rows`, `apply_row_updates`, a hand edit (`PATCH /v1/lists/{id}/rows/{row_id}`, source `manual`) and a merge mark the rows they wrote or left unlinked (`audience_link_queue`: one insert, no lock beyond the row the writer already holds). After the commit, the `link_audience_rows` beat (every 30 s, `System(DUE_WORK)` only to pick the organizations that have marked rows) links up to 200 marked rows of each organization as `ForOrg` of it, one row to a transaction (`audience_link_row`): no identity holds its aliases, a new one; one does, that one; two or more, or one other than the row's own, a conflict. Nothing is merged and no alias is attached on a conflict. A row that fails stays marked, behind the others, and is given up after 5 failures since its last write (logged at warning, `audience.link_gave_up`): it stays unlinked and protected by its own cells until a write marks it again. A mark that a later write refreshed is not deleted by a link that read the older one. A beat stops starting rows at its time budget, inside an organization too, and the task's own time limit ends it. So a slow beat never leaves a row unlinked for good, and a missed one is made up by the next. A link is one pass: it locks the identities it read in id order (a merge locks in id order too), then inserts the aliases in (kind, value) order. When another turn took a value or a merge folded an identity since the read, the pass raises `serialization_failure`, which releases every lock, and the row runs again in a new transaction (three passes), so the conflict with the other turn's identity is recorded, never dropped, and the link records no conflict that names a folded identity. `attach_alias` does not give that guarantee: it follows the identity it is given to its survivor, but a conflict it records can name an identity that a merge folded between its read and its insert, and `resolve` then follows the folded side to its survivor. Callers of `attach_alias` (HubSpot, Instantly) must not assume a conflict's identities are live. `resolve` follows a folded identity to its survivor; a conflict whose two sides are one identity closes as merged. Deleting a row or a list keeps the identity and its aliases, which opt-outs depend on.
- **Until a row is linked** it is no less protected than before this feature: its own email, LinkedIn URL and domain still match the exclusion rules and the enrollment checks directly, because those read the row's cells. Only following its other aliases (an opt-out of its email reaching its LinkedIn URL or another email) waits for the link, up to one beat.
- **What follows an alias.** `load_rules` returns each exclusion rule plus the other exact aliases of the person or account it names, in that project: an opt-out of one email also covers the LinkedIn URL and other emails of that person in search results, enrichment, enrollment, refill and the send path. Lifting the rule lifts them. The HubSpot opt-outs that enrollment reads (`gate.opted_out_rules`) follow aliases the same way. `enrollment_context` also returns the alias map, so a person already a target, replied or contacted under one alias is the same person under another (`hold` or `skip`). Opt-out and reply stops of #931 build on this. An alias is read in the entity it names (`entity_of`): an email is a person's, a domain an account's, and a LinkedIn URL an account's when its path is `/company/`, `/school/` or `/showcase/`, else a person's. A person's opt-out so never follows the account page that shares a URL with it.
- `GET /v1/audience/rows/{row_id}` returns `{row_id, identity_id, aliases: [{kind, namespace, value, source, observed_at}], open_conflicts}`. `identity_id` is `null` and `aliases` empty for a row with no identity. 404 `AUDIENCE.ROW_NOT_FOUND`.
- `GET /v1/audience/conflicts?status=open|merged|kept_apart&cursor=&limit=` returns `{conflicts: [{id, entity, status, created_at, resolved_at, row_id, evidence, identities: [{id, aliases, rows}]}], next_cursor}`, oldest first, 50 by default and 200 at most; pass `next_cursor` back as `cursor` until it is `null`. `evidence` lists the values that tied the identities, each with the identity, source and time of the alias it clashed with.
- `POST /v1/audience/conflicts/{id}/resolve {action: 'merge' | 'keep_apart', into?}` returns `{status, identity_id}`. `merge` folds the other identity into `into` (one of the two; the older when absent): its aliases and rows move, and a row the conflict left unlinked joins the winner. `keep_apart` records the pair as two people and it is not raised again. Any member of the project may resolve. 404 `AUDIENCE.CONFLICT_NOT_FOUND`, 409 `AUDIENCE.CONFLICT_CLOSED`, 422 `AUDIENCE.CONFLICT_SIDE` (`into` is neither identity).
- **Backfill.** The migration `20261016190050_audience_identity` links every existing row, oldest first, without touching cells, row ids, charges or activities. It is set-based: rows are grouped by the aliases they share (union-find by hooking and pointer jumping, a few rounds for a chain of any length), and a group is written in a few statements. Only a group where a later row bridges rows that did not share an alias is linked row by row, as a write would, so existing ties between two identities become open conflicts.
- **Not yet wired.** Signals (watchlists, #941) and event reconciliation (inbox and webhook matching, #930) do not resolve through identities yet; they can call `find_identity` and `alias_map`.
- **Design.** An identity belongs to one project, never shared across an organization's projects: a client's person is that client's, as its exclusions are. Alternatives left out: one identity across the organization (it needs field filtering between projects), and merging on name plus company.
